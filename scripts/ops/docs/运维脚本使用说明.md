| 脚本 | 频率 | 清单覆盖 | 写操作 |
| --- | --- | --- | --- |
| `scripts/daily-check.sh` | 每天 | **覆盖最广（12 章）**：主机/负载/内存/磁盘/inode、systemd 服务、Docker、容器日志扫描、健康端点、备份新鲜度、监听端口与 UFW、仓库状态 | 只读 |

| `scripts/monthly-ops.sh` | 每月 | 隔离恢复演练、依赖更新检查、故障记录复盘、文档更新 | **可选执行**，默认演练 |

| `scripts/ops-report.py` | 被 monthly 调用 | 多期报告汇总、检查闭环新鲜度 | 只读 |
| `scripts/cert_check.py` | 被 weekly 调用 | 证书有效期（已有脚本） | 只读 |
| `scripts/security-check.sh` | 被 weekly 调用 | 异常登录与安全访问（已有脚本） | 只读 |

> **2026-10-05 新增三处判据**（都在 `lib/ops-monitor.sh` 的 `ops_monitor_check()` 与
> `ops_systemd_check()` 里，由 daily-ops 与 weekly-check 共用）：
>
> | 判据 | 抓什么 |
> | --- | --- |
> | `mon.textfile` | `node_textfile_scrape_error != 0` —— textfile 收集器里**有文件重复定义同名指标**，指标真值可能被遮蔽（2026-10-04 就栽在这：孤儿 `.prom` 让备份的「假告警」与「critical 永不触发」同时发生） |
> | `systemd.failed-units` | **不在白名单**里的 failed 单元。白名单读 `SYSTEMD_FAILED_ALLOWLIST`（**缺省为空** = 任何 failed 都算问题） |
> | `systemd.<备份定时器>` | 原先是「找不到就记 INFO」→ 判据**空转**（`BACKUP_TIMER_UNIT` 当时还是改名前的旧名，永远走 else、从不检查）。现在找不到记 **WARN** |
>

> **`daily-check.sh` 没有任何定时器在跑**（只有 daily-ops / weekly-check / monthly-ops 三个 timer），
> 判据落在没人按计划跑的地方等于没有判据。`daily-check.sh` 因此**保持原状**，
> 不在两处重复实现（否则就是两份会漂移的判据）。
>
> **配置**：`SYSTEMD_FAILED_ALLOWLIST` 每一项都要能说清理由。本项目当前只有一项
> `repass.service` —— `INC-S2-003` 判它是云厂商控制台「重置密码」辅助链路，
> 刻意保留（*「禁用、删除或改写它可能让未来的控制台恢复能力失效」*）。
> 另一条 `setupfirst.service`（`INC-S2-002` 判为无效残留）**已清掉**，**不进白名单**。

**`daily-check.sh` 与 `daily-ops.sh` 的分工**

仓库里原本另有一份 `scripts/linux/daily-check.sh`（429 行，只输出原始数据），
**已于 2026-09-28 删除**，由本目录的版本取代。现在两个日巡检脚本都基于同一套公共库：

- `daily-check.sh` —— 覆盖最广，12 个章节；2026-09-28 在服务器实测通过
  （FAIL=0 WARN=2 OK=27 INFO=9，退出码 1）
- `daily-ops.sh` —— 精简版，聚焦日清单五项，报告格式与 weekly / monthly 完全一致

两者**可以并存**：报告都写进 `ops.conf` 的 `REPORTS_DIR`。
不需要两套时**建议只挂一个**，避免同一目录下出现两份日巡检报告 ——
挂哪个见 `systemd/MEMO.md`。若只关心清单覆盖面与排障证据，用 `daily-check.sh`；
若只想要「结论 + 退出码 + 告警接入」的极简输出，用 `daily-ops.sh`。

## 2. 公共约定

三个脚本共用 `lib/ops-common.sh`（和 Python 侧的 `lib/ops_common.py`），因此：

**结论分级**

| 级别 | 含义 |
| --- | --- |
| `OK` | 已确认符合预期（**必须实际验证过**） |
| `WARN` | 需要关注，但尚未影响可用性 |
| `FAIL` | 已确认异常，需要处理 |
| `INFO` | 事实记录，**不构成判断**（包括所有「无法验证」的情况） |

**退出码**（可直接接 systemd / cron / 告警）

| 码 | 含义 |
| --- | --- |
| 0 | 未发现异常 |
| 1 | 存在 WARN |
| 2 | 存在 FAIL |
| 3 | 脚本自身错误（参数、依赖、环境） |

**通用参数**：`--conf <文件>` `--json <文件>` `--markdown <文件>` `--no-json`
`--quiet/-q` `--no-color` `--help/-h`

**只读保证**：`daily-check.sh`、`daily-ops.sh` 与 `weekly-check.sh` 不做任何修改性动作。
唯一写入是报告文件（JSON/Markdown）与 `--record` 的记录文件。

## 3. 安装

**当前实际部署**（2026-09-28 完成）：工具包在 `KnowTrace-Workflow/scripts/ops/`（仓库权威源），
部署副本在 `/opt/knowtrace-ops/`，配置在 `/etc/knowtrace/ops.conf`。

```bash
# 0) 从仓库检出部署（推荐路径；不要把工具包放进 /opt/knowtrace）
sudo mkdir -p /opt/knowtrace-ops
sudo cp -a <仓库>/scripts/ops/{lib,scripts,systemd,docs,README.md,ops.conf.example} /opt/knowtrace-ops/

# 1) 建配置。注意：配置不放在工具包目录，而放 /etc/knowtrace/，
#    这样「重放部署」不会把它覆盖掉（ops.conf 含内网地址与账号名，已在 .gitignore）
sudo mkdir -p /etc/knowtrace
sudo cp /opt/knowtrace-ops/ops.conf.example /etc/knowtrace/ops.conf
sudo chmod 600 /etc/knowtrace/ops.conf
sudo vi /etc/knowtrace/ops.conf    # 至少确认 PROJECT_DIR / CERT_DOMAINS / PUBLIC_HEALTH_URL

# 2) 建报告目录
sudo mkdir -p /var/lib/knowtrace/reports

# 3) 赋权
sudo chmod +x /opt/knowtrace-ops/scripts/*.sh

# 4) 挂定时任务 —— 见 systemd/MEMO.md。顺序必须是「先手工 start 验证，再 enable」
```

> ⚠ **不要在 `/opt/knowtrace-ops/` 根目录另外放一份手册**。曾经有过一份过时副本
> （早期手工 scp 的遗留，后续修订都没同步），而单元里的 `Documentation=` 正指向它 ——
> 等于把 `docs/` 那份维护中的手册晾在一边。手册的权威位置就是 `docs/`。

`ops.conf` 查找顺序：`--conf 参数` > 环境变量 `OPS_CONF` > `<工具包根>/ops.conf` >
`/etc/knowtrace/ops.conf`。

`ops.conf` 需要 root 才可读（600），所以定时任务用 root 跑。

## 4. 日常使用

```bash
# 每日：直接跑，或加 --record 生成当日记录
sudo bash /opt/knowtrace-ops/scripts/daily-ops.sh --record

# 每周：--write-record 生成周记录骨架
sudo bash /opt/knowtrace-ops/scripts/weekly-check.sh --write-record

# 每周首次还要留存日志基线，下周才能对比「新增模式」
sudo bash /opt/knowtrace-ops/scripts/log_analyzer.py --save-baseline

# 每月：先演练看一眼计划（不带 --apply 绝不改东西）
sudo bash /opt/knowtrace-ops/scripts/monthly-ops.sh

# 确认计划没问题后真正执行
sudo bash /opt/knowtrace-ops/scripts/monthly-ops.sh --apply
```

**安静模式（适合定时任务）**：只输出 WARN/FAIL，退出码即结论
```bash
sudo bash /opt/knowtrace-ops/scripts/daily-ops.sh --quiet --json /var/lib/knowtrace/reports/
```

**汇总看趋势**：
```bash
sudo python3 /opt/knowtrace-ops/scripts/ops-report.py \
     --reports-dir /var/lib/knowtrace/reports --markdown /var/log/knowtrace-logs/汇总.md
```

## 5. monthly-ops.sh 的安全模型

这是唯一会改动服务器的脚本，因此设了 **四道闸**，缺一即降级为「只出计划」：

1. 命令行给了 `--apply`（不带就是演练模式）
2. `ops.conf` 里对应开关为 1（`MONTHLY_RESTORE_DRILL` / `MONTHLY_PRUNE_BACKUPS` / ...）
3. 没有用 `--without-<动作>` 关掉它（`--with-<动作>` 可临时强制打开）
4. 当前小时落在 `MONTHLY_WRITE_WINDOW` 内（若配置了，例 `1-6` 表示 UTC 凌晨 1~6 点）

之后还需要**输入 `yes` 确认**（`--yes` 可跳过，供无人值守）。

写操作与开关对应：

| 动作 | 开关 | 实际调用 | 风险 |
| --- | --- | --- | --- |
| 隔离恢复演练 | `MONTHLY_RESTORE_DRILL` | `verify-restore.sh <归档>` | 低（`network none` 临时容器，不碰生产） |
| 备份保留策略 | `MONTHLY_PRUNE_BACKUPS` | `prune-backups.sh` | **会删除旧备份** |
| 日志栈内存占用记录 | `MONTHLY_STOP_LOKI` | （默认 0，只记录不停） | 低（Loki 常驻，见下） |
| 日志与报告归档 | `MONTHLY_ARCHIVE_LOGS` | `tar` 报告目录 | 低 |
| 汇总报告 | `MONTHLY_BUILD_REPORT` | `ops-report.py` | 无（只写报告） |

**刻意不自动化的两项**：

- **apt 升级**：`--apply` 也还不够，必须再加 `--apply-updates`。依赖升级在生产属高风险变更。
- **重启系统**：只提示「需要重启」，永远不执行。

**恢复演练的准入条件**（不满足会拒绝执行，且记为 FAIL）：
归档存在、新鲜度 ≤ `THRESHOLD_RESTORE_DRILL_MAX_AGE_HOURS`（默认 72h）、
归档 SHA-256 校验通过、所需镜像在本地、`/tmp` 与内存充足。
另有 `--without-restore-drill` / `--without-prune-backups` 等可单独关掉。

## 6. 挂定时任务（systemd timer）

**2026-09-28 已挂上并启用。** 单元文件在 `systemd/`，已 `cp` 到 `/etc/systemd/system/` 并
`enable --now`。当前的排期：

| 定时器 | OnCalendar | 实际下次触发 |
| --- | --- | --- |
| `knowtrace-workflow-backup.timer`（原有） | 19:21 UTC | 每天 |
| `knowtrace-workflow-daily-ops.timer` | `*-*-* 19:30:00 UTC` | 每天 ≈19:34 |
| `knowtrace-workflow-weekly-check.timer` | `Mon *-*-* 20:00:00 UTC` | 周一 ≈20:04 |
| `knowtrace-workflow-monthly-ops.timer` | `*-*-01 21:00:00 UTC` | 每月 1 日 ≈21:06 |

实际触发会带 `RandomizedDelaySec` 的随机偏移，所以不是整点。

**时序不是随便定的**：日/周巡检要检查「备份是否新鲜」与「归档能否校验」，
所以必须排在备份（19:21 UTC）之后。改时间时别越过备份。

装法（重建时的完整步骤）：

```bash
sudo cp /opt/knowtrace-ops/systemd/*.service /opt/knowtrace-ops/systemd/*.timer /etc/systemd/system/
sudo chmod 644 /etc/systemd/system/knowtrace-*.service /etc/systemd/system/knowtrace-*.timer
sudo systemctl daemon-reload

# 先手工 start 验证一次，再 enable —— 顺序别反
sudo systemctl start knowtrace-workflow-daily-ops.service
journalctl -u knowtrace-workflow-daily-ops.service --since "-2min" --output=cat

sudo systemctl enable --now knowtrace-workflow-daily-ops.timer
sudo systemctl enable --now knowtrace-workflow-weekly-check.timer
sudo systemctl enable --now knowtrace-workflow-monthly-ops.timer
systemctl --no-pager list-timers 'knowtrace*'
```

> ⚠ **为什么必须先 start 再 enable**：单元里的 `Documentation=` 如果写成裸百分号编码，
> systemd 会在**运行时**才报 `Failed to resolve unit specifiers ... Invalid slot`
> 并把整条丢掉，而 `systemd-analyze verify` 查不出来。
> 先 start 一次是为了让这个错误在 enable 之前暴露。详见 `systemd/MEMO.md` 第 6.1 节。

**退出码语义**：三个 service 都带 `SuccessExitStatus=0 1 2`，让 systemd 不因
「检出 WARN/FAIL」把单元标成 failed —— 退出码表达的是**巡检结论**，不是**服务成败**。
否则 `systemctl --failed` 长期挂红，反而让人忽略真正的故障。

**接告警**：让定时任务把退出码交给已有告警链路即可，例如
`ExecStartPost` 判断 `$EXIT_STATUS`，或用一个包装脚本在退出码 ≥1 时
调用 `scripts/linux/test-email-alert.sh` 同款邮件通道。
`--quiet` 让输出只剩 WARN/FAIL，适合直接作为邮件正文。

> **公网探测已带重试（2026-09-28 加固）**：原先 `check_http` 是单次
> `curl --max-time 8`，实测遇到过一次瞬时失败（返回 `000`，紧接着连测 3 次都正常），
> 单次抖动就会记 FAIL 并让退出码变 2 —— 接到告警链路上会变成误报。
> 现在统一走 `ops_http_probe`：只在「拿不到状态码」时重试（默认 3 次），
> 拿到 4xx/5xx 立即返回（服务确实应答了，重试没意义）。
> 尝试次数可用 `OPS_HTTP_RETRIES` 覆盖；FAIL 消息会注明「已重试 N 次」。

详细备忘（安装/回滚/排障/坑）见 `systemd/MEMO.md`。

## 7. 首次运行发现的实际问题

2026-09-28 在服务器上实测三个脚本，发现以下真实问题（脚本能自己报出来）：

1. **认证服务在生产用 GIN debug 模式**
   `log_analyzer.py` 扫到 `[GIN-debug] Running in "debug" mode. Switch to "release" mode in production.`
   同时 `knowtrace-workflow-auth-1` 的日志量在 24 小时内就超过 2 万行上限（唯一被截断的来源）。
   建议在 `.env` 里把 `AUTH_APP_ENV` 之类切到 release，可同时降低日志量与噪声。

2. **`/var/run/reboot-required` 存在** —— 有内核/库更新等着重启才生效，日周运维都会持续提醒。

   月运维会列出并在 `--apply-updates` 时才执行。

4. **`/var/log/knowtrace-workflow-backup.log` 已有 500+ 小时未更新**

5. ~~**告警出口存在单点**：Alertmanager 最后一行日志是 2026-09-08（启动信息）。~~

## 8. 与仓库的关系

**2026-09-28 已落位**：本工具包现在就在 `KnowTrace-Workflow/scripts/ops/` 里，按
`bash与python的运维使用建议.md` 第 5 节的规划放置。

```
KnowTrace-Workflow/scripts/ops/
├── scripts/    巡检脚本（daily-check / daily-ops / weekly-check / monthly-ops + 4 个支撑脚本）
├── lib/        Bash 与 Python 公共库
├── systemd/    6 个定时任务单元 + MEMO.md
├── docs/       本手册
├── README.md   工具包索引
└── ops.conf.example
```

`.gitignore` 已加 `ops.conf` —— 它含内网地址、端口与账号名，**不能入库**。
服务器上实际使用的配置在 `/etc/knowtrace/ops.conf`（600 root）。

**部署方式**：从仓库拷到 `/opt/knowtrace-ops`（**不要**放进 `/opt/knowtrace`，
否则会被项目部署覆盖）：

```bash
sudo cp -a scripts/ops/{lib,scripts,systemd,docs,README.md,ops.conf.example} /opt/knowtrace-ops/
```

> **用 `cp -a` 而不是 `cp -r`**：`cp -r` 对**已存在的目标文件会保留其原有权限位**，
> 所以若某文件第一次是以错误的模式拷进去的，之后每次重拷都不会修正它 ——
> 表现是「哈希一致但可执行位不对」。`cp -a` 采用源文件的模式，能自愈。
> （2026-09-29 实际踩到：`systemd/install.sh` 首次以 644 拷贝，重拷多次仍是 644。）

改脚本的流程应是「改仓库 → 部署」，不要再手工 scp 单个文件，
否则服务器上跑的是哪个版本无法追溯。
