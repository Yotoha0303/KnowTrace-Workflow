## 1. 问题一句话

**去掉 Next.js 之后，`src/features/` 那 16,319 行业务逻辑住哪？**

用户的目标是「**大规模调整技术栈，方便后续开发顺畅**」——
**这个目标成立**。但 `前端技术栈调整建议.md` 假设「**后端是 Go**」，
而本仓的后端**只有一半是 Go**：

| 服务 | 语言 | 有 OpenAPI 吗 |
| --- | --- | --- |
| `services/go-user-system`（认证） | **Go** | ✅ 有 swagger |
| **主应用业务逻辑**（记录 / 主张 / 证据 / 检索 / AI） | **TypeScript** | ❌ **0 个** |

**⇒ 建议文档里「Orval 消费 Go 后端 OpenAPI」对本仓只对一半。**
它的「立即执行落地清单」是**从零搭 Monorepo**，**完全没有覆盖这 16,319 行怎么处理**。

## 3. 三个方案

### A · 保留一个**独立 Node API**（Hono / Fastify + `zod-openapi`）

```
knowtrace-api/          ← Node 服务，承接 src/features（逻辑不动）
   ├── 26 个 route handler 从"薄壳"改成真 HTTP
   └── zod-openapi 从现有 Zod schema 生成 openapi.json
knowtrace-frontend/     ← 建议文档的 monorepo（Web/Tauri/RN）
```

| 项 | 评价 |
| --- | --- |
| 16,319 行 | ✅ **一行不动**（只换入口） |
| Orval | ✅ **立刻可用**（zod → openapi.json） |
| 类型一致性 | ✅ TS 端到端（zod schema 是唯一事实源） |
| 新增服务 | ⚠️ 多一个 Node 进程（运维面扩大） |
| 与建议文档 | ⚠️ **偏离**「后端=Go」的假设 |

### B · 把业务逻辑**迁到 Go**

| 项 | 评价 |
| --- | --- |
| 16,319 行 | ❌ **TS → Go 重写** |
| drizzle schema | ❌ 977 行 schema 要重做（GORM 或 sqlc） |
| 与建议文档 | ✅ **完全一致** |
| 工作量 | ❌ **大一个量级**（且丢掉 TS 端到端的类型共享） |

### C · Next.js 只做 API（保留 route handlers），页面换成 SPA

| 项 | 评价 |
| --- | --- |
| 改动量 | ✅ **最小** |
| 是否"去掉 Next.js" | ❌ **没有**——只是把它降级成后端 |
| 与用户目标（"用很久"） | ⚠️ 与「大规模调整技术栈」的方向相反 |

---

## 4. 推荐：**A**（但**这是推荐，不是裁定**）

**理由**（针对用户说的「这套技术栈会用很久」）：

1. **保住最大的资产**：F-3 的 94 个框架无关文件是本次迁移里**唯一免费的部分**。选 B 等于全部作废。
2. **Orval 才真正成立**：现在主应用**无 OpenAPI**（F-5），建议文档里「禁止手写 API 请求函数」**今天是空的**。选 A 后 `zod-openapi` 能从现有 schema 生成 ⇒ 该约束第一次有牙。
3. **全端类型一致**：Web / Tauri / RN 共用同一份生成的 client + Zod 校验——**这正是建议文档的核心价值**。
4. **Go 只做擅长的事**：认证服务已是 Go，**保持不变**。不为"统一后端语言"重写业务层，那是为一致性付超额代价。

**代价（如实）**：多一个 Node 服务 ⇒ 运维面 +1；与建议文档的"Go 后端"表述不一致（需在其文档里注明这个偏离及其理由）。
