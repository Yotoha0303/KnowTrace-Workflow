## 1. 要迁什么

`services/go-user-system/frontend` —— **68 个文件的完整 React 前端**（Vite + React 18 + Redux Toolkit + react-router-dom）。

**它与主应用功能重叠**（已核）：

| 认证前端 | 主应用对应 |
| --- | --- |
| `pages/auth/login-page.tsx` | `src/app/login/page.tsx` |
| `pages/auth/signup-page.tsx` | `src/app/register/page.tsx` |
| `pages/profile/profile-page.tsx` · `edit-nickname-page.tsx` | `src/app/account/page.tsx` |
| `pages/security/password-page.tsx` | 主应用账号流程 |
| `pages/admin/access-page.tsx` | 主应用 RBAC |
| `e2e/auth.spec.ts` | `tests/e2e/auth-flow.spec.ts` |

## 2. ⚠️ 先回答一个可能让"迁移"变成"删除"的问题

**逐页比对后，主应用是否已经覆盖了它的全部能力？**

| 能力 | 主应用有吗 | 判据 |
| --- | --- | --- |
| 登录 / 注册 | ✅ | `src/app/login` · `src/app/register` |
| 昵称编辑 | ✅ | `src/app/account` |
| 改密码 | ✅（需核实细节） | `src/app/account/actions.ts` |
| **RBAC 管理页**（`admin/access-page.tsx`） | ⚠️ **需核实** | 主应用有 RBAC 数据，但**是否有管理界面**未确认 |
| **注册开关 / 管理员流程** | ⚠️ 需核实 | — |

**⇒ 若全部已覆盖，则「迁移」的实质是「删除 + 确认无功能丢失」**，不是搬代码。
**若 `admin/access-page.tsx` 是独有的，需评估：在主应用重建，还是保留。**

**这一步必须在动手前完成**——否则可能删掉一个**有人在用**的界面。

## 3. 结构性问题：**这是 subtree 上游副本**

```text
$ git log --grep="Squashed 'services/go-user-system/'"
8d4b159 Squashed 'services/go-user-system/' content from commit 0f30a4b
```

**⇒ `frontend` 不是我们写的，是上游 `go-user-system` 自带的标准组成部分**
（上游把认证服务交付为「Go 后端 + 自带管理前端」的一体化形态，`ADR-0014` 记的就是这个安排）。

**用户的裁定是「在 `services/go-user-system/` 上改」** ⇒ **接受 subtree 冲突**。
**本方案据此执行，但必须记录代价**：

| 代价 | 说明 |
| --- | --- |
| 每次 `subtree pull` 冲突 | 删除 68 个文件 ⇒ 上游若更新它们，**必然冲突且需每次手工裁决** |
| 与 `ADR-0019` 叠加 | 认证库迁 PG **也改同一子树** ⇒ **两层本地改动叠在一起**，冲突更难解 |
| 无到期日 | 这是**长期成本**，不是一次性 |

**⇒ 建议在 `ADR-0020`（或独立的 subtree ADR）里把这个取舍**显式记成已接受的偏离**，
而不是让它成为"每次合并时才发现的问题"。**

## 4. 执行顺序

| 步 | 做什么 | 判据 |
| --- | --- | --- |
| **F-a** | **逐页比对**：确认主应用是否覆盖全部能力（§2） | 输出一张「能力 × 覆盖情况」表；**任何"未覆盖"项必须先有处置决定** |
| **F-b** | 若 `admin/access-page` 是独有的：**在主应用重建**（用新的 `apps/web` 栈） | 功能等价；**不得直接搬 Redux 代码**——主应用用的是 TanStack Query + Zustand |
| **F-c** | 删除 `services/go-user-system/frontend/` | `git ls-files 'services/go-user-system/frontend/*'` 为空 |
| **F-d** | 清理 `.github/dependabot.yml` 的该路径条目 | 该条目消失 |
| **F-e** | 清理 CI 的 `auth-frontend` job | job 消失；**同时确认 `KT-GAP-32`（受版本控制的测试必须在门内）不被违反** |
| **F-f** | `#40`（Tailwind 3 告警）随之关闭 | 目录不存在 ⇒ 告警消失 |

**步骤 F-c ~ F-f 必须成组完成**：删了目录但仍留着 dependabot/CI 配置 ⇒ **CI 会红且原因指向一个不存在的路径**。

## 5. 验证

| 正向 | 负向（注入什么必须失败） |
| --- | --- |
| 主应用的登录/注册/账号/RBAC 全部可用（e2e 覆盖） | 删掉一个主应用**没有**的认证前端功能 ⇒ **必须有 e2e 红**。若全绿，说明**该功能从未被测试覆盖**（比删错更严重） |
| `git ls-files 'services/go-user-system/frontend/*'` 为空 | 若还有残留文件 ⇒ 删除未完成 |
| CI 全绿 | 删除后若 CI 仍红 ⇒ **说明还有配置指向该路径**（dependabot / workflow） |
