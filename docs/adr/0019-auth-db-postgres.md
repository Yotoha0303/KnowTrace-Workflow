## 1. 背景

`ADR-0014` 把 `go-user-system` 以 `git subtree` 纳入 `services/`，并定下「MySQL、Redis、
PostgreSQL 保持独立数据卷」。那个决定只说明了**分开部署**，**没有说明为什么认证库用 MySQL**。

实测现状（2026-10-16）：

| 事实 | 证据 |
| --- | --- |
| 主应用已是 PostgreSQL 18 | `drizzle.config.ts:9` `dialect: "postgresql"`；`compose.yaml:20` `postgres:18-alpine` |
| 认证服务是 MySQL，驱动写死 | `go.mod:8,20` `go-sql-driver/mysql` + `gorm.io/driver/mysql` |
| goose 方言写死 | `cmd/main.go:76` `goose.SetDialect("mysql")` |
| **同一服务的 MySQL 主版本在 4 处冲突** | 根 `compose.yaml:37` 与两个 CI = `8.0`；服务自建 `compose.yaml:5`、`k8s/mysql.yaml:34`、`Makefile:282,284` = `8.4` |
| 排序规则也不一致 | `migrations/00001` 用 `utf8mb4_0900_ai_ci`；`k8s/mysql.yaml:55` 用 `--collation-server=utf8mb4_unicode_ci` |
| 主应用**从不读取**认证库 | `git grep -n "3306\|auth-mysql\|mysql" -- src/` → **0 命中**；两库间**只有 HTTP**（`AUTH_SERVICE_URL`） |

⇒ 结果是**两种 DBMS 并存**，而主应用侧原本就要维护一套 PG 的迁移、备份、恢复、巡检工具链。

### 1.1 一条改变前提的事实：存量数据已不可用

认证库随生产服务器于 **2026-10-08 停机且不续**而丢失：

| 检查 | 结果 |
| --- | --- |
| 本机是否有认证库备份 | ❌ **无**——`_ops-backups/` 只有 ops-toolkit / 证据报告 / TSDB / ledger，**无任何 MySQL dump** |
| 本机 MySQL 实例 | ❌ 无 |
| 本机 Docker | ❌ 无 |

**⇒ 本次不是「迁移存量数据」，而是「用 PostgreSQL 重建认证库」。**
这一条改变了本文的形态：**无数据搬迁章节**、回滚更简单（无旧数据要保），且
**没有可 `superseded` 的对象**（当年为何选 MySQL 无 ADR，故本文只能是**新决策**）。

> 停机前最后一次快照显示认证库只有 `users=1` / `roles=2`（`KnowTrace-Document/KnowTrace-十环补齐/10-服务器到期前收尾盘点.md`）。
> **该数字当前无法复核**（机器不存在），故**不作为决策依据**，只作量级参考。

## 2. 决策

**把 `go-user-system` 的存储从 MySQL 改为 PostgreSQL**，与主应用**同 DBMS、同版本线（18）**，
但**保持独立实例与独立库**（不合并为单库，见 §4 Options D）。

### 为什么做

1. **统一 DBMS**：一套迁移/备份/恢复/巡检工具链，而不是两套。判据是可测的——
   `monthly-ops` 演练要同时拉的镜像从 3 个（postgres/mysql/redis）降到 2 个。
2. **消掉 §1 表里那两处 SSOT 漂移**（版本 pin 冲突、排序规则不一致）——它们会被本次一并收口。
3. **主应用零改动**：两库只有 HTTP 耦合，这是 `ADR-0014` 已经付过的解耦成本，现在兑现收益。

### 目标 schema（逐列类型映射）

**这张表是换库最容易出错的地方**，逐条给出「MySQL → PG」与**必读语义差**：

| 表.列 | MySQL | PostgreSQL 目标 | ⚠️ 语义差（必须知道） |
| --- | --- | --- | --- |
| `*.id`（4 处） | `BIGINT AUTO_INCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` | **不用 `serial`**（`serial`=`integer`+隐式序列，`bigserial` 才是 bigint）。用 `BY DEFAULT` 而非 `ALWAYS`，因为 `00004`/`00005` 需要**显式插 `role_id`/`permission_id`** |
| `users.status` | `TINYINT NOT NULL DEFAULT 1` | **`smallint`** | **不要 `boolean`**：Go 侧是 `int8`，且**现有值是 `1/2` 不是 `0/1`**——`boolean` 会把 `2` 判为非法 |
| `*.created_at/updated_at/last_login_at/deleted_at/expires_at/revoked_at`（14 处） | `DATETIME(3)` | **`timestamptz(3)`** | **全表最危险的一行**。MySQL `DATETIME` **无时区**，靠 `db.go:47` 的 `loc=Local` 按进程本地时区解释；PG `timestamptz` 存**绝对时刻**。搬迁/重建时若源时区声明错，**时间平移而每一层类型检查都过**。`refresh_tokens.expires_at` 用它判过期 ⇒ **平移 = 会话提前/延后失效，是安全事件** |
| `*.username/code/name/jti/token_hash/...` | `VARCHAR(n)` / `CHAR(64)` | 同宽 `varchar(n)` / `char(64)` | **排序规则变了 ⇒ 唯一键语义变了**。现库是 `utf8mb4_0900_ai_ci`（**大小写不敏感**），PG 默认大小写**敏感**。⇒ `unique(username)`、`uk_roles_code` 等在 MySQL 下 `Alice`/`alice` **冲突**，迁到 PG **不再冲突**——**这是唯一约束的静默放宽**。缓解：`CREATE UNIQUE INDEX ... (lower(username))` 或列级 `COLLATE "und-x-icu"`（**PG 18 上的可用性待实测**） |
| `user_roles(user_id, role_id)` 等复合主键 | `PRIMARY KEY (a,b)` | 同 | 无差异 |
| 字符集 | `utf8mb4` | `UTF8` | PG 的 `UTF8` = 完整 Unicode，**等价于** MySQL 的 `utf8mb4`。**注意**：`CREATE DATABASE ... ENCODING 'utf8mb4'` 会报错 |
| `ENGINE = InnoDB` / `CHARSET` / `COLLATE` | 6/12/6 处 | **删除** | 库级设定 |
| `ON UPDATE CURRENT_TIMESTAMP` | **实测 0 处** | — | **无需映射**：时间戳由 GORM 的 `autoCreateTime`/`autoUpdateTime` 标签负责 |
| `INSERT IGNORE`（4 处） | | `INSERT ... ON CONFLICT DO NOTHING` | — |
| `ON DUPLICATE KEY UPDATE ... VALUES(x)`（2 处） | | `ON CONFLICT (…) DO UPDATE SET x = excluded.x` | `VALUES()` 自 MySQL 8.0.20 已 deprecated |
| `NOW(3)`（20 处） | | `now()` | PG 原生微秒精度 |
| `MODIFY COLUMN`（1 处） | | `ALTER COLUMN … TYPE …` / `SET NOT NULL` | — |
| `AFTER <col>`（4 处） | | **删除** | PG 无列序概念 |
| `DROP KEY`（1 处） | | `DROP INDEX` | — |

**保留的净收益**：MySQL 的 DDL 隐式提交使每个迁移文件都必须写 `-- +goose NO TRANSACTION`；
**PG 的 DDL 是事务性的**，去掉该行后可获得「**迁移失败自动回滚**」。

### 两个驱动路径都要改（易漏）

1. **GORM**：`pkg/database/db.go:11` `gorm.Open(mysql.Open(dsn), …)` → `gorm.io/driver/postgres`。
2. **⚠️ 迁移路径不经 GORM**：`pkg/database/migration.go:17,64-70,84` 用 `database/sql` +
   `mysqldriver.NewConfig()` + `FormatDSN()`，那是 `migrate up` / `bootstrap-admin-if-needed`
   两个子命令的**唯一** DB 入口。
   ⇒ **`github.com/go-sql-driver/mysql` 不能从 `go.mod` 删掉**，除非把这一整个文件也换掉。

## 3. 决策依据与代价

**依据**：主应用侧已有一套成熟的 PG 工具链（`scripts/migrate.mjs` 带 sha256 校验、
`backup-all.sh` 含逐表行数清单、`verify-restore.sh` 在临时容器逐表比对）。
复用它的收益是**可测的**，不是偏好。

**代价（如实列，不淡化）**：

1. **`git subtree` 的长期成本**：`services/go-user-system` 是 `git subtree` 引入的上游副本
   （`ADR-0014` §「更新上游源码」给的是 `git subtree pull`）。改成 PG 后，本地适配面积
   从「几处」扩大到约 40 个文件 ⇒ **每次 `subtree pull` 都会冲突，且没有到期日**。
   **本 ADR 不解决它**，只在 §5 记为待决。
2. **方言依赖是语法性的，`grep` 查不出来**：实测
   `git grep -l -i mysql -- services/go-user-system/migrations/` → **0 个文件**，
   而方言语法确实在里面（`AUTO_INCREMENT`×4 · `utf8mb4`×12 · `DATETIME(3)`×14 …）。
   ⇒ **任何"grep 过没有 mysql 了"的收尾声明在本仓不可信**，收尾判据必须是 §4 的负向用例。
3. **测试基建有 PG 里不存在的语句**：`internal/testutil/mysql.go:135,139`（`SET FOREIGN_KEY_CHECKS`）、
   `:200`（`SELECT DATABASE()`）、**`:213`（`SELECT GET_LOCK(?,30)`）**——最后一条最阴：
   MySQL 返回 `1/0`，`pg_advisory_lock` 返回 `void` ⇒ `:216` 的 `if lockResult != 1`
   **编译不过或永远为假**。
4. **验证面当前是空的**：CI 刻意不配 `TEST_DATABASE_DSN`，集成测试全部 `t.Skipf`
   （`ci.yml:120-121` + `testutil/mysql.go:91`）。**换库最需要的那类证据不在任何门里**（见 §5 先决）。

## 4. Options（含被否方案与理由）

| # | 方案 | 裁定 | 理由 |
| --- | --- | --- | --- |
| **A** | **`gorm.io/driver/postgres`** | ✅ **采纳** | 与现有 `gorm.Open(...)` 链一致，改动面最小；GORM 链实测**方言中立**（全服务只有 4 处 `clause.*`，无一处 `OnConflict`/`UpdateAll`/`Returning`） |
| **B** | `pgx` v5 直连 | ❌ 否 | 性能更好，但要绕过 GORM 重写 DAO 层；本服务的负载（`users=1`、`refresh_tokens` 少量）**用不上**。**若将来 DAO 层要重写，可另立 ADR** |
| **C** | 保留 MySQL，只统一版本 pin | ❌ 否 | 只解决 §1 的一半问题（版本冲突），**不解决两套工具链**；且与主应用仍是两套方言 |
| **D** | 合并为**单一 PG 实例**（同实例不同库/不同 schema） | ❌ **本次不采纳** | 收益是把「灵活性」从**一次性可行**变成**结构性解耦**；代价 +3~8 人·天，且要重建 `ADR-0014` 的隔离论证（"独立数据卷"是它刻意选的）。**本次先不扩大范围**——若日后要做，另立 ADR 并处理与 `0014` 的取代关系 |
| **E** | 移植存量数据（`mysqldump` → 转换 → `psql`） | ❌ **不可行** | 数据源已随停机丢失（§1.1）。**不是"次优"，是做不到** |
| **F** | 双写 / 影子写 | ❌ 否 | 认证写路径是 JWT refresh token 的**单次使用 + 家族吊销**，跨两库双写**无法保证 token 不被重复消费**。拿**认证正确性**换**不存在的可用性收益** |

## 5. 后果

> ⚠️ **本节是 `sre-operator` 成对互审后重写的版本**（互审裁定 `需修改后再定`）。
> 初稿本节有 **8 条 P0 缺口**，其中一条是**内部矛盾**（R1 与 §5.3 的收口判据互斥），
> 另一条是**全篇无变更窗口**。逐条修正在下，每条注明改动理由。

### 5.1 变更窗口（**初稿全篇缺失，互审 P0-1**）

**这是本 ADR 最严重的遗漏**：§6 自认 C 档、要求「变更窗口」，但初稿**全文无窗口评估**。

**窗口 = 全站窗口，不是「认证不可用」。** 实测依赖链：

| 服务 | 依赖 | 出处 |
| --- | --- | --- |
| `app` | `auth: condition: service_healthy` | `compose.yaml:158-162` |
| `auth` | `auth-bootstrap: service_completed_successfully` → `auth-migrate` → `auth-mysql` | `compose.yaml:108-112,86-88,72-74` |

⇒ **`auth` 起不来 ⇒ `app` 也不启动 ⇒ 全站不可用。**

**同链路已有先例数字**：`deploy/systemd/knowtrace-workflow-offsite-backup.service:7-8` 记载
`docker compose stop app auth` 造成 **app 约 24 秒 / auth 约 13 秒**计划外停机。
**⚠️ 该数字是「同链路先例」，不是本次窗口的实测值**——本次窗口须在有 Docker 的环境空跑实测
（只改镜像名与 `DB_HOST`，`time docker compose up -d --wait`，记录 `app` ready 墙钟）。
**未实测前，本 ADR 不给窗口数字**（D1：不得把推测写成计划值）。

**窗口要素（与变更单一起定；此处只定「必须有什么」）**：

| 要素 | 要求 |
| --- | --- |
| 时段 | 对齐既有低峰排班 —— `deploy/systemd/knowtrace-workflow-backup.timer` 的 `OnCalendar=*-*-* 03:20:00 Asia/Shanghai` |
| **中止条件** | `/readyz` 非 200，**或** `KnowTraceAuthNotReady` 告警 firing ⇒ **立即中止并回退**，不得「先上再修」 |
| 授权人 | **人工**（C 档不可由 AI 自批） |
| 回退时限 | 必须在窗口内可完成 —— 见 §5.5 |

### 5.2 先决条件（初稿只列 1 条，互审 P0-7）

**两条并列，缺一不得开工**：

**① 测试基建**：`ISSUE-S3-015` —— 先把 Go 集成测的 CI 门补上（`ci.yml:118-121` 自述不配
`TEST_DATABASE_DSN`；`testutil/mysql.go:91` `t.Skipf`）。不补，§5.6 的每条负向判据**都没有载体**。
判据：`go` job 里集成测试**真的执行**（CI 日志非 skip 用例数 > 0）。

**② 备份链**：**先在新库上产出并验收一份可恢复归档**，然后才允许改 `compose.yaml`。
反序的代价是本 ADR 初稿自己写的「回滚能力在迁移那一刻消失」。
现状：`scripts/linux/backup-all.sh:170-176` 备份期间 `stop --timeout 30 app auth` 再恢复运行时
（`QUIESCE_WRITES=1`，见 `deploy/systemd/knowtrace-workflow-backup.service:14`）——
**这条链本身要在 PG 上重建并重测**。
**验收判据必须含一次真实登录**（见 §5.7）。

### 5.3 三处 SSOT 漂移必须同步收口（初稿第 1 行与 §5.5 互斥，**已修正**）

| # | 漂移 | 收口判据 |
| --- | --- | --- |
| 1 | MySQL 版本 pin 4 处冲突（8.0 / 8.4） | 见下 ⚠️ |
| 2 | 排序规则不一致（`_0900_ai_ci` vs `_unicode_ci`） | 统一到 PG 的显式 `COLLATE`，并在文档写明 |
| 3 | `.env.goose.example` 的 `GOOSE_DRIVER=mysql` 与写死 `127.0.0.1:3306` | 随驱动一并改 |

> ⚠️ **修正一处内部矛盾（互审 P0-2）**：初稿把第 1 行的判据写成
> 「`grep -rn "mysql:8\."` **应为空**」，而初稿 §5.5 的 R1 又要求「**MySQL compose 定义不得先删**」。
> **两者互斥** —— 前者要求删掉 `auth-mysql`，后者要求留着它。
> **⇒ 正式判据改为**：`grep -rn "mysql:8\."` **只允许命中「回滚基线」一处**，
> 且该处必须在一个**显式标注为回滚用途**的 compose 文件（或 profile）里。
> **回滚优先于「清零」**：观察期结束、回滚窗口关闭后，才允许彻底清零。

### 5.4 运维链必须同步改（初稿漏 `external` 卷等，互审 P0-2 / P0-4 / P1 系列）

**初稿只列了备份/恢复脚本，漏了卷与一批巡检/监控点位。补全如下。**

**（a）`external` 卷 —— 初稿完全未提**

```text
compose.yaml:173-175   auth_mysql_data: { name: go-user-system_mysql_data, external: true }
scripts/linux/prepare-host.sh:75   volumes=(go-user-system_mysql_data go-user-system_redis_data)
scripts/install.sh:225             for v in go-user-system_mysql_data ...
scripts/start-all.ps1:26           同两个卷名写死
```

**两个失败方向都不报错**：新机器上 `prepare-host.sh:84-89` 仍会创建 `go-user-system_mysql_data`
⇒ 留一个**永不挂载的孤儿卷**；而真正在用的 PG 卷若没进 `:75` 的数组 ⇒ `compose up` 直接
`external volume ... not found`（`prepare-host.sh:12` 已记载过同形事故）。
**转 PG 必须同时改这四处，并复测三脚本的幂等性**（其幂等判据是 `docker volume inspect`，
`prepare-host.sh:78` —— 卷名一改，判定分支就换）。

**（b）备份/恢复链（初稿已列，但深度不够）**

`scripts/backup-auth.ps1`、`scripts/linux/backup-all.sh` 的 `mysql_counts()`、`verify-restore.sh`、
`services/go-user-system/scripts/ops/*`、`monthly-ops.sh`。**必须同一变更改完。**

两处**必须保留、但校验器必须换**的机制：

| 机制 | 位置 | ⚠️ 转 PG 后的变化 |
| --- | --- | --- |
| 归档强制必需组件 | `verify-restore.sh:74-86` `required_file` 含 `mysql.sql` / `mysql-counts.tsv`，`[[ -s ]] \|\| die` | 改名要**同改备份端生产者**（`backup-all.sh:188-192`）与 `:95-97` 的镜像预检，否则演练**永远不能通过** |
| 四步校验 | `backup-auth.ps1:43-54` 执行 → 容器内 sha256 → `cp` → 主机 sha256 比对 | **`-Fc` 是二进制**：`grep` 不可用、`-s` 只挡 0 字节 ⇒ **必须补 `pg_restore --list` 级别的可解析性校验**，且**在容器内算 sha 的同时算**。否则**被截断但非空的 dump 四步全绿**（`AGENTS.md` §8.1 ① 的 PG 版） |

> 初稿说「`verify-restore.sh:201` 的 `cmp` 与四步校验**必须保留**」——
> **这句是对的，也是初稿最有价值的一句**；但它没说清「保留」不等于「可用」：
> 二进制格式下**校验器必须换**。

**（c）巡检 / 监控 / 文档点位（初稿遗漏）**

### 5.5 回滚策略（初稿三档，**互审修正**）

初稿说「数据源已丢 ⇒ 回滚更简单」。**部分成立，但漏了真正决定代价的变量：新产生的数据 + 观察期。**

**数据不会少**：`internal/dao/user.go:52` `auth_version = auth_version + 1` —— **每次登出/改密都是一次写**；
`refresh_tokens` 随每次刷新签发增长（`migrations/00003`）。

⚠️ **且本仓没有可依的 RTO/RPO**：`verify-restore.sh:242-248` 的输出**只有计数、无计时**；
全仓运维脚本 `git grep "RTO|RPO"` → **0 命中**。⇒ **ADR 不得给出观察期数字**，除非先做计时实测。

| 档 | 动作 | 前置 | 代价（**新增列**） |
| --- | --- | --- | --- |
| **R1** 应用回滚 | `git revert` → 用 MySQL 镜像重建空库 → `auth-bootstrap` 重放管理员 | **§5.3 修正后**：回滚基线 compose 必须在观察期内保留 | **观察期内新产生的会话与会话吊销全部丢失**（`refresh_tokens` / `auth_version`）。用户表现为「新会话失效」，**且无日志提示** |
| **R2** 库回滚 | 同 R1；若观察期内已产生数据，按新建库的备份还原 | 备份链已改好（§5.2 ②） | 需一次恢复演练；**未经演练的恢复 = 没有恢复** |
| **R3** 冷备 | 迁移前对空/新库做基线备份 | — | — |

**观察期（新增，初版缺失）**：时长**待实测**；测量方法 = 用本仓既有形态
`tests/isolated-v2-recovery.test.ts:311,435,460-462,651`（empty-instance restore / trust downgrade /
same-actor idempotency）**对齐** `verify-restore.sh`，并在其上**加计时**。
（该测试当前**不在服务器上跑，也不在备份链上** —— 本 ADR 把它列为对齐目标。）

> **判据：回滚方案没演练过 = 没有回滚方案。**

### 5.6 验证判据（初稿 5 条有 4 条可假绿，**互审 P0-6 逐条修正**）

| # | 修正后 | **注入什么会暴露它（初稿的漏洞已补）** |
| --- | --- | --- |
| 1 | `/readyz` 200 且**真实登录一次**成功 | 初稿「把 `DB_HOST` 指向不存在的服务」**在 compose 下不可执行**（`depends_on` 会先拦，容器根本不创建 —— **「起不来」与「fail closed」观测同形**）。**改为**：`DB_HOST` 指向**可解析但不可达**的地址（如 `127.0.0.1:1`）或**运行中停 PG**，断言 `/readyz` → 503 且 `go_user_system_readiness == 0`（`internal/handler/health_handler.go:82-84,91-94,103-106`）。**另注**：`migrate up` 走 `pkg/database/migration.go`，**不经 GORM**，是另一条代码路径，需单独测 |
| 2 | 权限：**指明**测 `admin` 的**哪一个**权限码 + **哪一个**接口 + 期望响应码 | 初稿「删掉一条 `role_permissions`」**可假绿**：删一条不服务于 admin 的映射，admin 路由仍全通 ⇒ 判为 PASS |
| 3 | **迁移文件本身**成为被测对象：空库跑 `migrate up` 必须成功 | 初稿「在 `testutil` 写一条 MySQL 语法」在重写 `testutil` 后**已无载体**；且它抓不到 `migrations/` 里的方言残留 |
| 4 | **显式选定目标语义**：`CREATE UNIQUE INDEX ... (lower(username))` ⇒ **`Alice` 与 `alice` 必须冲突** | 初稿「MySQL 下必须被拒绝」**不可执行**（MySQL 已不存在）；且它把「PG 下允许」读作「复现同一行为」，而 ADR 自己又说那是「静默放宽」—— **判据方向与决策目标互相矛盾** |

### 5.7 业务级恢复验收（初稿缺失，互审 P0-8）

`AGENTS.md` §2 的 08 环准出要求「**实测 RTO/RPO + 业务级可用性核验**」，其 §3 明确
**「不得只给数据层校验（checksum / 行数）」**。本仓现状：

- `verify-restore.sh:242-248` 输出**只有计数**：`RESTORE_VERIFY=PASS / POSTGRES_TABLES / MYSQL_TABLES / REDIS_KEYS_* / UPLOAD_FILES`。
- `docs/日常运维/部署清单与验收.md:51` 的验收定义**也是纯数据层**。

**注入什么会暴露它**：一份**密码哈希列全为 NULL** 的 dump，`COUNT(*)` 相等、`SHA256SUMS` 自洽
⇒ `cmp` 与 `-s` **全过**；人拿着「演练 PASS」以为能恢复，**真恢复后没人能登录**。

**⇒ 本次必须补一条**：恢复后**用真实账号登录一次**。判据见 `scripts/linux/verify-business-acceptance.sh`
（**该脚本存在，但本 ADR 未核实其覆盖面** —— 列为 §5.8 待核）。
