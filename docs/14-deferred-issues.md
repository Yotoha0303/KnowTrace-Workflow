# 暂缓问题与后续迭代清单

本文件记录已经明确提出、但当前迭代暂不处理的问题。这里的“当前现象”来自使用者报告，不等于已经通过日志、测试或代码复现；进入开发迭代后必须先复现，再实现和验收。

## KT-DEFER-001 无实际修改仍重复保存 Revision

状态：已完成。服务端在乐观锁校验后比较规范化持久化字段；无变化时不更新 Capture、不增加版本、不创建 Revision，分类关系单独判断。

当前现象：同一版本的记录即使标题、正文、内容类型、描述对象、发生时间等有效内容没有变化，重复点击保存仍可能增加版本号或历史记录。

期望行为：保存前比较规范化后的持久化字段；没有实际变化时不更新 Capture、不增加版本号、不创建 Revision，并向用户提示“没有需要保存的修改”。分类等独立关系的变化应按各自规则处理，不能错误生成正文 Revision。

后续验收：

- 连续多次提交完全相同的数据，Capture 版本和 Revision 数量保持不变。
- 仅存在空白、日期格式等可规范化差异时，不产生虚假版本。
- 任一受版本管理字段真正变化时，只增加一个版本并保存一个正确的历史快照。
- 乐观锁和并发冲突检查继续有效，不能用“无变化”判断绕过并发保护。

## KT-DEFER-002 AI 整理前反复要求测试连接

状态：已完成。选择 CC-Switch 后自动检测代理、供应商和可用路由；检测到可用路由即可直接运行，模型测试保留为可选排障入口。

当前现象：已经成功使用过的 CC-Switch 连接，在后续 AI 整理或分析前仍反复要求用户手动点击“测试当前供应商”，无法直接运行。

期望行为：选择 CC-Switch 后自动完成必要的代理、供应商和模型能力检查；成功状态在合理范围内复用，使用户进入已配置环境后可以直接运行 AI。不能把每次 AI 操作都变成一次重复的手工连接测试。

后续验收：

- 同一浏览器会话、同一 CC-Switch 地址、供应商和模型配置在测试成功后，后续整理与分析可以直接运行。
- 页面刷新或在记录之间切换不会无条件清除仍然有效的成功状态。
- CC-Switch 供应商、模型、地址或凭据发生变化，或者实际调用返回连接/鉴权/模型错误时，旧状态必须失效并自动重新检测。
- 检测过程展示明确状态和失败原因，不使用无限加载动画，也不要求用户反复手动测试。
- 缓存的“可用”状态不能掩盖 CC-Switch 已停止或已切换供应商的事实。

## KT-DEFER-003 管理员创建内容对成员可见

状态：已完成。管理员新建和导入的 Capture 默认 `shared`，普通成员新建和导入默认 `private`；共享内容对普通成员只读。管理员首次访问时会把本人历史私有记录迁移为共享，迁移脚本同时覆盖本地管理员和默认首个管理员标识。

当前现象：管理员可以读取所有成员的内容，但管理员自己创建的记录仍按创建者私有范围处理，其他管理员和普通成员无法看到。

期望行为：管理员账户创建的内容可以作为小群体共享内容，被其他已登录管理员和普通成员查看；普通成员自行创建的内容仍只对本人和管理员可见，不得因此变成成员之间互相可见。

后续验收：

- 管理员 A 创建的共享记录，管理员 B 和普通成员均可读取，并能在允许的列表、检索、分类和对象时间线中找到。
- 普通成员 A 创建的私有记录对普通成员 B 仍不可见。
- 管理员仍能按管理权限查看所有成员内容。
- 详情、搜索、分类、图片、导入导出和派生知识使用同一可见性规则，不能只修复首页列表。
- 下一迭代必须明确管理员内容是默认共享还是由管理员显式选择，并决定现有管理员记录是否需要迁移；在决定前不批量改变历史数据权限。

## KT-DEFER-004 同一用户可重复导入相同记录

状态：已完成防重，仍不自动删除既有重复数据。导入使用“创建者 + v1 记录指纹”并保留稳定记录标识检查；数据库部分唯一索引防止并发重复写入。

当前现象：同一用户可以重复导入相同文件或相同记录，系统会再次创建 Capture，导致重复记录持续增加。

期望行为：导入以“用户身份 + 来源记录身份”为隔离边界进行幂等判断。同一用户重复导入同一来源记录时跳过重复项；不同用户导入相同内容仍分别属于各自数据，不能跨用户错误去重。

后续验收：

- 优先使用导出文件中的稳定记录 ID、版本或导入来源 ID 识别同一记录。
- 缺少稳定 ID 时，使用经过明确定义和版本化的记录指纹；指纹字段必须包含创建者范围，并避免把内容相同但事件时间或描述对象不同的合法记录误判为重复。
- 同一文件内的重复行和跨多次导入的重复记录都能识别。
- 导入预览和结果明确显示新增、跳过重复、冲突和失败数量，并允许查看原因。
- 防重检查和写入必须在数据库层保持并发安全，不能只依赖前端筛选。
- 对已经存在的重复记录，后续提供只读扫描和合并/删除预览；任何清理必须再次确认，不在本次记录工作中执行。

## KT-DEFER-005 Excel 携带完整主张与证据链

状态：已完成。现有数据迁移页同时保留 `.xlsx v1` 与 `.zip v2`：v2 已实现知识链 contracts 与 Excel 生成/解析、稳定引用和公式校验，以及 `manifest.json + knowtrace.xlsx + attachments/` ZIP 二进制包。ZIP 导入会校验原始/规范化路径、额外文件、工作簿与附件大小、SHA-256、图片 MIME 和单 Evidence 图片数量；导出会从真实附件存储读取字节并再次校验。Capture/Category 已复用 v1 预检与事务逻辑；Claim/Evidence/Attachment 使用 actor + format version + object type + source key 的 provenance 身份，支持 `create / skip / repair / conflict`。预检通过的 ZIP 会服务端暂存，确认时重新检查文件哈希、完整包和数据库预检快照，再以单事务写入并对附件文件执行失败补偿。可信状态、来源版本和 Evidence 版本按非受信任包策略降级，历史检查与人工结论仅保留为迁移审计上下文。生产 Docker 构建通过，`0018` 与 `0019` migration 已应用。隔离恢复验收使用两套独立 App/PostgreSQL 实例完成真实 HTTP 导出、预检和确认，验证空白实例恢复、图片在线读取与 SHA-256 一致、同 actor 第二次导入全量幂等；同一真实目标 PostgreSQL 上还验证第二 actor 使用独立 provenance 重新创建，不跨 actor 错误去重。

当前现象：用户导出 Excel 后只能得到记录原文、对象、时间、状态和分类。记录下已经形成的主张、证伪条件、证据摘录、来源信息、审核状态和图片无法随该文件迁移，导入后不能还原知识调查上下文。

期望行为：新增版本化的 Excel `v2` 知识链交换格式。导出文件至少包含主张、证据、来源核验、附件核验、人工结论及各对象之间的稳定关联；证据图片通过同一导出包中的附件目录与 SHA-256 清单关联，不依赖当前机器的绝对路径。普通 Excel 交换仍不能替代 PostgreSQL、认证数据库和上传目录的完整备份。

下一次迭代范围：

- 增加“主张”“证据”“来源检查”“附件检查”“人工结论”“结论证据关联”和“图片清单”等工作表；使用稳定 ID 关联 Capture、Claim、Evidence、Review 和图片。
- 主张至少导出来源记录与版本、陈述、证伪条件、状态和版本信息；证据至少导出来源标题、可选 URL、摘录、支持/反驳/背景立场、审核状态和版本。
- 图片二进制文件不写入单元格，改为生成包含 Excel、附件和 manifest 的 ZIP；manifest 保存相对路径、大小、MIME、SHA-256 和 Evidence ID，禁止绝对路径与目录穿越。
- 导入先解析并展示预检，不直接写库；校验引用完整性、格式版本、权限范围、状态依赖、图片哈希、文件大小和 MIME 后，再由用户确认并以事务写入。
- 同一用户重复导入同一知识对象时跳过；稳定 ID 相同但内容、版本或哈希冲突时阻止导入并指出具体工作表、行和字段。
- 为避免伪造审核结果，普通交换包不能仅凭可编辑单元格恢复“已采纳、已审核或已发布”的可信状态；产品决策已确定为**导入后安全降级为待核验**。`v2` 可以携带原状态用于迁移上下文和人工检查，但数据库写入阶段必须重新建立来源检查、证据采纳和人工结论，后续如需无损可信迁移再单独设计带完整性签名的受信任包。
- 继续支持读取现有 `v1` Excel；格式升级不能使旧文件无法导入。

下一次迭代验收：

- 创建包含至少 1 个 Claim、支持与反驳 Evidence、无链接图片证据、来源检查和人工结论的记录，导出包中能逐项找到对应数据和稳定关联。
- 将导出包导入隔离的空白实例后，记录、分类、主张和证据数量及正文一致，图片可在线查看，所有附件 SHA-256 与导出前一致。
- 删除附件、修改附件字节、破坏引用或伪造状态时，预检明确失败且数据库不产生部分数据。
- 对同一用户连续导入同一 `v2` 包两次，第二次全部识别为重复；换用不同用户时不跨用户错误去重或泄露私有内容。
- 自动化测试同时覆盖 `v1` 向后兼容、`v2` 往返、冲突、权限隔离、恶意公式、ZIP 路径穿越和超限文件。

## KT-DEFER-006 会话续期未覆盖页面重获焦点与多标签串行

状态：**未开始**。来源 `INC-009` 改进项第 3 条的后半段。

当前现象：会话续期已由 Proxy 在 Access Token 失效时**按需触发**并上线。但`INC-009` 要求的两点仍未实现：页面重新获得焦点时主动续期；多标签页刷新串行化以避免 Refresh Token 重放。实测 `grep -rn "visibilitychange\|focusin\|BroadcastChannel\|navigator.locks" src/` 无命中。

期望行为：用户切回长时间搁置的标签页时，会话在提交动作之前已续期，不出现「点了保存才被踢」；多个标签页同时需要续期时只发生一次 Refresh 调用，其余复用结果，不产生 Refresh Token 重放。

后续验收：

- 两个标签页同时打开且 Access Token 已失效，任一页面触发续期后另一页面直接获得有效会话，服务端只收到一次 Refresh 请求。
- 页面从后台切回前台时，若 Access Token 临近或已过期，续期在用户操作前完成。
- Refresh Token 已失效时，多标签行为一致：都提示重新登录，不出现一个标签成功、另一个进入错误页。

## KT-DEFER-007 部署文档未写明 `.env` 管理员密码的语义边界

状态：**未开始**。来源 `INC-009` 改进项第 6 条。

当前现象：`INC-009` 的触发条件之一是「管理员改了密码，但有人拿 `.env` 里的初始密码当恢复来源」。运维手册与部署清单**都没有**说明：`.env` 的 `KNOWTRACE_ADMIN_PASSWORD` 只在首次创建管理员时使用；管理员已存在时初始化任务跳过；改密后 `.env` 不会同步，也不构成可用的恢复来源。实测两份文档均无相关说明。`.env.example` 只写了「不要写死默认口令」（另一件事，2026-10-02 的修复）。

期望行为：运维文档明确写出这条语义，使排障者不会把 `.env` 里的过期口令当成当前密码。

后续验收：

- 在 `docs/日常运维/运维手册.md` 与 `部署清单与验收.md` 里各有一处明确说明（或一处权威、另一处指向它）。
- 说明里包含三条：仅首次初始化生效 / 改密后不同步 / 不是恢复来源。
- 说明与 `scripts/linux/init-env.sh` 的实际行为一致（以脚本为准核对一次）。

## KT-DEFER-010 桌面端 T2 的三个未定子问题（不能开工的前提）

状态：**未开始**。来源 ADR-0018（2026-10-05 由 `proposed` 转 `accepted`，采纳 T2）。

背景：桌面端形态已定为 **T2（进程内 Node sidecar，可离线）** —— 理由是
`docs/00-product-brief.md` 把「随手记录」列为主路径，而 `docs/18` §M2 已把移动端的
「本地写入队列，先落本地再同步」列为必做项；桌面端若不能离线记录，两端行为会不一致。
被否的 T1（静态导出）会关掉 Server Actions 与动态路由。

**但形态定了不等于能开工。** 下面三个子问题任一未定，都不应动工 ——
否则会写出一套无法收尾的东西：

1. **Node 运行时的打包与体积预算**。T2 要随壳打包一个 Node 运行时（约 +60–100 MB）。
   需先定：用哪个运行时（node 官方 / bun / deno）、装到哪、如何与应用版本对齐、
   体积上限是多少（这会直接影响「用户愿不愿意装」）。
2. **sidecar 的进程生命周期与端口分配**。崩溃怎么重启、端口冲突怎么办、
   应用退出时怎么保证不留孤儿进程、升级时怎么换二进制而不丢本地队列。
3. **离线队列与 `Idempotency-Key` 的对接**。服务端机制已现成（幂等创建 + 乐观锁 +
   冲突返回 `409` 附 `currentVersion`），但**客户端策略要定**：队列持久化在哪、
   重试风暴下幂等键怎么生成、冲突在 UI 上怎么呈现（§M2 已定首期只做「提示并显示两版」）。

后续验收（每个子问题各一条，**必须可执行**）：

- ① 一份体积实测数字（打出来的安装包大小）+ 运行时选择理由；
- ② 一份「杀掉 sidecar 进程后自动恢复、且本地队列不丢」的实测记录；
- ③ 一份「断网写入 N 条 → 联网后按序同步、重复提交被幂等吸收」的端到端用例
  （进 CI 的 e2e job，走 `/api/v1`，不新增只有桌面端能验的接口 —— 见 `docs/18` §6）。

**边界**：本条**不与移动端首期（M2/M3/M4）并行**。T2 的工作量比 M3 + M4 加起来还大。
