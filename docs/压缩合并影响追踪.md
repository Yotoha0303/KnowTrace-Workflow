## 1. 现象

**GitHub 的压缩合并（squash merge）会重写提交身份** ⇒ 在已合并的 PR 上继续推送的提交，
**不再属于新 `main` 的历史**，而 GitHub **不会**把它们并入。

**机制**：压缩把 N 个提交压成 1 个**新提交** ⇒ 原分支与新 `main` **立即分叉**。

---

## 2. 纪律（本仓的应对 · 方案 B）

> **PR 开着时，不再向其推送提交。要追加内容，新开一个 PR。**

**为什么选 B 而非 A（改仓设置）**：
- 零配置、立刻生效、**不依赖平台权限**
- 它防的是**根因**（提交时机），而不是症状
- 代价：**靠自觉** —— 而 `2026-10-16` 那次踩坑，恰恰是**没自觉**（我没确认 PR 是否已被合并就继续提交）

**⇒ 纪律的执行判据**：推送前先跑
```bash
gh pr view <N> --json state,mergedAt          # state 必须仍是 OPEN
```
`MERGED` ⇒ **停**，改开新 PR。
