## 1. 连接服务器

```powershell
ssh knowtrace-vps
```

**别名现在可用了。** 2026-10-03 修掉了 `C:\Users\Yotoha\.ssh\config` 开头的 UTF-8 BOM ——
在此之前 `ssh knowtrace-vps` 会直接报 `Bad configuration option: \357\273\277host`。
备份留在 `config.bak-bom-20261003`。

别名解析为：`root@45.64.74.99:22345`，密钥 `~/.ssh/knowtrace_vps_ed25519`。

不想用别名时（等价写法）：

```powershell
ssh -i C:/Users/Yotoha/.ssh/knowtrace_vps_ed25519 -p 22345 root@45.64.74.99
```

> ⚠️ **不要加 `-F /dev/null`** —— 那是"绕过 ~/.ssh/config"，会让别名解析失败
> （`Could not resolve hostname knowtrace-vps`）。只有在需要**避免**读取用户 config 时才用它。

**认证方式（实测 `sshd -T`）**：

| 项 | 值 |
| --- | --- |
| 端口 | `22345` |
| `passwordauthentication` | `no`（**已关闭密码登录**） |
| `permitrootlogin` | `without-password`（等同 `prohibit-password`） |
| `maxauthtries` | `3` |
| 加固文件 | `/etc/ssh/sshd_config.d/00-knowtrace-hardening.conf` |

**兜底**：若公钥失效被锁在外面，密码在 `D:\MyDocuments\KnowTrace-Workflow\.env.local` 的
`KTSERVER_PASSWORD`。走 `SSH_ASKPASS` 而非命令行参数（不进历史）：

```powershell
$env:KT_PW = (Get-Content D:\MyDocuments\KnowTrace-Workflow\.env.local | Select-String '^KTSERVER_PASSWORD=').Line.Split('=',2)[1].Trim()
$ap = "$env:TEMP\kt-askpass.cmd"; Set-Content $ap "@echo off`r`necho %KT_PW%" -Encoding ASCII
$env:SSH_ASKPASS = $ap; $env:SSH_ASKPASS_REQUIRE = "force"
ssh -o BatchMode=no -o NumberOfPasswordPrompts=1 -o StrictHostKeyChecking=no `
    -o UserKnownHostsFile="$env:TEMP\kt_kh" -p 22345 root@45.64.74.99 "whoami"
Remove-Item $ap
```

### 在服务器上跑多行脚本

经 `ssh` 传多行脚本时，**用 base64 参数**，不要用管道：

```powershell
$s = @'
echo hello
hostname
'@
$b = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes(($s -replace "`r","")))
ssh knowtrace-vps "echo $b | base64 -d | bash -s"
```

> **为什么**：PowerShell 管道会在首行前面塞 UTF-8 BOM，远端报
> `bash: line 1: ﻿cd: command not found`（BOM 粘在第一条命令前）。
> 注意 base64 **参数**有长度上限（约 12 KB 会被截断），传大文件用 `scp`。

```
        → knowtrace_ops_report_worst_level → 告警 KnowTraceOpsCheckFailed → 邮件
```


> `worst_level`：`0`=OK `1`=INFO `2`=WARN `3`=FAIL `-1`=未知。

## 4. 看日志

日志栈是 **PLG**：Alloy 采集 → Loki 存储（7 天）→ Grafana 查询。**常驻，不需要启动。**

### 4.1 在 Grafana 里查（日常用这个）

开隧道：

```powershell
ssh -N -L 3001:127.0.0.1:3001 -L 9090:127.0.0.1:9090 -L 9093:127.0.0.1:9093 knowtrace-vps
```

然后访问 `http://127.0.0.1:3001`，Explore 里选 **Loki**：

```logql
{container=~".+"}                           全部容器
{container="knowtrace-workflow-app-1"}               某个容器
{job="caddy"}                               Caddy 访问日志
{job="nginx"}                               Nginx
{container="knowtrace-workflow-app-1"} |= "EACCES"   内容过滤
```

Grafana 口令在服务器的 `.env.observability`（`GRAFANA_ADMIN_PASSWORD`），别贴进聊天。

### 4.2 不开界面，用命令行

```bash
# 四路各有几条流 —— 哪一路是 0，就是哪一路断了
for j in caddy nginx external; do
  printf '%-9s ' "$j"
  curl -sG 'http://127.0.0.1:3100/loki/api/v1/series' \
    --data-urlencode "match[]={job=\"$j\"}" | grep -o '"job"' | wc -l
done

# 容器日志最近一小时
curl -sG 'http://127.0.0.1:3100/loki/api/v1/query_range' \
  --data-urlencode 'query={container=~".+"}' \
  --data-urlencode "start=$(date -d '1 hour ago' +%s)000000000"
```

### 4.3 日志不全 / 是空的

先分清**哪一路**断，再对症：

| 症状 | 大概率原因 |
| --- | --- |
| 容器日志 + 宿主机日志**都**空 | Alloy 没起来，或它到 Loki（`http://loki:3100`）不通 |
| **只有** Caddy/Nginx 空 | 文件未生成，或 `local.file_match` 的发现没生效 |
| 刚重启 Alloy 后暂时空 | 正常，它每 10s 重新做一次文件发现 |

```bash
docker logs --tail 50 knowtrace-workflow-alloy-1
docker logs --tail 50 knowtrace-workflow-loki-1
```

> ⚠️ **别被 Alloy 启动瞬间的报错骗了。** `could not perform the initial load successfully`
> 在启动时出现是**正常的**（试图装载尚未生成的文件），实测 `RestartCount=0` 且日志照常入库。
> 判断采集是否正常，要看上面那个"有没有流"，不是看启动日志。

> ⚠️ **改 Alloy 配置后，`alloy fmt` 只查语法、不查组件属性名** ——
> 实测 fmt 通过但启动报 `unrecognized attribute`。真正的校验是启动后读 `docker logs`。

深度参考：[`../16-stage3-observability.md`](../16-stage3-observability.md) 的「日志栈（PLG）与查询」。

### 5.2 ⚠️ 部署前必读：2026-09-30 事故的教训

**部署积压代码前，必须重新取 HEAD 再算 diff。**

那天用**过期的 HEAD** 算积压范围，得出「src/ 改动为 0」的假安全结论，
一次放出 41 个积压提交（含一个从未生效过的全站缺陷），造成**约 70 分钟全站 500**。

```bash
# 正确做法：先重新取，再算
git fetch origin main
git log --oneline HEAD..origin/main          # 到底积压了什么
git diff --name-only HEAD origin/main | grep -E '^(src/|package.json|pnpm-lock.yaml|Dockerfile|services/|drizzle/)' \
  && echo "触及镜像 -> 必须 --build-app" || echo "不触及镜像"
```

完整复盘：**仓库外**的 `KnowTrace-ops/docs/2026-09-30-全站500事故复盘.md`（独立仓库，见文末「仓库外文档」）

### 6.3 **必须做恢复验证**

> **未经恢复验证的备份不能算备份。**

验证分**两层**，两层都要做 —— 数据层过了不等于业务能用。

#### 第一层：数据层（隔离恢复 + 校验和/行数）

```bash
scripts/linux/verify-restore.sh /var/backups/knowtrace/<归档名>
```

它在 `network none` 的临时容器里恢复，**不碰生产**。

#### 第二层：业务级可用性（登录 / 读记录 / 下载附件）

```bash
# 凭据从环境变量读，**不要写进任何入库文件**
BUSINESS_USER=<用户名> BUSINESS_PASSWORD=<口令> \
  bash scripts/linux/verify-business-acceptance.sh
# 可选：BASE_URL=http://127.0.0.1:3000（默认走 nginx :8080）
```

三步判据**都可证伪**：① 登录 `POST /api/v1/auth/login` → 200 且 `ok:true`，
并验证会话在下一跳仍有效；② 读记录 `GET /api/v1/captures` → **至少 1 条**
（空库不算通过）；③ 下载真实附件 `GET /api/evidence-images/<id>` →
**字节数一致 + `sha256` 与库里记录一致**（只有哈希能抓出「字节数对但内容不对」）。

**退出码刻意分两档，别混淆**：

| 退出码 | 含义 |
| --- | --- |
| 0 | PASS |
| 1 | **FAIL** —— 真的坏了（登录被拒、会话失效、附件内容不符） |
| 2 | **前置不满足** —— 缺凭据 / AUTH 未启用 / 库里还没有业务数据 |
| 3 | 脚本自身错误 |

> **为什么要区分 1 与 2**：这台机器**生产库目前没有真实业务数据**（`captures=0`），
> 于是判据 ②③ 必然走 exit 2。若把它当 FAIL，一个**环境状态**就会长期伪装成
> 红色缺口，看久了就没人当真了。

### 7.6 真实停机演练（告警送达）—— 2026-10-04 修正

十环 `06 观测` 的准出要求「完成**真实停机告警送达演练**」。此前两次都不完整，
**原因在脚本，不在配置**：

- 2026-09-08（`INC-S3-001`）：只验到 Alertmanager 收到；记录说「未使用邮件通知，因为 SMTP 未配置」

- 2026-10-04 第一次重跑：`RESULT=PASS`，但投递计数**纹丝不动**，**一封都没发**。

**根因是竞态**：AM 的 `group_wait` 是 **30s**，而演练脚本 3 秒一轮、
一确认 AM 收到就**立刻**恢复故障 —— 告警只存活 30 秒，**比 `group_wait` 还短**，
AM 在首次投递前就把整组丢掉。

```text
15:57:40  KnowTraceMetricsTargetDown 进 firing（AM 开始 group_wait 30s）
15:58:05  脚本恢复 blackbox → 告警 resolve
15:58:10  首次投递本应发生 —— 但组已不存在
```

**正确跑法**：用编排器，它把保持时长设为 `> group_wait`，并断言**投递计数至少 +1**：

```bash
# 默认保持 = group_wait + 30s（本栈即 60s）；也可显式指定
bash scripts/linux/verify-alert-delivery-drill.sh
DRILL_HOLD_SECONDS=90 bash scripts/linux/verify-alert-delivery-drill.sh
```

| 判据 | 2026-10-04 实测 |
| --- | --- |
| 场景 | 停 `blackbox-exporter` → `KnowTraceMetricsTargetDown`（**critical**，路由到 email） |
| 故障保持时长 | `60s`（必须 > `group_wait` 30s） |
| 投递计数 | 基线 `4` → 结束 `5`，**增量 1**（判据：≥1） |
| 投递失败计数 | **0** |
| 投递时刻 | **16:07:30** = firing 16:06:55 + `group_wait` 30s（**精确吻合**） |
| 收尾 | 12/12 targets up、AM 0 条、0 个 unhealthy |

## 9. 故障排查（按症状）

| 症状 | 先看 |
| --- | --- |
| 网站打不开 / 5xx | `docker ps` → app 健康 → `docker logs knowtrace-workflow-app-1` → `curl -sS http://127.0.0.1:3000/api/health/ready` |

### 三条最有价值的经验（本项目反复踩到的）

1. **「命令返回 0」不等于「成功」。**
   2026-09-30 事故、以及本轮我自己 `cmd | tail` 读错退出码，都是这个形状。
   验收要看**状态改变**，不是看退出码。
2. **「部署看起来成功了」是最贵的故障形状。**
   容器起来了不等于日志采到了；`up -d` 成功了不等于镜像重建了。
   所以本项目到处是"读运行态"的断言（`sshd -T`、`sysctl -n`、`ufw status`）。
3. **断言"规范化输出"前，先看它实际印什么。**
   实测踩到：配置写 `prohibit-password`，`sshd -T` 却印 `without-password`；
   `ufw` 把端口印在行首而我查的是带前导空格的串。
   两次都是**配置正确、断言写错** —— 绿灯被当成红灯。

## 12. 变更纪律

改任何东西之前：

1. **先记录**：在 [`../changes/`](../changes/) 写「改什么 / 为什么 / 怎么验收 / 怎么回滚」，
   提交。**记录要先进 git**，这样"当时的意图"和"实际的结果"是两次提交，事后能看出差异。
2. **改动**。
3. **验收**：把结果填回记录的「执行结果」一节。验收标准必须**可执行**。
4. **提交**。

对运维侧（不在 `KnowTrace-Workflow` 仓库内）的改动，记在
`KnowTrace-ops/docs/`（仓库外）。

### 12.1 改名 / 改名类变更的清单（**四项，缺一项就留一个静默失效**）

这条是 2026-10-03 改名换来的：**收尾只做了第 ① 项，后三项各漏出过一个「不会报错的错」**。

#### ⚠️ 先定作用域 —— 否则清单会变成噪声

**2026-10-03 那次改名只动了「标识符」，没动「路径」。** 实测：

| 改了 | 没改 |
| --- | --- |
| 仓库名、compose `name:`、systemd 单元名、镜像名、站点/cookie | 域名、服务器路径（`/opt/knowtrace`、`/etc/knowtrace`、`/var/backups/knowtrace`）、SSH 密钥名（`knowtrace_vps_ed25519.pub`）、日志文件名（`knowtrace-access.log`、`/var/log/knowtrace-backup.log`） |

所以**直接 `grep 'knowtrace'` 会命中 83 个文件，其中绝大多数是合法的**
（`deploy/ansible/` 里的 `00-knowtrace-hardening.conf`、`/root/knowtrace-ops/`、
`deploy/alloy/` 里的日志路径……）。

> **一份 83 条命中、要人眼过一遍的清单，实际效果等于没有清单** ——
> 它会训练人「看到这些就当噪音」，而真正那条会淹在里面。
> **清单必须只列「本次实际改名的那些标识符」**，见下。

#### 四项检查

以 2026-10-03 为例，改名的标识符是 `knowtrace` → `knowtrace-workflow`
（作 **compose project / 单元名前缀 / 镜像名前缀 / 站点名** 用时）。

| # | 查什么 | 漏了会怎样（本项目实测） |
| --- | --- | --- |
| ① | **仓库内的硬编码旧名** | 10-03 漏了 `scripts/linux/` 里的旧 PG 名 → **生产备份 10-03 19:20 起静默失败**（`pg_dump` 产 0 字节） |
| ② | **仓库外的运行时状态** | 配置里 `BACKUP_TIMER_UNIT` 仍是旧名 → 「备份定时器还活着吗」这条判据**空转**（永远记 INFO、从不报警） |
| ③ | **制品与镜像 tag** | 旧 tag 残留：占盘、易误用（10-05 清掉两个，省约 90 MB） |
| ④ | **残留物清点** | 旧 `.prom` 与新文件**定义同一组指标名** → 收集器先撞上旧的赢 → **假告警 + critical 永不触发**（`KT-GAP-28`） |

#### ⚠️ ① 不能用「grep 旧名」来做 —— 实测这条路走不通

试过 `git grep -P 'knowtrace(?!-workflow)'`，命中 **310 行**，绝大多数是**有意保留**的：
`00-knowtrace-hardening.conf`、`99-knowtrace-security.conf`、`knowtrace.access.log`、
`/root/knowtrace-ops/`、`knowtrace.revision`（告警组名）、`knowtrace_vps_ed25519`……
**一份 300+ 条的清单等于没有清单**，它会训练人「看到就跳过」，真正那条会淹在里面。

**根本原因**：grep 只能找到「**你已经知道要改的那类**」标识符；
它发现不了「**你不知道自己漏了**」的那一类 —— 而 10-03 的 PG 名恰恰属于后者
（一个埋在 `scripts/linux/backup-all.sh` 里的 `--dbname=knowtrace` 字符串）。

**正确的做法是两件事**：

**(a) 按「改名前先列出所有会被改的标识符种类」逐个显式查**（不是扫全仓）：

```bash
# compose project name
grep -m1 '^name:' compose*.yaml
# systemd 单元名
systemctl list-unit-files --no-legend 'knowtrace*' --no-pager | awk '{print $1}'
# 镜像名 / 容器名
docker ps --format '{{.Image}}' | sort -u
# 站点与 cookie（Caddy / Nginx）
grep -rn 'server_name\|output file\|cookie' deploy/caddy/ deploy/nginx/
```

> **注意**：`deploy/nginx/` 里 `server_name knowtrace.duckdns.org` 是
> **有意保留的** —— 2026-10-03 那次改名明确**不动域名**（改域名要重新签证书、
> 且 DuckDNS 的记录也要改）。所以「域名里还有旧名」不是漏改。
> **这条正说明 ① 必须是「按已知标识符种类逐个查」，而不是「扫全仓」** ——
> 扫全仓会把这类有意保留的项混进来，让清单失去作用。

**(b) 对「脚本里的硬编码值」做语义比对 —— 这才是能抓到漏改的判据**。
把脚本里写死的值与**运行时的实际值**对一遍：

```bash
# 例：备份脚本写死的库名/用户名 vs PostgreSQL 里真实的（10-03 就漏在这）
grep -nE '\-\-dbname|\-\-username|DATABASE_URL' scripts/linux/backup-all.sh
docker exec knowtrace-workflow-postgres-1 psql -U knowtrace_workflow -l 2>/dev/null | awk '{print $1}' | grep -v '^|' | head

# 例：ops.conf 里的单元名 vs 实际存在的单元
grep -E 'BACKUP_TIMER_UNIT|SYSTEMD_UNITS' /etc/knowtrace/ops.conf
systemctl list-unit-files --no-legend 'knowtrace-workflow-*' --no-pager | awk '{print $1}'
```

**这一类检查的性质是「两侧对账」，不是「搜索」** —— 它同时需要「仓库里的字面量」和
「系统里的实际值」，所以 grep 单侧永远做不到。
（同理：10-03 那次 `pg_dump` 产 0 字节，本来只要有一条
「备份产物非空」的断言就能抓到 —— 见 §6.3。）

#### ②③④ 的可执行清单

```bash
# ② 仓库外运行时状态（这些都不在 git 里，重装/改名都会丢）
#    重点不是「有没有旧名」，而是「键的值指向的东西还在不在」
grep -nE 'BACKUP_TIMER_UNIT|SYSTEMD_UNITS|_UNIT=|_FILE=|_DIR=' /etc/knowtrace/ops.conf
ls -la /opt/knowtrace/runtime/node-exporter/     # 指标文件名也要一起看

# ③ 制品
docker images --format '{{.Repository}}:{{.Tag}}' | grep -i knowtrace
# 删之前先确认没有容器引用它（空才可删）：
docker ps -a --filter ancestor=<image> --format '{{.Names}}'
docker rmi <旧镜像>...

# ④ 残留物：每个 .prom 还有没有**写入者**？没有就是孤儿，必须移出
for f in /opt/knowtrace/runtime/node-exporter/*.prom; do
  b=$(basename "$f")
  printf '%-34s <- %s\n' "$b" "$(grep -rl -- "$b" /opt/knowtrace/scripts/ 2>/dev/null | head -1 || echo '无写入者 ⚠️')"
done
```

**2026-10-05 实测这四项的结果**：
- ① 按 (a) 逐个查：compose name / 单元名 / 镜像名 / 站点 全部为新名 ✅；
  按 (b) 对账：`backup-all.sh` 的 `--dbname=knowtrace_workflow` 与 PG 里实际库名一致 ✅
- ② `BACKUP_TIMER_UNIT` 已修；指标文件名全部为新名 ✅
- ③ 清掉 2 个孤儿镜像（`knowtrace-app:latest` / `knowtrace-auth:dev`，无容器引用）✅
- ④ 4 个 `.prom` 全都有写入者 ✅

#### 为什么 ④ 最容易漏

①②③ 都能靠 `grep` 一次扫出来，而 ④ 要求的是「**找出那些『已经没有源头、但仍然在生效』的东西**」
—— 孤儿文件**不会出现在任何 `grep` 结果里**，因为**没有代码再引用它**。
它的唯一判据是「这个文件还有没有写入者」。

#### 两个必须记住的细节

- **孤儿指标文件要「移出目录」，改名无效。** node-exporter 的 textfile 收集器按 `*.prom`
  **通配**，点开头**不算隐藏** —— 改成 `.orphan-xxx.prom` 仍会被读、仍然遮蔽。（实测踩过。）
- **改完要验证「新的在生效」，不能只看「命令返回成功」。** 最快的证伪方式是**注入**：
  把孤儿文件放回去，判据必须**立刻变坏**；移走，必须恢复。
  （`KT-GAP-28` 的修复就是这么验的 —— 只看「现在没告警了」不足以证明判据没瞎。）
