## 2. B 部分：业务级可用性（`KT-GAP-16` 的核心缺口）

数据层 PASS **不等于**恢复出来的东西能用。所以要真的读出业务对象。
本次把归档里的 `postgres.dump` 恢复到一次性容器并**读表**：

```bash
docker run -d --name kt-drill-pg-$$ --network none \
  -e POSTGRES_DB=knowtrace -e POSTGRES_USER=knowtrace -e POSTGRES_PASSWORD=drill-only \
  postgres:18-alpine
docker cp <解包>/postgres.dump kt-drill-pg-$$:/tmp/pg.dump
docker exec kt-drill-pg-$$ pg_restore -U knowtrace -d knowtrace \
  --no-owner --no-privileges --exit-on-error /tmp/pg.dump
docker exec kt-drill-pg-$$ psql -U knowtrace -d knowtrace -tAc "<各表 count>"
```

【实测】恢复后读出：

| claim_evidence | 0 |

**`pg_restore --exit-on-error` 退出码 0** —— 23 张表的结构、外键、约束在恢复过程中
没有任何一条失败。默认 Workspace 与 2 条成员关系可读。

## 3. ⚠️ 本次演练最重要的发现：**生产库当前没有业务数据**

上表 `captures=0` 起初看着像「恢复丢了数据」。**实测核对了生产库**：

```bash
docker exec knowtrace-workflow-postgres-1 psql -U knowtrace_workflow -d knowtrace_workflow -tAc "<各表 count>"
```

【实测】生产库同样是 `captures=0 / categories=0 / claims=0 / …`，
只有 `workspaces=1`、`workspace_memberships=2`；MySQL `go_user_system` 有 `users=1 / roles=2`。

**结论：归档是忠实的，没有丢数据 —— 是生产库本来就没有业务数据。**
这与「备份坏了」是完全不同的两件事，如果只跑数据层脚本、不做这次人工读表，
**很容易误判**（行数 `cmp` 通过是因为源和目标都是 0）。

> **对备份的意义**：当前备份「有内容」的部分只有：数据库结构、默认 Workspace、
> 认证账号（MySQL 1 用户）、以及上传目录里的 1 个文件。**它的正确性目前是靠结构与
> 少量种子数据验证的，还没有被真实业务数据验证过。** 等有了真实记录，应再跑一次本演练。

| 项 | 值 |
