# 编号规范

标识符是**索引**。索引不可靠，历史记录就检索不到——而排障最需要的恰恰是「以前遇到过没有」。
本文把仓库里**已经在用**的编号体系写定，并说明历史上出现过的一次语义漂移与映射。

> 最后核对：**2026-10-04**（前缀清单由 `grep -rhoE` 全量枚举得出，不是回忆）。

| `KT-DEFER-` | 暂缓债务 | `KT-DEFER-NNN` | `docs/14-deferred-issues.md` | `KT-DEFER-009` |
| `S<n>` | **阶段前缀**（不是独立编号） | 拼在 `INC-`/`ISSUE-`/`BUG-` 后 | — | S1 / S2 / S3 |

**约定**：

- 编号**只增不改**。已发布的编号不复用、不改含义；作废时保留并标 `已作废`。
- **阶段前缀是必需的**（`S1`/`S2`/`S3`）。它让「阶段二的 INC-001」与「阶段三的 INC-001」
  不再撞号——历史上它们确实撞了，见第 3 节。
- 文件名形如 `<前缀>-<阶段>-<序号>-<中文简述>.md`，简述用**问题本身**命名，不用「问题」「异常」这类空词。
- `docs/changes/` 下的变更记录**不用编号**，用日期 + 主题（`2026-10-04-主题.md`），
  因为它记的是「动作」，不是「条目」。

## 2. 三条纪律

1. **故障与问题分开编号。** 造成线上不可用/降级的 → `INC-`；发现了但没造成故障的 → `ISSUE-`。
   这个区分在阶段二之后已经成立，**阶段一没有**（见第 3 节），新记录一律按新规则。
2. **一条记录一个编号，不合并。** 同一次排查里发现的两件独立的事，写两条。
   编号的价值在于可检索，合并会让「以前遇到过没有」这个问题失去答案。
3. **结论回写后才算关闭。** 任何 `INC-`/`ISSUE-` 的根因结论，必须同步到受影响的下游文档
   （产品侧、架构侧），否则同一事实会在两处处于不同成熟度——`INC-009` 就是这么埋了 8 项未执行
   的改进项，代价见 [`changes/2026-10-04-INC-009改进项与验收标准跟踪.md`](changes/2026-10-04-INC-009改进项与验收标准跟踪.md)。

## 4. 新记录怎么编

1. 选前缀：线上不可用/降级 → `INC-`；其它发现 → `ISSUE-`；使用者报告的软件缺陷 → `BUG-`。
2. 加阶段前缀：`INC-S3-002`。
3. 序号取该前缀在该阶段的**下一个空号**（`ls <阶段>/<目录>/` 看最大号 +1，不复用）。
4. 从模板起笔：[`模板/ISSUE-模板.md`](模板/ISSUE-模板.md)（问题）、
   阶段二/三目录里已有的 `INC-模板.md` / `BUG-模板.md`（故障 / 缺陷）。
5. 结案时：在记录里写「结论回写到哪份文档」，并在对应台账里更新状态。
