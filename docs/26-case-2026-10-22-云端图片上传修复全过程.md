## 1. 一句话结论

云端（Vercel）证据图片上传之所以长期失败，**不是一个 bug，而是五个依次叠加的缺陷**。
它们按顺序暴露，每一个都被前一个掩盖：修掉前一个，后一个才显形。

## 3. 五个缺陷，按暴露顺序

### 缺陷 ① 本地文件系统硬绑定（issue 原始根因）

- **现场**：`image-storage.ts` 用 `node:fs/promises` 读写 `data/uploads/evidence`。
- **为什么在云端必然失败**：Vercel 函数文件系统**只读**；且实例重启即清空。
- **修法**：抽出 `local` / `vercel-blob` 双驱动（`ADR-0020`）。
- **为什么只做到这一步不够**：见 ②。

### 缺陷 ② 请求体 4.5 MB 硬限（issue 未提到）

- **事实**：Vercel 函数的**请求体上限是 4.5 MB**（官方 `functions/limitations` 原文），
  而产品允许**单张 10 MB**。`next.config.ts` 的 `serverActions.bodySizeLimit: "12mb"`
  **只影响 Next 自己的检查，改不了平台上限**。
- **后果**：只换存储驱动时，>4.5 MB 的图片仍会在**进入函数之前**被 413 拒绝。
- **修法**：浏览器**直传**对象存储（`@vercel/blob/client` 的 `upload()`），函数只签发一次性令牌 + 收几 KB JSON。
- **代价**：直传的字节不经服务端 ⇒ 引入 ③。

### 缺陷 ③ 服务端不能盲信浏览器（直传带来的）

- **问题**：直传后浏览器只回报一个 pathname；MIME / 大小 / 哈希都来自客户端。
- **修法**：提交时服务端**从存储回读字节**，重做魔数与大小校验，**由服务端计算 SHA-256** 后落库。
- **附带修掉的两个真实缺陷**（复查时发现，非计划内）：
  - 重复提交会命中 `storage_path` 唯一索引，而失败分支的**补偿删除会删掉第一次已落库引用的对象**
    ⇒ 改为 `onConflictDoNothing` 后无返回行即判重复提交、**不删对象**。
  - 直传的令牌签发路径**漏了 `requireEvidenceAccess`**（本地通道有），与 `ADR-0015/0017` 的隔离模型不一致 ⇒ 补齐。

### 缺陷 ④ 读图把一切错误伪装成 404

- **现场**：`/api/evidence-images/:id` 原实现 `catch {}` 一律返回 404。
- **后果**：存储切到 Blob 后，凭据失效、存储未配置、网络故障**全部显示为「图片不存在」**——
  排查时没有任何线索。
- **修法**：区分 404（真不存在）/ 401-403（凭据）/ 存储未配置；其余**记日志并返回 503**。

### 缺陷 ⑤ 驱动判定只认静态 token，不认 OIDC（**决定性的那一个**）

- **现场**：生产日志
  `[knowtrace-startup] 云托管环境（VERCEL=1）没有可用的对象存储凭据`，上传仍失败。
- **根因**：Vercel 上存储是以 **OIDC** 方式连接的（注入 `BLOB_STORE_ID`，运行时用
  `VERCEL_OIDC_TOKEN` 换授权），而驱动判定**只检查静态 `BLOB_READ_WRITE_TOKEN`**
  ⇒ 判「无凭据」⇒ 回落本地磁盘 ⇒ 只读文件系统 ⇒ 失败。
  **这是实现缺陷，不是配置缺陷**——用户其实早就把存储配好了。
- **两个必须读源码才知道的细节**：
  1. `@vercel/oidc` 的 `getVercelOidcToken()` **首选读请求上下文头** `x-vercel-oidc-token`，
     `process.env.VERCEL_OIDC_TOKEN` 只是兜底 ⇒ 判定**不能只查 env**。
  2. SDK 的 `handleUpload`（签发客户端令牌）走 `getReadWriteBlobTokenFromOptionsOrEnv()`，
     **没有静态 token 就直接抛错**，不会退到 OIDC ⇒ **OIDC 下不能浏览器直传**。
- **修法**：
  - 凭据判定分三态 `read-write-token` / `oidc` / `none`；
  - **直传与存储解耦**：新增 `server-blob` 通道——**存储仍是对象存储，由服务端写入**；
  - `server-blob` 与 `form-action`（本地磁盘）**必须可区分**（混为一谈正是本次故障形态）；
  - 服务端写入受 4.5 MB 限制 ⇒ 前端在 `server-blob` 下超限直接给可读提示，不把裸 413 抛给用户；
  - 凭据类错误**没有 HTTP 状态码**，需单独识别并翻译，否则会落进 500「未知错误」。

## 5. 这一轮真正有价值的教训

1. **「CI 绿 + 已合并」不等于「功能可用」。** 前四个缺陷全部修完、CI 五 job 全绿之后，
   生产仍然失败。**判据必须是外部可观测状态**（存储里有没有对象、能不能读回），不是流程信号。
2. **「没有证据」与「没有发生」是两件事。** 修复后我两次 `list` 到 `COUNT=0`，
   当时的正确结论是「**未被证实**」，不是「没修好」，也不是「修好了」。四小时后同一个查询变成 1。
3. **平台默认值会改变代码分支。** OIDC 是 Vercel 现在的默认连接方式，而 SDK 的直传子能力
   并不支持它——**默认值本身就是一条分支**，必须实测，不能按「一般情况」推断。
4. **错误必须可区分。** ④（404 吞掉一切）与⑤（无凭据回落本地）是同一族缺陷：
   失败被伪装成另一种状态，于是**排查方向被引到错误的层**。
   本次能定位到⑤，正是因为启动告警把「没有凭据」直接打了出来。
5. **只读源码才能拿到的事实，不要去猜。** OIDC token 从请求头取、`handleUpload` 只认静态 token，
   都是**读 SDK 与 `@vercel/oidc` 实现**才确认的；按文档措辞推断会得出错误的修法。
