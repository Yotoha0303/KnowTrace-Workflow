### D-01 图片上传 100% 失败——绑定挂载盖掉了镜像里的属主（✅ 已于 2026-09-30 修复）

**【实测】决定性证据**

```
容器内身份：uid=1001(nextjs) gid=65533(nogroup)
目录属主：  drwxr-xr-x root root /app/data/uploads/evidence
写入探测：  touch /app/data/uploads/evidence/.probe  →  Permission denied
            WRITE_FAIL
```

应用日志中的对应错误：

```
Error: EACCES: permission denied, open
'/app/data/uploads/evidence/73f06f20-...-...png.77af47ec-...-....tmp'
```

出现 42 次（2026-09-13：38 次，2026-09-19：4 次）。

**根因（比「忘了改权限」更具体）**：`Dockerfile` 里其实做对了——

```dockerfile
RUN addgroup --system --gid 1001 nodejs \
  && adduser --system --uid 1001 nextjs \
  && mkdir -p /app/data/uploads/evidence \
  && chown -R nextjs:nodejs /app/data
```

但 `compose.yaml` 的绑定挂载 `./data/uploads:/app/data/uploads` **把镜像里这个目录整个盖掉了**，宿主机那份是 root 建的。所以是**镜像的正确设置被挂载覆盖，而宿主机侧没有任何机制补位**。

另一个易错点：容器内 `nextjs` 的主组是 **65533(nogroup)** 而不是 1001(nodejs)——`adduser --system --uid 1001 nextjs` 没给 `--ingroup`，主组落到 alpine 的默认系统组。用 `1001:1001` 去 chown 仍然会失败。

**修复（已完成并实测）**：

1. 服务器上执行 `chown -R 1001:65533 /opt/knowtrace/data/uploads`。
2. 用真实写路径验证（`writeFile {flag:"wx"}` + `rename`）→ `WRITE_OK`。
3. 新增 `scripts/linux/fix-uploads-ownership.sh`（幂等，带真实写入探测，成功输出 `UPLOADS_OWNERSHIP=PASS`），已在服务器上双向实测：故意打回 `root:root` → 写入失败 → 脚本修复 → `WRITE_OK`。
4. 新增启动自检 `src/server/startup-checks.ts`：目录不可写时打印带修复命令的显式告警，不再静默失败 42 次。
5. 写入 `docs/11-operations.md` 第 7 节与 `docs/15-stage2-vps-reliability.md`（恢复路径）。

**这条推翻了我此前的判断。** 我曾把 BUG-003 归因于 HEIC 格式不被支持（写进了 `docs/17-mobile-client-bugs-and-features.md`）。**那是错的**——目录从 2026-09-06 13:34 创建起就不可写，**上传从未成功过一次**，与图片格式无关。格式兼容是修好权限之后才会遇到的第二个问题。

**影响**：证据图片功能完全不可用；主张-证据链的「附件核验」环节随之无法走通。

**残余风险：还没做成自动化**

修复动作是**手动的**，靠文档告知。风险窗口比最初判断的窄——**实测确认**：容器重建（`compose up -d app`）后属主保持 `1001:65533`、写入仍 `WRITE_OK`，因为 Docker 只在绑定挂载源目录**不存在**时才创建它。

会真正触发故障的是这三种情况：

| 触发条件 | 为什么 |
|---|---|
| 全新主机首次部署 | 目录不存在 → Docker 以 root 创建 → 不可写 |
| 从备份恢复 `data/uploads` 之后 | `tar` 解包属主是解包者（通常 root） |
| 挂载目录被删除后重建 | 同首次部署 |

日常 `compose up` / `restart` **不会**触发。已写入 `docs/11-operations.md` 的部署步骤与恢复步骤。

彻底消除需要在以下三者中选一个（均未实施）：

| 方案 | 代价 |
|---|---|
| 部署脚本固定顺序执行 `up` + `fix-uploads-ownership.sh` | 需要有一处「唯一部署入口」，而当前部署是手工 `cp` + `compose up` |
| 用命名卷替代绑定挂载，由镜像内初始化固定属主 | 改动备份/恢复路径（备份脚本按 `data/uploads` 路径打包） |
| compose 里用 root 入口脚本先 chown 再降权 | 需要改 Dockerfile 的 `USER` 策略，影响面最大 |

**建议**：等 D-06（部署链路）一起处理，因为那件事本来就要引入部署入口，两件事合并成本最低。

> **2026-10-21 更新（残余在新平台复现并已处理）**：上面的属主修复只对**自建 Docker / VPS**有效。
> 迁到 Vercel 后，容器文件系统**只读且易失**，本地驱动无法通过任何 `chown` 修复 —— 现场是
> 启动日志的 `EACCES`／上传失败（`ISSUE-S3-024`）。另有第二根因：上传走 Server Action，
> 而 Vercel 函数请求体上限 **4.5 MB**、产品允许 **10 MB/张**，所以**只换存储驱动仍修不完整**。
> 处理方式见 [`ADR-0020`](adr/0020-evidence-image-object-storage.md)：云端改为**浏览器直传对象存储**
> + 服务端回读复核；本地驱动保持不变，第 7 节运维步骤对本地部署仍然有效。
> **未闭环的前置**：Vercel 侧创建 Private Blob 存储（`CICD-待完成.md` E5）——完成前云端上传会以
> 「缺少 `BLOB_READ_WRITE_TOKEN`」显式报错（**不再是** `EACCES`），这是预期的失败形态。

### D-02 线上 AI 是本地规则模拟，不是真模型（✅ 已于 2026-09-30 配置真实 AI）

**【实测】修复前的服务器配置**

```
AI_DEFAULT_PROVIDER=mock           ← 默认提供方是 mock
OPENAI_API_KEY    未设置
DEEPSEEK_API_KEY  未设置
OPENAI_MODEL=gpt-5.6-luna / DEEPSEEK_MODEL=deepseek-v4-flash   ← 配了名字但没有密钥
```

**【实测】19 次 AI 运行的构成（修复前）**

| provider | 次数 | 结果 |
|---|---:|---|
| `mock`（`knowtrace-local-rules-v1`） | 3 | 全部成功，耗时 21–51 ms |
| `deepseek`（`deepseek-v4-flash`） | 11 | 9 失败 / 2 成功（17.9 s、65.6 s） |
| `openai`（`gpt-5.6-luna`） | 5 | 5 失败 |

总成功率 5/19；剔除 mock 后真实模型 2/16。14 次失败全是 `AI_APICallError`，耗时仅 64–606 ms——**立即拒绝，不是模型慢**。

**【实测】用户对 AI 结果的处置**：`modified=2, rolled_back=3, accepted=0`。

**根因**：服务器 `.env` 里 `DEEPSEEK_API_KEY` 与 `OPENAI_API_KEY` 都是空的，而 `AI_DEFAULT_PROVIDER=mock`。用户在界面选 DeepSeek 时，密钥输入只在 `connection.mode === "api_key"` 下生效（`src/server/ai/provider.ts:264-273`），否则回落到 `process.env.DEEPSEEK_API_KEY`——为空则 401。这正好解释了「立即失败」的时间特征。

（注：若密钥真的完全缺失，应抛 `AI_PROVIDER_NOT_CONFIGURED`；线上记录的是 `AI_APICallError`，说明当时有密钥但被上游拒绝。这一点**未完全确认**，不影响修复结论——现在密钥有效且实测可用。）

#### 已完成的修复与线上验证

1. 用有效密钥配置服务器 `.env`（`DEEPSEEK_API_KEY`、`AI_DEFAULT_PROVIDER=deepseek`），权限 600，改动前已备份到 `/root/knowtrace-env-backup-20260930T112526Z`。
2. 重建 app 容器（`--env-file .env --env-file .env.observability` + 三份 compose），**实测停机 8 秒**。
3. **容器内出网实测**：`CONTAINER_EGRESS_OK status=200 model=deepseek-flash`，中文回答正确。
4. **真实集成测试 4/4 通过**：新增 `src/server/ai/provider.integration.test.ts`（默认跳过，有密钥才跑），走的是生产同一条 `organizeWithAI` 路径与同一段 system prompt。

```
[1] PASS  latency=19498ms  in=1472 out=4385  title="某公司采购与技术负责人关于下季度预算的说法矛盾"
[2] PASS  latency=13111ms  in=1472 out=2814  title="某公司采购与技术负责人对下季度预算说法不一致"
[3] PASS  latency=10994ms  in=1472 out=2306  title="某公司下季度预算说法矛盾：采购称可能腰斩，技术负责人此前称会增加"
[4] PASS  latency= 7232ms  in=1472 out=1444  title="某公司下季度预算口径前后矛盾（采购 vs 技术负责人）"
```

质量结论：四次都把「同一公司两个来源说法矛盾」抓成了标题——这是知识管理真正要的点，不是模板化改写。**质量不是问题。问题在延迟。**

#### 修复后暴露的两个新问题

**① 延迟仍在 7–20 秒，且输出 token 异常高。**

四次调用输出 1444–4385 token，而输入只有 1472。原因是 `deepseek-v4-flash` 实际是一个**推理模型**——实测一次简单调用 `completion_tokens=172` 里 `reasoning_tokens=151`。绝大多数输出预算花在思维链上。

这解释了线上那两次成功的 17.9 s / 65.6 s。**用推理模型做结构化字段抽取，成本与延迟都不划算。**

**② 模型名会被静默改写。**

`GET /models` 只返回 `deepseek-flash` 与 `deepseek-v4-pro`，但请求 `deepseek-v4-flash` 返回 200 且响应 `model` 字段为 `deepseek-flash`。即该名字**可以被接受并静默路由**。这意味着只靠模型名审计（`ai_processing_runs.model`）无法确认真实执行的是哪个模型。

**③ 65.6 秒那次仍未解释。** 需要生产侧真实数据，而当前**没有 `/api/v1` 的 AI 触发端点**（AI 整理走 Server Action），所以只能等下一次真实使用。

**建议的后续动作**（未执行，需你决定）：

| 项 | 说明 |
|---|---|
| 换用非推理模型 | 试 `deepseek-flash` 是否与 `deepseek-v4-flash` 同物；若同为推理模型，需评估 `deepseek-v4-pro` 或换回 OpenAI。目标是把 P95 压到 5 秒内 |
| 补 `/api/v1/ai-runs` | 缺口二。不补则无法对 AI 做受控的线上测量，也无法支撑移动端 |
| 在 UI 中显式提示延迟 | 7–20 秒的等待需要进度反馈，否则用户会重复点击 |

**怎么验证真正修好了**：`ai_processing_runs` 中出现 `provider='deepseek'` 且 `status='succeeded'`、`latency_ms` 稳定在目标区间的新行；`ai_suggestions` 出现 `accepted` 状态。**当前只有 4 条本地集成测试证据，还没有生产侧的真实使用数据。**

### D-09 演示数据清理误删系统默认工作区，导致新旧用户登录触发外键违约 500 循环（✅ 已于 2026-10-21 根治）

**【实测】决定性证据**
- 线上用户在 `/register` 可以顺利创建账号，但在 `/login` 登录后无法进入主界面，反复被重定向弹回登录页。
- 探测脚本直接携带认证生成的 Cookie 访问根路径 `GET https://knowtrace-workflow.vercel.app/`，服务端稳定抛出 **500 Internal Server Error**。
- 根因定位到数据库报错：
  ```text
  insert or update on table "workspace_memberships" violates foreign key constraint "workspace_memberships_workspace_id_fkey"
  Key (workspace_id)=(00000000-0000-4000-8000-000000000001) is not present in table "workspaces".
  ```

**根因**：
- `src/shared/workspace.ts` 与迁移 `0020_workspace_foundation.sql` 约定了硬编码默认空间锚点 `00000000-0000-4000-8000-000000000001`（`LEGACY_DEFAULT_WORKSPACE_ID`）。
- 2026-10-20 在准备线上演示数据时，播种脚本执行了 `DELETE FROM workspaces;`，并将新数据放入随机 UUID 空间，导致默认锚点被物理删除。
- Next.js 服务端在用户认证通过后执行 `ensureLegacyWorkspaceMembership`，无条件向默认空间写入成员映射，导致外键违约崩溃。

**修复（已完成并实测验证）**：
1. 数据库事务内恢复 `00000000-0000-4000-8000-000000000001` 默认工作区。
2. 将既有业务捕获与分类全量迁移挂载至该默认空间。
3. 自动化测试用例以全新用户 `user_e2e_*` 实测执行注册、登录、换取 Token、带 Session Cookie 访问首页，验证状态码由 500 彻底恢复为 **200 OK** 并成功渲染个人仪表盘。
4. 详见事故复盘报告：[`docs/25-incident-2026-10-21-default-workspace-fkey-login-loop.md`](25-incident-2026-10-21-default-workspace-fkey-login-loop.md)。

## 二、P1：影响体验或存在真实风险

### D-04 「访问慢」的归因与直觉相反：服务端一点不慢（实测）

**【实测】边缘侧真实延迟**（Caddy 访问日志 9,874 条请求）

```
p50 = 5.9 ms
p90 = 9.0 ms
p95 = 10.8 ms
p99 = 20.2 ms
max = 607 ms
状态码：200×9810 / 307×49 / 401×6 / 502×5 / 404×2 / 308×2
```

**没有任何一条请求超过 1 秒。**

**【实测】从 VPS 本机向自己握手**：TLS 建立 11 ms。从我这台机器握手 820–920 ms，而 TCP connect 只要 1.2 ms——是中间链路的调度/带宽问题，不是 VPS 配置问题。VPS 是 AMD EPYC 7K62、有 AES-NI、2 vCPU，密码学不是瓶颈。

**所以「访问慢」的真实来源在浏览器侧：【实测】生产构建的 JS 总量 1.2 MB / 24 个 chunk，最大单块 283 KB，而服务端没有对静态资源配置 `immutable` 长缓存**（响应头是 `private, no-cache, no-store`）。首次访问要把这些下载并解析完才能交互。

**【实测】另一个被忽略的事实**：9,874 条请求里 **9,722 条（97%）是 `/api/health/ready` 健康探针**。真实用户请求只有几十条。当前样本量下，任何「用户觉得慢」的结论都缺乏统计基础。

**怎么验证修好了**：静态资源配置指纹化长缓存后，浏览器 DevTools 中首屏 transferred size 与 LCP 明显下降；`cache-control` 对 `/_next/static/*` 返回 `immutable`。

### D-05 数据隔离机制完整，但从未在多用户下被验证过（实测）

> **2026-10-01 收尾更新**：仍**未做**，且查明了一个硬阻塞——
> **认证服务没有建号接口**（从 GIN 路由日志确认只有 login/refresh/logout/

> 绕过路径：临时打开自助注册（服务自带，推荐）或直写 MySQL（风险高）。
> 详见 [`changes/2026-10-01-收尾闭环.md`](changes/2026-10-01-收尾闭环.md) 第 3 节。

**【实测】机制层面**

```
workspace_id  出现在 7 张表
created_by_id 出现在 3 张表
索引 79 个，其中 gin/trgm 6 个
```

服务端数据访问层有逐资源的访问校验（`src/features/auth/access.ts`，含 `requireCaptureReadAccess` / `requireEvidenceAccess` / `requireAttachmentReadAccess` 等），跨成员资源按不存在处理（返回 404 而非 403），这些设计是**正确的**。

**【实测】验证层面——这是问题所在**

```
RLS：0 张表启用行级安全，0 条策略     ← 隔离完全依赖应用层，数据库层无兜底
真实用户：仅 1 个（go-user:1）
captures：4 条，全部 created_by_id=go-user:1、全部 visibility=shared
workspaces：2 个，成员都是同一个 go-user:1
```

**没有任何一条私有记录、没有第二个创建者、没有跨 Workspace 的真实数据。** 也就是说：隔离逻辑写得再对，也**从没有被真实的多用户数据检验过**。

**风险**：一旦开放注册（FEAT-006）或第二个用户进入，隔离的第一次真实检验就发生在生产。而应用层单点隔离意味着**任何一个漏掉校验的新入口都会直接泄露数据**，没有数据库层兜底。

**怎么验证修好了**：用两个真实账号在生产（或与生产同构的隔离实例）完成一次越权矩阵回归——A 的私有记录在 B 的列表/详情/搜索/分类/图片/导出中均不可见，且跨 Workspace 访问被拒。现有 `tests/e2e/content-ownership.spec.ts` 覆盖了部分，但需要重跑并补充图片与导出路径。

### D-08 登录限流按「容器 IP」计数 → 所有人共用一个桶（✅ 2026-10-01 实测定位）

**用户现象**：「即使密码和账号正确，仍然可能触发『账号或密码错误』」。

#### 决定性证据

```text
$ docker logs knowtrace-workflow-auth-1 | grep auth/login   →  每次成功后紧接一串失败
  time=10:28:41 status=429 latency=108026301 ip=172.18.0.9
  time=10:28:43 status=429 latency=1545578   ip=172.18.0.9
  time=10:28:43 status=429 latency=1813593   ip=172.18.0.9
```

**`ip=172.18.0.9` 是 Docker 容器的地址，不是任何真实用户。**

#### 转发链为什么断在这里

| 跳 | 是否传递真实 IP |
| --- | --- |
| Caddy → nginx | ✅ Caddy 自动设 `X-Forwarded-For` |
| nginx | ✅ `real_ip_header X-Forwarded-For` + `real_ip_recursive on`（`/etc/nginx/sites-enabled/knowtrace-workflow.conf:17-19`），**ngnix 自己的 `$remote_addr` 已是真实 IP** |
| nginx → app | ❌ 转发的是 `$http_x_forwarded_for`（**入站头**），而真实 IP 在 `$remote_addr`。出站链变成 `<真实IP>, 172.18.0.2` |
| **app → auth** | ❌ **KnowTrace-Workflow 的 BFF 完全不转发任何 XFF**（`src/app/api/v1/auth/login/route.ts` → `loginWithGoUserSystem`） |

**结果**：认证服务看到的 `c.RemoteAddr` = 应用容器 IP。
又因为 `config.yml` 里 **`trustedProxies: []`**（空），Gin 不信任任何代理，
`c.ClientIP()` 直接返回该容器地址。

#### 后果（比"显示错误"更严重）

限流是**双维度**的：

```yaml
loginRateLimit:
  accountLimit: 5     # 同一账号 5 次失败
  ipLimit: 20         # 同一 IP 20 次失败
  window: 15m
```

因为所有请求共享同一个"IP"，**ipLimit 退化成全站总配额**：

> **任一用户累计失败 20 次，会让这台服务器上所有人的登录在 15 分钟内全部失败**，
> 包括密码完全正确的用户。

**已实测复现**（用不存在的账号，避免锁住真实账号）：

```text
第1~4 次  → {"code":"AUTH_INVALID_CREDENTIALS","message":"账号或密码错误。"}
第5次     → {"code":"AUTH_LOGIN_RATE_LIMITED","message":"登录尝试过于频繁，请稍后再试。"}
第6次     → 同上
```

#### 一个容易搞错的地方（记录以免误改）

`src/features/auth/auth-errors.ts` **已经**把 2008 正确翻译成「登录尝试过于频繁」，
且前端会显示它。所以**限流路径给出的文案是正确的**。

真正的坑是：**用户必须先把失败次数堆到 `ipLimit`（20）才会看到那句正确文案**。
在 5–20 次之间，别人失败造成的限流会以「账号或密码错误」的形式出现。

#### 另一处更隐蔽的同形问题（多标签页）

连续成功登录时，若某些请求带的是**已失效的 access cookie**，
Proxy 会先走续期；续期若失败则**清空会话 cookie**。某个标签页清空后，
另一个仍在轮询的标签页会变成未认证 → **被登出**。
现行机制无法区分「refresh 真的失效」与「另一个标签页刚把它换走了」。

#### 怎么验证修好了

- `docker logs knowtrace-workflow-auth-1 | grep auth/login` 中 `ip=` 字段应是**真实客户端 IP**，不再是 `172.18.0.x`；
- 用一个来源的 20 次失败**不应**影响另一个来源的正确登录。

#### 修法方向（**本次未实施**）

| # | 方向 | 说明 |
| --- | --- | --- |
| 1 | **恢复真实 IP 传递** | nginx 改传 `$remote_addr`；BFF 转发 `X-Forwarded-For`；auth 侧设 `trustedProxies` 为**该容器网段**并启用 Gin 的信任链 |
| 2 | 或改用账号维度为主 | 削弱/去掉 IP 维度，避免共享桶 |
| — | **明确不做** | 不加 `X-Forwarded-For` 而不配 `trustedProxies` —— 那会**信任客户端伪造的头**，比现在还糟（可被用来绕过限流） |

**本次只定位与记录，未改代码** —— 限流是认证边界，改动需要单独记录并按流程走。
