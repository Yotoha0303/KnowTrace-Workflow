## 1. 被推翻的是什么

原断言步是四条 `grep` 文本判据：`^--- SKIP: Test…Integration` 计数为 0、`^--- PASS: Test…Integration` 计数 >= 1。
它**看起来**在验「集成测真跑了」，实际有四条假绿通道：

| # | 通道 | 为什么原判据看不见 |
| --- | --- | --- |
| **A1** | 删掉 9 条里的 8 条 | 只判 `>= 1`，降到 0 才红 |
| **A2** | 把真用例换成 fake driver | 文本里 `--- PASS:` 与真库完全同形 |
| **A3** | 把用例包进 `t.Run` 再 `t.Skip` | `grep -cE '^--- SKIP:'` 锚在行首，子测试缩进 4 空格；父用例照打 PASS |
| **A6** | 重跑同一 SHA | `go test` 缓存成功包，`-v` 回放上次的 `--- PASS` |

## 3. 新判据（四条，缺一不可）

实现：`scripts/check-go-integration-gate.mjs`。输入是 `go test ./... -count=1 -json 2>&1 | tee` 的原始输出。

| # | 判据 | 堵哪条 | 为什么这样写 |
| --- | --- | --- | --- |
| ① | 日志里必须出现 `REAL_DB_FINGERPRINT database=… version=…` | A2 | 标记由 `testutil.OpenMySQL` 向**数据库**要 `SELECT DATABASE()` / `SELECT VERSION()` 拼出。fake driver 不经过 `OpenMySQL` 的真实分支，造不出这一行。 |
| ② | 任何 **名字含 Integration** 的 `Action=="skip"` 都失败 | A3 | JSON 事件里**没有缩进**这个概念，子测试与顶层同形；整条规则与 `t.Run` 无关。 |
| ③ | 顶层（`Test` 不含 `/`）、名字含 `Integration` 的 `Action=="pass"` **>= 8** | A1 | 8 是**真实连库**的下界（9 条里 1 条走 fake driver）。见 §6 的取舍。 |
| ④ | 包级/构建失败、用例失败、`(cached)` 各自单列，**先于**计数报告 | A5 / A6 | 让「环境坏了」与「判据没建」在输出上不同形；`-count=1` 从根上去掉缓存，`(cached)` 检查是纵深防御。 |

### 3.1 指纹为什么放在 `OpenMySQL`

- 全仓 import `testutil` 的包只有 `dao` / `service`（`grep -rn 'internal/testutil' --include=*.go` 实测），
  它们**只**通过 `OpenMySQL` 拿库；放在这里覆盖 100% 的真实集成路径。
- 与 `assertTestDatabase` / `acquireIntegrationLock` 同层——任何 DRY 修法自会经过它。
- 失败时**只 `t.Log` 不 `t.Fatalf`**：`mysql_test.go` 里有多条用例把 `openMySQLDB` 指向 fake driver
  并照常调 `OpenMySQL`；若这里 Fatal，那些单元测会红，且它们的红与「指纹没打出来」混在一起。
  假连接**不会**因此蒙混：拿不到合法 `version` 就不打印前缀（由 `TestBuildRealDBFingerprintRejectsFakeConnection` 钉住）。

### 4.4 本机咬到的两个真缺陷（都修了）

1. **「一切 skip 都失败」会误伤合法用例**：`TestOpenMySQLSkipsWhenDSNIsMissing` 是**故意** skip 的
   单元测（验的正是「无 DSN 时应 skip」）。真实跑一次就红了。判据收窄为「名字含 Integration 的 skip」——
   仍堵得住 A3（子测试名是 `TestXIntegration/sub`）与「DSN 配错 → 集成测全 SKIP」。
2. **`working-directory` 会找不到脚本**：`go` job 的 defaults 是 `services/go-user-system`，
   而脚本在仓库根的 `scripts/`。断言步显式覆盖为 `${{ github.workspace }}`。

## 6. A1 的取舍：为什么是 `>= 8` 而不是更强

**能做到的更强判据**：

| 方案 | 问题 |
| --- | --- |
| `== 8` | 用例数**加一条**就红，门变成「每次加用例都得改门」——会训练人改门而不是看门 |
| 名字白名单（8 个名字写死在门里） | 重命名即静默失效：名字对不上 = 不计入 = 门变松，且**不会响** |
| 动态基线（上次运行的数） | 需要跨 run 存状态；第一次运行无基线；基线本身可被一次坏运行污染 |

**选 `>= 8` 的理由**：8 是**真实连库**用例数在写下判据时的实测值。它把「删用例」从
「静默变绿」变成「红」，同时不惩罚加用例。**已知取舍（明确接受）**：
将来加用例不会红；**删到 8 以下才红**。若某天真实用例数**合法地**降到 8 以下（例如合并用例），
需要连同本判据一起改——这是**有意的**人工判断点，不是缺陷。
