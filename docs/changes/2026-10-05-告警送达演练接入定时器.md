# 告警送达演练接入定时器

- 日期：2026-10-05
- 关联：`KT-GAP-34`（判据已改并人工验证）、新增 `KT-GAP-38`（自然时机）
- 记录纪律：本文件按 `运维手册.md` §12「先记录 → 改动 → 验收 → 提交」写，
  验收结果见文末「执行结果」。

## 改什么

新增一组 systemd 单元，让**告警送达演练**按排班自然跑一次：

| 文件 | 作用 |
| --- | --- |
| `deploy/systemd/knowtrace-workflow-alert-drill.service` | 跑 `scripts/linux/verify-alert-delivery-drill.sh` |
| `deploy/systemd/knowtrace-workflow-alert-drill.timer` | `Mon 20:30 UTC`（周一，在 `weekly-check` 之后） |
| `scripts/linux/deploy-observability.sh` | 安装这两个单元（与 backup 同处） |

## 为什么

`KT-GAP-34` 修好了「演练根本不验证邮件投递」这个缺陷（原来故障在 `group_wait`
到期前就被撤掉，AM 一封都不发），但**只能人工跑**。没有自然时机意味着：
**没人在场的时候，这条链路不会被验证**。

## 为什么是每周一，而不是每天 / 每月

- **不是每天**：每次演练发 **1–2 封邮件**（`send_resolved: true` 会让一条告警产生
  firing + resolved 两封）。每天 2 封 = 一年 700+ 封演练邮件，**会训练人忽略邮件**
  —— 这正是台账 D11 写下要避免的事（假 WARN 训练人忽略 WARN）。
- **不是每月**：一次演练间隔一个月，「链路断了」最长可以存在 30 天才被发现。
- **每周**是折中：一年约 100 封，可接受；且周一本来就有 `weekly-check`，是同一天的自然节律。

## 影响边界（这是它能每周跑的前提）

演练**只停 `blackbox-exporter`** —— 它是**探针**组件，不承载任何用户流量。
`INC-S3-001`（2026-09-08 同类演练）的记录原文：

> 影响：Prometheus 无法抓取 Blackbox Exporter；**KnowTrace-Workflow 和认证业务保持在线**。

所以「停机」停的是监控探针，不是业务。代价只有：演练期间 12 个 target 少 1 个
（会触发 `KnowTraceMetricsTargetDown` —— 这正是演练要的），以及那 1–2 封邮件。

## 为什么 `Persistent=false`（与本项目其它定时器不同）

其它定时器都是 `Persistent=true`（错过就补跑）。这条**刻意不补**：

- `README.md` 的判据写着「**自然发生** = 由定时器 / CI / 真实事件触发，不是人工
  `systemctl start`」，且台账明确把「安装时的 `Persistent=` 补跑」记为**非自然**
  （见 `KT-GAP-22` 对 `weekly-check` 的处理）。
- 若用 `Persistent=true`，启用当天（今天不是 1 号，但周一的 20:30 尚未到，所以今天
  不会补跑；不过一旦某次错过就会补），第一次运行可能是**补跑** ——
  证据就不干净了。
- 一次演练错过无所谓（它不紧急），所以用 `Persistent=false` 换取「每次运行都是
  排班真实触发」这个干净的判据。

**代价（明说）**：首次自然运行是 **2026-10-12（下周一）20:30 UTC**，
不在这两天的窗口内 —— 所以本文件**不声称** `KT-GAP-34` 靠它关闭。

## 怎么验收（可执行）

```bash
# 1. 单元装载且语法正常
systemctl list-unit-files 'knowtrace-workflow-alert-drill.*' --no-pager
systemctl show -p Result -p Documentation knowtrace-workflow-alert-drill.service

# 2. 装完先 start 一次验证（沿用 ops/systemd/install.sh 的纪律：先 start 再 enable）
systemctl start knowtrace-workflow-alert-drill.service
systemctl show -p Result -p ExecMainStatus knowtrace-workflow-alert-drill.service
journalctl -u knowtrace-workflow-alert-drill.service --since '5 min ago' --no-pager | tail -20

# 3. 投递判据（演练的核心判据，不是「跑完了」）
curl -s localhost:9093/metrics | grep '^alertmanager_notifications_total{integration="email"}'

# 4. 记录落盘
ls -t /var/lib/knowtrace/reports/alert-delivery-drill-*.md | head -1

# 5. 定时器已启用且 NEXT 是下周一
systemctl list-timers 'knowtrace-workflow-alert-drill.timer' --no-pager

# 6. 收尾：targets 回到 12/12、AM 无告警
curl -s localhost:9090/api/v1/targets | jq -r '[.data.activeTargets[]|select(.health=="up")]|length'
curl -s localhost:9093/api/v2/alerts | jq 'length'
```

**负向证伪**（判据不能是瞎的）：

```bash
# 把 unit 里的 ExecStart 指到一个不存在的脚本 → 单元必须 failed
# 且被 KT-GAP-29 新加的 systemd.failed-units 判据抓到
```

## 怎么回滚

```bash
systemctl disable --now knowtrace-workflow-alert-drill.timer
rm -f /etc/systemd/system/knowtrace-workflow-alert-drill.{service,timer}
systemctl daemon-reload
```

单元文件本身在仓库里，删除即回滚；不涉及任何数据或配置。
