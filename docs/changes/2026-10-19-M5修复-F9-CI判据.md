### 4. 本机踩到的两个坑（已修，写在这里免得下次重踩）

1. **`Get-Command bash` 在 Windows 上拿到的是 WSL 存根**（`C:\Windows\system32\bash.exe`）。
   未装发行版时它对任何输入都 exit 1 并打印 WSL 提示 ⇒ **32 个文件全被判语法错**，
   门自己坏了却长得像脚本坏了。修法：候选逐个 `--version` 探针，必须命中 `GNU bash`；
   Windows 上会落到 Git for Windows 的 `D:\Git\bin\bash.exe`。
2. **`$ErrorActionPreference = "Stop"` + 原生命令 stderr**：注入语法错时 PowerShell 把
   `bash -n` 的 stderr 包成 `NativeCommandError` 终止性错误，脚本在打印汇总前就死掉 ——
   只剩 `NativeCommandError`，看不到「受检 N / 失败 M」。修法：`Invoke-NativeCheck`
   局部降级为 `Continue` 并收集输出与退出码，**聚合后统一报**。

### 2. 为什么客户端在**容器内**执行

runner 上预装的 `pg_dump` / `pg_restore` 是 PG 16 一代，对 PG 18 服务端会
`abort: server version mismatch`。service 容器里有**版本完全一致**的客户端，
且这与生产链路同形 —— `backup-all.sh` 的 `pg_dump` / `pg_restore` 本来也是
`docker compose exec <service> …`。

### 5. 本机无法验证的部分（**必须留给 CI**）

| 项 | 原因 |
| --- | --- |
| `positive` / `negative` 的**全部** PG 用例 | **本机没有 Docker**（已实测：`docker` 不在 PATH），起不了 `postgres:18-alpine` service |
| 「PG 18 上追加/截断/翻字节的真实退出码」 | 同上；这正是本 job 存在的理由 |
| `${{ job.services.postgres.id }}` 能否被 `docker exec` 访问 | GitHub Actions service 容器名即容器 id 这一用法**本机无法验证** |
| ubuntu-latest 上的 `python3` 分支 | 本机 `python` 与 `python3` 指向同一个 Windows Store 别名 |
| `~/.pgpass` / 客户端版本匹配 | 客户端在容器内，理论上一致；仍以 CI 为准 |

> ⚠️ **不得**把本节写成「PG 18 行为已确认」。本 job 的价值是**产出**那份真实 stdout，
> 而不是替它下结论。首次 CI 运行后须回来把第 3 节的「期望」列替换为实测值。
