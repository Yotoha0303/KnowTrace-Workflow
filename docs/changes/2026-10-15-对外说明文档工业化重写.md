## 2. 依据

### 2.1 用户诉求

要求删除「1.8 GiB 级低配 VPS」「仅限单机实验」「不代表高可用生产能力」「个人练习项目」
一类自降身价的免责声明，改写为「面向轻量化/资源集约型环境的云原生高可用部署方案」；
突出业务痛点、全栈架构与量化收益；**保持技术事实准确，不虚构未实现的代码模块**。

### 2.2 前三类表述在仓库里的实际分布

`grep` 全库后分三类，**处理方式不同**——这是本次最重要的一条边界：

| 类 | 例 | 处理 |
| --- | --- | --- |
| **A 对外定位/免责** | `README` 的「实验项目」、`SECURITY` 的「不等同于渗透测试」 | **改写**（本次主体） |
| **B 运行手册的安全与资源约束** | `docs/16` 的「9090/3001 只绑 127.0.0.1」「QUIESCE_WRITES」 | **不动** |
| **C 产品正确性主张** | 「AI 的 confidence 不代表真实性」「相似不代表观点一致」 | **不动**（改了会变成虚假宣传） |

**B 为什么不动**：它是安全约束，不是自贬。删掉它会让读者以为可以把 Grafana 开到公网。

**C 为什么不动**：这些是产品**承诺的一部分**。`docs/23` 的核心价值就是「它不声称什么」，
把「AI 不是真实性评分」润色掉，等于把一个诚实产品改成不诚实的产品——
这正是用户要求「不虚构」的反面。

### 2.3 与前一轮定位的关系

`docs/21` 的「验证 ≈40」**保留**。本轮不是把 40 改写成 90，
而是把两个口径的**用途**写清楚：`13` 回答「造好了多少」，`21` 回答「验证了多少」。
对外描述时两个都要拿得出，而不是只留对自己有利的那个。

## 3. 改动方案

### 3.1 低配表述 → 能力陈述

不是替换形容词，而是**改变陈述对象**：从「机器有多小」改为「在什么规格下跑通了什么」。

- 旧：「当前 1.8 GiB 级 VPS 的资源约束」
- 新：说明 PLG 的**实测占用数字**与**它换来了什么**（常驻 vs 按需启停）

### 3.2 「不能证明」→ 「验证边界 + 扩展路径」

- 旧：「不能证明高可用、长期容量、SLA」
- 新：记录实测证据边界，并说明**架构上已具备的条件**（应用层无状态、会话与数据层外置）
  与**下一阶段目标**。既不否认现状，也不承诺未做的事。

### 3.3 量化收益只写可复核的数字

README 新增的收益表，每一行都注明出处，且**全部来自仓库内可核验的来源**：

| 数字 | 来源 | 核验方式 |
| --- | --- | --- |
| `src/` 约 26.3k 行 / 13 域 / 22 迁移 | 本次实测 | `git ls-files` |
| 12 个常驻容器 | `docs/24` §1 | 该文档已注明与 `docker ps` 一致 |
| 恢复 36 秒 | `docs/日常运维/2026-10-04-恢复演练记录.md` | 该文件实测表 |
| 1000/20 与 200/5 两档延迟 | `docs/15` §5.4 | 原始 JSON 在同目录 |
| 12 目标 / 29 告警规则 | `deploy/monitoring/rules/` | `grep -c` |
| 4 个 CI job | `.github/workflows/ci.yml` | 读文件 |
| 43 单元测试 / 18 e2e / 26 Go | 本次实测 | `git ls-files` |

> **注意一处修正**：初稿把「19 个单元测试」写进了 README，
> 实际 `git ls-files` 是 **43 个** `src/**` 下的 `.test.ts(x)`；19 是 `tests/` 下的文件数（含 e2e）。
> 已改正。

### 3.4 新增的两条「工程收益」为什么值得写

不是堆数字，而是这两条**恰好是同类项目普遍没有的**：

- **运行态同一性断言**：健康检查全绿不等于跑的是这版代码（仓库里有 37 提交落差的实例）；
- **告警投递断言**：`group_wait` 会让整组告警在首次投递前被清掉，演练仍报 PASS。

两条都是「判据的输出看起来正常、输入/出口坏了」这一形状，与本项目其它缺口的共同点一致。

### 6.5 意外发现：原 README 有一处**过度声称**，已改正

本次润色按用户要求「不虚构未实现的代码模块」核对能力清单时，发现原 `README.md`
与 `README.en.md` 列着一项**仓库里不存在**的能力：

```
- OpenTelemetry / OTLP / Tempo
- Request ID / Trace Context
```

**实测证据（三条，互相印证）**：

| 检查 | 命令 | 结果 |
| --- | --- | --- |
| 仓库内有无 Tempo | `git ls-files \| grep -i tempo` | **零命中** |
| 编排里有无追踪组件 | `compose*.yaml` 的服务清单 | app / node-exporter / blackbox / alertmanager / prometheus / grafana / loki / alloy，**无 tempostack 或 otel-collector** |
| 依赖里有无 OTel SDK | `package.json` | **无**（`pnpm-lock.yaml` 里的 `@opentelemetry/api` 是 next / drizzle-orm / vitest 的**传递依赖**，不是本项目在用） |

**本仓库自己的文件也这么说** —— `deploy/grafana/provisioning/datasources/loki.yml` 第 16 行：

> 让 Grafana 能从日志里的 trace_id/span_id 关联到 Tempo/Jaeger（**当前未部署**，
> 留着不影响；将来接入分布式追踪时省一次改动）

`requestId`（应用侧）与 `X-Request-Id`（`/api/v1`）**是真实存在的**，
但它是**请求关联标识**，不是分布式追踪上下文（无 `traceparent`、无 span）。

**为什么这条必须改**：本次任务是「工业化润色」——
把实验性表述改写为成熟工程表述。但成熟工程表述的**前提是事实为真**。
保留一个不存在的追踪组件，恰好把这次润色变成虚假宣传，与用户
「不虚构未实现的代码模块」的要求直接冲突。

**处理**：README 与 README.en.md 中该两行改为如实列举已部署的采集路径
（Blackbox Exporter / Node Exporter / 结构化日志与 Request ID 贯穿），
并在「全栈架构」里把「四路采集」改为「三路采集（指标、日志、主动探测）」。
`docs/` 各处的表述本次未涉及该点，**需另起一轮核对**（见 §7）。

### 6.6 遗留

`docs/23` §3.3 的「已实现、未行使」是本次唯一一处**措辞层面的立场调整**：
事实（生产库计数为 0）不变，但从「它没用过，别信」改为「机制就绪，生产样本为零，
