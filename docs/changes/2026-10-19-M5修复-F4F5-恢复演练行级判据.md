# 2026-10-19 · M5 修复 F4 + F5 · 恢复演练的行级判据与 psql 错误停止

> 依据：M5 三跳链阻断项 **F4**（A3）与 **F5**（G-4 / R5）。
> 两项同在 `services/go-user-system/scripts/ops/restore-postgres.ps1`，且互为前提
> （没有 ON_ERROR_STOP 时，断言失败也可能被吞成 0），故一个提交。

## F4 · 只有 `table_count > 0`，没有行级判据

### 缺陷

原断言只有 `table_count -le 0 -or migrationVersion -le 0` 两条下界。
**只含 2 张表的 dump 一样通过**——实测 `pg_dump -t public.users -t public.goose_db_version`
（13 条 TOC，150 334 B）在旧代码下拿到 `TableCount=2`、`MigrationVersion=6`，被判 `passed`。

### 改动

| 项 | 内容 |
| --- | --- |
| 期望表集合 | `goose_db_version, permissions, refresh_tokens, role_permissions, roles, user_roles, users`（来自 migrations 00001–00006） |
| 断言 | **缺任何一张即 throw**，错误里带「缺了哪些 + 实际恢复了哪些」 |
| 迁移版本 | `MAX(version_id) WHERE is_applied` 必须 ≥ 6（goose 版本表本身也在期望集合里） |
| 证据 | 输出与 `restore-drill-*.json` 新增 `tables` 实际表名列表；多余表只 WARN |
| 新迁移 | **新增迁移时必须同步 `$expectedTables` / `$expectedMigrationVersion`**，否则演练会开始报缺表（这是有意的：让漂移显形） |

## F5 · `Invoke-ComposeWithInput` 没有 `ON_ERROR_STOP`

### 缺陷

`psql` **默认遇到 SQL 错误仍以 0 退出**。实测（本机 PG 17.11）：

```
$ echo 'SELECT * FROM no_such_table_xyz;' | psql ... --set=ON_ERROR_STOP=1   → EXIT=3
$ echo 'SELECT * FROM no_such_table_xyz;' | psql ...                        → EXIT=0
```

于是 `DROP DATABASE` / `CREATE DATABASE` / 两条校验查询任何一条失败，都表现为「成功」。

### 改动

`$adminArguments` 与 `$drillArguments` 都追加 `--set=ON_ERROR_STOP=1`。
放在参数里而不是只加在 `-c` 上：这三条调用**都经 stdin 传 SQL**，必须由 psql 在执行期停止。

### 验收

| 用例 | 结果 |
| --- | --- |
| F4 正向：完整 dump | `TableCount=7`，`Tables: goose_db_version, permissions, refresh_tokens, role_permissions, roles, user_roles, users`，`MigrationVersion=6` |
| F4 负向：`-t public.users -t public.goose_db_version` 的 dump | `restored database validation failed: missing tables [permissions, refresh_tokens, role_permissions, roles, user_roles]; restored tables [goose_db_version, users]` |
| F5-①：真实 psql 带/不带 `ON_ERROR_STOP` | `3` / `0` |
| F5-②：桩在 psql 层注入「SQL 出错」，跑**整条脚本** | 新脚本在**第一条失败调用处**抛出真实错误（`... --set=ON_ERROR_STOP=1 failed: ERROR: relation "no_such_table_xyz" does not exist`）；旧脚本**吞掉该错误继续执行**，随后在别处以误导性错误收场（`relation "goose_db_version" already exists`，即 DROP 根本没生效却没人知道） |

## 本机验证方式与边界（如实）

- 本机**无 Docker**。脚本要求的 `docker compose cp/exec` 用一个本机替身
  （`docker-stub.ps1`，把 `compose exec/cp` 映射到本机 PG 17.11 的 5433 集群）跑通；
  `docker cp` / `docker exec` 两层的**真实行为未验证**。
- 被测判据（表集合 / 迁移版本 / `ON_ERROR_STOP`）全部在**本机真实 psql、真实 pg_restore**
  上执行，只有「容器边界」被替身替代。
- CI 是 PG 18，本机 17.11；`information_schema.tables` 与 goose 表行为两版一致，
  但最终仍以 CI / 真机为准。

## 回滚

`git revert <本提交>`。注意：本次改动会让**旧备份**（缺表或迁移版本 < 6）的演练开始失败——
这是有意的行为变化，不是回归。
