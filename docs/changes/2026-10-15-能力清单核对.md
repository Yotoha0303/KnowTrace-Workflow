## 2. 查出的问题

### 2.1 GHCR —— 过度声称（与 Tempo 同一形状）

`README.md:96` 与 `README.en.md:91` 的技术栈列着：

```
- GitHub Actions / GHCR
```

**实测**：

| 检查 | 命令 | 结果 |
| --- | --- | --- |
| 根仓库 CI 有无镜像推送 | `git grep -n "ghcr.io" -- .github/` | **零命中** |
| CI 有无 build-push 动作 | 读 `ci.yml` 全文 | 4 个 job 全是 check/test/build，**无 registry 登录、无 push** |
| 部署链是否用注册表 | 读 `scripts/linux/deploy-observability.sh` | 在目标机 `docker build`，不经注册表 |
| `package.json` 有无相关依赖 | `git grep -i "docker\|registry"` | 无 |

**为什么全库 `grep ghcr` 有 14 处命中却仍是过度声称**：
那些命中**全部在 `services/go-user-system/` 子树内**——那是 `git subtree` 引入的
上游仓库副本，自带 `release.yml`、`k8s/*.yaml`、Kubernetes 清单与 GHCR 发布流程。

但：

1. **GitHub 只执行根目录的 `.github/workflows/`**，子树的 `release.yml` 在本仓库**不会运行**；
2. 本部署**不使用**它的 K8s 清单与 GHCR 镜像（`compose.yaml` 用的是本地构建的
   `knowtrace-workflow-auth:dev`，见 `docs/24` 第 1 节的部署拓扑）。

**处理**：改为 `GitHub Actions（4 个门禁 job；镜像在部署侧构建，不经注册表推送）`。

> **与 Tempo 的相同点**：都是「在别处见过这个名字，就写进了自己的能力清单」。
> **不同点**：Tempo 是全库零命中（纯虚构）；GHCR 是**子树里真有、本部署不用**
> ——这类更隐蔽，因为 `grep` 会给出一堆看起来支持它的结果。
