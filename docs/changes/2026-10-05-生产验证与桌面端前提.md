## 2. 依据

### 2.1 D1：CI 的 8 个 skipped 是**空库缺种子**，不是缺凭据

`tests/e2e/*.spec.ts` 的 `test.skip` 条件写的是 `AUTH_E2E_USERNAME` 一类环境变量，
**读起来像「CI 没有凭据」**。实测读代码 + 读 `compose.yaml` 后发现更根本的一层：

- 那 8 个 spec 确需一个能登录的账号；
- CI 的 e2e job **已经起了 postgres 服务**，只是没建账号；
- `compose.yaml` 里**已有**现成种子机制：`auth-bootstrap` 服务跑
  `bootstrap-admin-if-needed`，账号名取自 `KNOWTRACE_ADMIN_USERNAME`。

**危害**：十环 03 环的「CI 全 success」当前并不等于「登录链路在门内验过」——
这比 `KT-GAP-33` 修掉的 `lint` 假门更宽。

**边界**：本 D1 **不承诺**把 8 个全部变成通过。实测读完后分两类：

| spec | 需要什么 | D1 能否覆盖 |
| --- | --- | --- |
| `auth-flow` / `account-center` / `mobile-api` / `ai-runs-api` | 1 个账号（**不要求 admin**） | ✅ |
| `reliable-release` | 额外必须 `RELIABLE_RELEASE_E2E=true`（自建 fixture） | ❌ 不在 D1 范围 |
| `iteration-fixes` | 额外需要 CC-Switch 代理（`AI_E2E_CCSWITCH_BASE_URL`） | ❌ 环境依赖 |
| `content-ownership` | 需要**第二个**账号且两者角色可区分 | ⚠️ 见下 |
| `account-management` | 需要注册**开启** + 可丢弃账号 | ❌ 现策略是关注册 |

**为什么 `content-ownership` 需要「角色可区分」**：它验的是
「管理员内容对成员只读共享、成员内容保持私有」。
而应用侧的角色来自 go-user-system——`admin` 角色是 `bootstrap-admin` 赋的，
**普通注册用户只有 `user` 角色**，不会是 admin。所以「两个账号」本身不够，
第二个账号必须在应用侧表现为**非管理员**。

D1 的做法：CI 里播种 **1 个**账号（= auth-bootstrap 的 admin），
把它同时喂给 `AUTH_E2E_USERNAME`（4 个 spec 用）与 `AUTH_E2E_ADMIN_USERNAME`。
`content-ownership` 仍跳过——但**跳过原因从此是显式的一条 TODO，而不是「CI 没凭据」这种含糊说法**。

### 2.2 D3：桌面前提「Tauri 套现有 Web 产物」未经验证

`docs/adr/0016` 与 `docs/18` §M5 都写「Tauri 套现有 Web 构建产物」。
但 `next.config.ts` 是 `output: "standalone"` —— 产物是**一个 Node 服务**，不是静态目录。
Tauri 的 `frontendDist` 吃静态目录。两者不是一回事。

**这是对 ADR-0016 的澄清，不是推翻**：该 ADR 的决策（Expo 原生 + 端上转写 + token 模式）
不变；变的是「桌面端怎么落地」这一条从**断言**降级为**待决**。

## 6. 执行结果

### 6.1 第一次 CI 运行（run `37307352954`）：**门是通的，spec 有一处既有漂移**

| job / step | 结果 |
| --- | --- |
| `quality` / `go` / `auth-frontend` | ✅ pass |
| e2e › 无认证（18 spec） | ✅ **pass**（主运行语义未变，D1 的最大风险排除） |
| e2e › 认证基础设施（mysql / 迁移 / 播种 / 限流放宽 / 起服务 / 查库断言） | ✅ **六步全 success** |
| e2e › **有认证（4 spec）** | ❌ 3 passed / 1 failed |

**失败的只有 `auth-flow` 一处断言**：

```
Error: strict mode violation: getByText('@CiAdmin') resolved to 2 elements:
  1) <small>@CiAdmin · 账户中心</small>   (details 内的嵌套元素)
  2) <small>@CiAdmin · 账户中心</small>   (外层 link)
```

**这是既有脆弱点，且形状与 `KT-GAP-06` 那次完全一致**（当时是
`getByLabel("原文")` 命中 2 个元素）。这条 spec 此前**一直 skipped**
（CI 从没提供账号），所以从没暴露。

修法照抄本仓库 `account-center.spec.ts` 已在用的写法 —— 按 role 定位（唯一）：
`page.getByRole("link", { name: new RegExp(`@${username}.*账户中心`) })`。

> **这条失败本身就是 D1 价值的证据**：门一开，立刻抓出一处此前无人看见的漂移。
> 另外三条（`account-center` / `mobile-api` / `ai-runs-api`）**首次真实通过**。
