# 2026-10-19 · M5 修复 F11 · CI 判据 N3 改为语义正确（真实恢复，而非全量读取）

> 依据：CI run `39258948661`（PG 18）的 `Backup dump criteria on PostgreSQL 18` job：
>
> ```
> === 负向 3：数据区翻 1 字节 -> 全量 --file=/dev/null 必须失败 ===
> MUTATION mode=flip-fraction src_size=80110 offset=72099 old=0x20 new=0xdf
> FAIL  N3/full --file=/dev/null rejects data flip    expected=1    actual=0
> DOORS N3-data-flip  list=0 data_only=0 full=0 tail=0
> ```
>
> 该 FAIL **不是** CI 的问题，而是**判据的期望值错了**：PG 18 上全量
> `pg_restore --file=/dev/null` 本来就不报数据区损坏。**不**下调期望值让它变绿
> （那是降低判据），而是把期望值换成语义正确的那一条：**真实恢复验证必须失败**。

---

## 1. 改了什么（提交 2：`tests/ci/pg-dump-criteria/run-criteria.sh`）

| 项 | 变更 |
| --- | --- |
| 新增 `real_restore_verify_rc <dump> <log名>` | 「建库 → `pg_restore --exit-on-error` → 逐表计数 → 与正向阶段的 `main-counts.tsv` 逐字节 `cmp` → 删库」；返回 0 通过 / 非 0 不通过。与 `backup-all.sh` 的 `verify_dump_by_real_restore` 同一口径 |
| N3 判据名 | `N3/full --file=/dev/null rejects data flip` → **`N3/real restore verification rejects data flip`** |
| N3 期望值 | 由「全量读取 exit=1」改为「**真实恢复验证 exit=1**」 |
| `full` | 降为**观察项**：仍出现在 `DOORS … full=` 行里，**不计失败** |
| 日志说明 | 新增 `OBS N3-note/reason`：写明「PG 18 上全量 `--file=/dev/null` 不报数据区损坏，故必须靠真实恢复」，并打印真实恢复日志末尾 10 行 |
| 正向 | **已确认存在，无需新增**：`O4a/main real restore exit`=0、`O4b/main counts cmp`=0（`positive` 段，既有用例 O4a–O4e） |

> 为什么新增的是「恢复验证」而不是把 `full` 从断言里删掉：删掉只是「不测了」，
> 而换成语义正确的那条判据仍然**拦得住**这份坏归档 —— 且与生产备份端同一口径。

**关键预期**：`N3/real restore verification rejects data flip expected=1 actual=1`。
其中 `actual=1` 可能来自两处（都是「拦住」）：恢复本身非零退出，或恢复成功但计数与
`main-counts.tsv` 不一致（`real_restore_verify_rc` 两条路径都返回 1）。
`DOORS … full=` 的取值**不参与判定**；若仍为 0，恰恰复现了本次修复的动机。

`Positive` 步骤（已存在，预期不变）：

```
PASS  O4a/main  real restore exit                          expected=0      actual=0
PASS  O4b/main  counts cmp (backup vs restored)            expected=0      actual=0
PASS  O4d/auth  real restore exit                          expected=0      actual=0
PASS  O4e/auth  counts cmp (backup vs restored)            expected=0      actual=0
```
