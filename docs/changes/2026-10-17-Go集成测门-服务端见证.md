## 2. G1-R1 的处置与理由

### 2.1 先回答「能否在进程内把伪造成本抬回来」：**不能**

qa 已实测否掉两条，本轮复核同意：

- 「要求前缀是 `mysql.go:`」——`-json` 按**打印者**归属；去掉 `t.Helper()` 能改前缀，
  而 `fmt.Println("mysql.go:164: REAL_DB_FINGERPRINT …")` 不经 testing，可手写任意前缀。
- 「只允许 `t.Log`」——同上，措辞不构成防线。

根因是**信息源在同一进程内**：测试进程既是「被验者」又是「证人」。
只要证据由它自己产出，它与证据之间就没有任何强制力。

### 2.2 选定的修法：**服务端作证**（已实施）

`scripts/check-go-integration-server-witness.mjs`：测试前后各一步，用 root 读
MySQL 自己的 `mysql.general_log`，统计——

> 「以**测试账户**（`go_user_system`）连上**测试库**（`go_user_system_test`）、
> 并在该连接上执行过 `testutil.OpenMySQL` 的真实启动序列
> （`GET_LOCK(` / `DATABASE()` / `VERSION()`）的**不同线程（连接）数**」，
> 要求 **>= 8**。

为什么测试二进制伪造不了：

| 事实 | 证据 |
| --- | --- |
| 测试账户**读不到**服务端统计 | 本机实测：`SELECT … FROM performance_schema.events_statements_summary_by_digest` → **ERROR 1142** |
| 只有 root 能写 `general_log` | 服务端权限模型；测试进程只有 app 账户 |
| root 连接**不满足过滤条件** | 门按 `user_host LIKE '[<测试账户>]%'` 过滤；root 的连接前缀是 `root[` |
| 每条真实连接**必留下**启动序列 | fake driver 根本不建服务端连接；OpenMySQL 的真实分支必然执行 GET_LOCK + DATABASE() + VERSION() |

### 2.3 可行性评估（qa 要求先评估再决定，此处给结论）

| 维度 | 评估 |
| --- | --- |
| CI 改动 | **+2 步**（prepare / assert），均为 `working-directory: ${{ github.workspace }}`；root 口令走 `MYSQL_PWD`（与本 job 已有 e2e 查库步同形） |
| 成本 | **< 1 小时**：脚本约 260 行、两条 SQL、无新依赖（只需 `mysql` CLI，runner 自带；本机实测已在 PATH） |
| MySQL 版本依赖 | 依赖 `mysql.general_log` 表（5.7+ 结构）。本机在 **8.4.8** 实测；CI 是 **8.0**（与既有 `mysql:8.0` service 同批） |
| 权限依赖 | 需 root（或 `SYSTEM_VARIABLES_ADMIN` + 对 `mysql.general_log` 的 SELECT）。CI 的 service 已提供 root 口令 |
| 会不会误伤 | prepare 步**回读实际值**（`log_output` 含 TABLE 且 `general_log=1`），不信 `SET` 成功；读不到即 **fail-closed（exit 1）**，与「读到了但不够」分开报 |
| 已知边界 | 证明「有过 8 条连接」，**不证明**「是哪 8 条 Go 用例连的」——服务端没有测试名 |
| 覆盖缺口 | 不防「删掉 CI 里的本步」——任何 CI 门共有的信任边界，靠 diff 评审 |

⇒ **判断：应该做，且已做。** 它把「伪造」从「一行日志」抬高到「取得 root 口令
或改 CI 文件」——两者都越过了测试进程的边界，是**可评审的**动作。

### 2.4 无论实施与否都做：三处降格措辞

| 位置 | 改成 |
| --- | --- |
| `scripts/check-go-integration-gate.mjs` 文件头 + 判据 ① + 通过输出 | 「**跳线（tripwire），不是证据（proof）**；防误配 / 疏忽，不防蓄意伪造；**攻击成本 = 一行日志**；**不得**引用为『集成测真的连过库』的证据」 |
| `.github/workflows/ci.yml` job 头 + 断言步注释 | 同上；并写明「真证据在第二道门」 |
| 本文件 | 同 §1 / §2 |

**通过时也打印这句**（`check-go-integration-gate.mjs` 的绿色分支）：
绿色单独出现时，读的人最容易把它当成证据——所以降格必须跟着绿色一起出现。

## 4. 执行结果（**本机实测**，2026-10-17）

环境：本机隔离 MySQL **8.4.8**（`--initialize-insecure`，端口 33307，数据目录在仓库外，
验证后销毁）；Go 1.25.13；Node 22。

### 4.1 正向

```
$ node scripts/check-go-integration-server-witness.mjs --prepare --database go_user_system_test --user go_user_system --port 33307
服务端见证日志已就绪（log_output=TABLE general_log=1），表已清空。              EXIT=0

$ go test ./... -count=1 -json > pos2.jsonl            # TEST_DATABASE_DSN 指向 33307
GO_EXIT=0

$ node scripts/check-go-integration-gate.mjs pos2.jsonl
门通过：带自有指纹的顶层集成用例 8 个 >= 下界 8 个，无 SKIP、无失败。
⚠️ 本门是跳线，不是证据：…「集成测真的连过库」以 server-witness 门（服务端 general_log）为准。   EXIT=0

$ node scripts/check-go-integration-server-witness.mjs --database go_user_system_test --user go_user_system --port 33307 --min-connections 8
服务端看到：以 go_user_system 连上 go_user_system_test、并执行过 OpenMySQL 启动序列的连接 8 条
（VERSION() 16 次 / DATABASE() 16 次 / GET_LOCK 8 次）。
```

重复正向 **3 次**（每次 12–13s）：`GO_EXIT=0 / GATE_EXIT=0`，三次全绿。

### 4.2 负向（真跑，逐条对应 finding）

| 用例 | 注入 | `go test` | 第一道门（日志门） | 第二道门（服务端） |
| --- | --- | --- | --- | --- |
| **G1-b（回归）** | `-skip=TestUserDAOIntegrationHonorsCanceledContext` | 0 | `7 < 8` · **原因 (c)** · **EXIT 1** | 服务端 **7 条** < 8 · **EXIT 1** |
| **G1-c（回归）** | 改名 `TestUserDAORenameProbe` + 首行 `t.Skip` | 0 | `7 < 8` · **原因 (c)** · **EXIT 1** | 服务端 **7 条** < 8 · **EXIT 1** |
| **G5（回归）** | 某集成用例 `t.Fatalf` | 1 | `有用例执行失败 1 个（…**不是**编译错误）`，**无**「构建失败」字样 · **EXIT 1** | — |
| **G5-b（回归）** | 真编译错误（未定义符号） | 1 | `构建失败 1 个`（去重后**只 1 条**）+ `5 < 8` · **EXIT 1** | — |
| **G1-R3 (a)** | 真连接后 `t.Fatalf`（模拟偶发失败） | 1 | `7 个，低于下界` · **原因 (a)：…确实跑过…但没有通过** · 点名该用例 · **EXIT 1** | — |
| **F1（qa 的形态）** | fake 用例加一行 `t.Log("REAL_DB_FINGERPRINT …")` + `-skip` 一条真用例 | 0 | **`8 >= 8` · EXIT 0（伪造成功）** | 服务端 **7 条** < 8 · **EXIT 1** |
| **F2 变体（零连库）** | 8 条假用例各打一行指纹：`go test ./internal/testutil/ -count=1 -json`，DSN **置空**（隔离到包级，避免真用例把计数顶回来） | 0 | `8 >= 8` · **EXIT 0（全绿，全程无任何连接）** | 服务端 **0 条** · **EXIT 1** |
| 无 DSN（回归） | 清空 `TEST_DATABASE_DSN` | 0 | 指纹缺失 + 8 条 SKIP + `0 < 8` · **原因 (d)：有 8 条含 Integration 的用例被跳过** · **EXIT 1** | — |

**F1/F2 是本轮最重要的两行**：它们证明（1）第一道门的伪造是**真的、可复现的**；
（2）第二道门**独立地**把它抓住了。这正是「证据」与「跳线」分家的意义。

| `go test ./... -count=1`（**不带** DSN） | `TEST_NO_DSN_EXIT=0` |
| `gofmt -l internal cmd pkg router config` | 无输出 |
| `go vet ./...` | `VET_EXIT=0` |

### 4.4 本轮咬到的两个真缺陷（都修了）

1. **分诊把「DSN 没配」误报成「用例根本没跑起来 / 有人删了用例」**：实测 8 条集成 SKIP 时，
   原先的分诊既不进 (a)（没有 fail 事件）也不进 (b)（没有孤儿指纹），落到 (c)；
   而 (c) 的措辞会把人引向「有人删了用例」——**方向对，结论错**。
   修法：新增 **(d)** —— 孤儿指纹为零、**但有**含 Integration 的 SKIP 事件 ⇒
   「有 N 条集成用例被跳过，首要解释是 DSN 没配」。
   **最终四分实测**：DSN 空 ⇒ (d) 点名 8 条；`-skip` ⇒ (c)；改名+skip ⇒ (c)（no SKIP 事件）；
   真连接后失败 ⇒ (a) 点名该用例。**四种不再同形。**
   > ⚠️ (c) 里「误删」与「故意跳过」仍然同形——这是**本门的结构极限**（日志里没有信息可区分），
   > 不是措辞问题；区分它们的是服务端见证门（真实连接数掉到 8 以下）。
2. **F2 无法在 `./...` 下复现**：8 条真用例会同时连库，服务端计数顶到 8。
   改为 `go test ./internal/testutil/` 做**包级隔离**，其余包里的真实连接不会被触发——
   「零连库」这个性质才**可复现**。

## 6. 未验证项（如实）

- **真 CI 上的行为**：本机无 Docker，`services.mysql` 与 `if: always()` 的实际语义**未在 CI 复跑**；
  本轮用的是本机 MySQL **8.4.8**，CI 是 **8.0**（`general_log` 表结构在 8.0 上未实测）。
- **`--prepare` 在 CI runner 上的权限**：service 容器的 root 口令已有（`knowtrace-root`），
  但「`mysql` CLI 在 ubuntu-latest 上可用」只有 e2e job 的**先例**（同一条查库命令），本 job 上未跑过。
- **多包并行与 `general_log` 的关系**：`go test ./...` 并行跑多包，连接数会叠加；
  本轮实测恰好等于 8（每条用例 1 条），但**未构造**「某条用例开 2 条连接」的场景。
- **服务端门在「`go test` 已红」时的输出**：已按 `if: always()` + fail-closed 设计并本机验证脚本行为，
  但**整条 job 的失败传播**（上一步红、本步也红）未在 CI 上观察。
- **`build-fail` 的 ImportPath 形态**：本机实测两种（`pkg [pkg.test]` 与 `pkg`），
  注释已按两种写；未在 CI runner 上核对。
