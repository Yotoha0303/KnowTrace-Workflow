# 2026-10-19 · M5 修复 F2 + F3 · dump 完整性判据与「备份的是哪个库」

> 依据：M5 三跳链阻断项 **F2**（G-3 / A5 / B1-5 / B1-6）与 **F3**（A1 / A2）。
> 两项同在 `scripts/linux/backup-all.sh` 与 `scripts/linux/verify-restore.sh` 的同一段逻辑里，
> 且共用 metadata 的新字段，故一个提交。

## F2 · dump 完整性只覆盖了「尾部截断」

### 1. 实测（本机 PG 17.11，非 Docker；160 KB / 45 TOC 条目的认证库 dump）

| 注入 | `--list` | `--data-only --file=/dev/null` | 全量 `pg_restore --file=/dev/null` | 真实恢复 |
| --- | --- | --- | --- | --- |
| 无（基线） | 0 | 0 | 0 | 0，7 表 / 3003 行 |
| 尾部追加 128 B **随机** | **0** | **0** | **0** | **0，且逐表计数与源库一致** |
| 尾部追加 128 B **全 0** | 0 | 0 | 0 | 0，计数一致 |
| 数据区翻 1 字节（offset 20000 / 60000 / 100000 / 150000） | 0 | **1** | **1** | 1 |
| TOC 区翻 1 字节（offset 2000 / 3000 / 5000 / 6000 / 8000） | 0 | **0** | **0** | **1**（SQL 出现非法 UTF-8） |
| TOC 头部镜像字段翻 1 字节（offset 200 / 600） | 0 | 0 | 0 | 0，计数一致 |
| 截断 1% / 截断 128 B | 0 | 1 | 1 | 1 |

**结论（如实）**：
- 任何「把 dump 喂给 pg_restore」的检查都**看不见尾部追加** —— 包括全量
  `pg_restore --file=/dev/null`。原因：最后一条 TOC 记录记的 `size` 与实际读取长度失配时，
  pg_restore 按**名字长度**调 `archive_read`，把追加字节当成该记录载荷读走。
  本机 PG 17.11 上产物碰巧不变；权威验证方在 PG 18 上观察到「真实恢复 0、数据却只剩 2 张表」
  —— 即**版本相关、会静默损坏**。故正确做法是在**归档层**判结构，不指望 pg_restore 报错。
- `--data-only` **抓不到 TOC 区与文件尾**；文件尾只能靠**结构判据**。
- TOC 头部镜像字段（`int` / `off`）翻转在 PG 17.11 上**不影响产物**，属于不影响恢复的位翻转。

### 2. 改动

| 位置 | 判据 | 抓住什么 | 抓不到什么 |
| --- | --- | --- | --- |
| `backup-all.sh`（两库） | 已有 `--list` | 头部截断 / 非 dump | 尾部 |
| `backup-all.sh`（两库） | 已有 / 新增 `--data-only --file=/dev/null` | 尾部截断、数据块损坏 | 文件尾、TOC |
| `backup-all.sh`（两库） | **新增** 全量 `pg_restore --file=/dev/null`（不连库） | 数据区、TOC 区损坏、截断 | 尾部追加、TOC 头部镜像字段 |
| `backup-all.sh`（两库） | **新增** `require_custom_archive_tail`：末 5 字节必须是 5 个 NUL | **尾部追加** | — |
| `backup-all.sh` metadata | 写 `*_dump_bytes` / `*_dump_toc_entries` | 归档被换成同样大小的其他 dump | 内部位翻转 |
| `verify-restore.sh` | 字节数与 metadata 比对（SHA256SUMS 已覆盖内容） | 文件被替换 | — |
| `verify-restore.sh` | TOC 条目数与 metadata 比对 | 换成条目数不同的 dump | — |
| `verify-restore.sh` | 认证库再加一道全量 `pg_restore --file=/dev/null` | 与备份端同口径 | 同上 |

**末 5 字节为 NUL 的依据（实测）**：custom 归档的 5 字节 footer = 最后一条 TOC 的偏移 + NUL 结尾；
归档里不可能有「最后一条记录就贴着文件末尾」，故这 4 字节恒为 0。
样本：1.6 KB / 14.9 KB / 160 KB / 376 KB（`-Z0`）四种 dump，末 8 字节均为 `xx xx xx xx 00 00 00 00`。

### 3. 验收（可执行）

`backup-all.sh` 的桩环境（本机 PG 17.11 + `harness/docker` 把 `compose exec` 映射到本地集群）：

| 用例 | 结果 |
| --- | --- |
| 正向（无注入） | `SCRIPT_EXIT=0`，落 1 个归档 |
| 尾部追加 128 B 随机字节 | `SCRIPT_EXIT=1`，`ERROR: 认证库 dump 末尾不是 5 个 NUL`，归档数量 0 |
| 数据区翻 1 字节（offset 60000） | `SCRIPT_EXIT=1`，`ERROR: 认证库 dump 数据块不完整（全量读取失败）`，归档数量 0 |
| 尾部追加 128 B **全 0** | `SCRIPT_EXIT=0`，落 1 个归档；真实恢复 exit 0 且**逐表计数与源库完全一致**（7 表 / 3003 行） ⇒ 该形态不破坏产物，放行是正确行为 |
| TOC 头部镜像字段翻转（offset 200） | `SCRIPT_EXIT=0`（见上表的边界，恢复产物一致） |

## F3 · `verify-restore.sh` 无法识别「备份的是哪个库」

### 1. 实测（旧判据为何全绿）

把 `postgres.dump` 与 `auth-postgres.dump` **互换**、`*-counts.tsv` 一并互换、metadata 的
字节数 / TOC 条目数也改成互换后的值、**重算 SHA256SUMS** 后：

```
SHA256SUMS: 全绿（自洽）
旧判据: postgres.dump 恢复 + 计数 cmp → 全绿（**看不见调包**）
旧判据: auth-postgres.dump 恢复 + 计数 cmp → 全绿（**看不见调包**）
```

旧判据的每一环都「自洽」：SHA 与新内容自洽、每条 dump 各自能恢复、清单与恢复库 cmp 相等。
**自洽不等于正确。**

### 2. 改动

- `backup-all.sh`：metadata 新增 `postgres_db=` / `auth_postgres_db=`，值来自
  **`psql` 在源库内 `SELECT current_database()`**（实测值，不是字面量）。
  备份端同时断言两库名**不同**，否则恢复端无从区分。
- `verify-restore.sh`：
  1. metadata 必须含两库名，且**互不相同**、且分别等于 `knowtrace_workflow` / `$AUTH_POSTGRES_DB`；
  2. 每条 dump 的 `pg_restore --list` 头部 `;     dbname:` 必须等于 metadata 里对应的库名；
     **TOC 头其实带库名**（实测 PG 17.11），它是与 metadata 独立的一路来源，故两者交叉核对；
  3. dump 字节数 / TOC 条目数与 metadata 一致。

> ⚠️ 任务书里写「`pg_restore --list` 的 TOC 里取不到库名，所以别指望它」——**实测不成立**：
> `--list` 的输出头确实带 `;     dbname: <库名>`。它是 dump 的自述、可被单独伪造，
> 所以**不能只靠它**，但作为与 metadata 交叉核对的第二路来源是有价值的。

### 3. 验收（可执行）

| 用例 | 结果 |
| --- | --- |
| 正向（未调包） | `PASS: 库身份断言全部通过` |
| 互换 + 重算 SHA256SUMS | `DIE: postgres.dump 字节数与 metadata 不符`（README 口径的第一步就拦住） |
| 互换 + counts 一起换 + metadata 字节数/TOC 也改 + 重算 SHA256SUMS | `DIE: postgres.dump 实际来自库 go_user_system，但 metadata 声明主应用库是 knowtrace_workflow —— 两份 dump 被互换/调包` |

## 边界（本次**未**覆盖，不得表述为「完整性已闭环」）

1. **TOC 头部镜像字段翻转**（offset 200 / 600 一类的位翻转）：PG 17.11 上产物一致，未拦。
2. **尾部追加全 0 字节**：结构判据看不见；实测该形态不破坏恢复产物（计数一致），故不视为缺陷。
3. **本机无 Docker**：`verify-restore.sh` 本身未在本机执行（它要 `docker run`）。
   本机验证的方式是把它新增的断言**逐行照搬**到本机文件上跑（`harness/f3-swap.sh`）；
   `docker cp` / `docker exec` 那两层未执行。
4. **CI 是 PG 18、本机是 17.11**：authority 观察到的「append 后真实恢复 0 且表数变化」在本机未复现，
   上面的判据**不依赖**该差异；但 PG 18 上的最终行为仍应以 CI / 真机为准。

## 回滚

`git revert <本提交>`；metadata 新字段对旧归档**缺失即 die**（verify-restore 拒绝演练），
故回滚必须**与恢复端同一提交一起回滚**。
