## 1. 先纠正三个预期（10 分钟）

团队接手一个项目，第一件事是校准预期。KnowTrace-Workflow 有三个数字容易被误读。

### 1.1 「90 分」不等于「快完成了」

`docs/13-product-completion-audit.md` 给出 **建成完成度 90/100**（【依据：文件】）。
但这个分数衡量的是「代码写完了吗」，不是「它起作用了吗」。

按「**被真实验证过**」重新计分，`docs/21-path-to-100-percent.md` 的估算是 **约 40 分**。
生产库的原始数据是【实测】：4 条记录、1 个账号、19 次 AI 调用（其中真实模型 16 次只成功 2 次）。

> **建成 90、验证 40** 才是真实进度。差距不在「再写几个功能」，在「让已经写完的东西被跑通」。

### 1.2 线上跑的**可能不是**仓库里的代码

`docs/19-product-defect-inventory.md` 的 **D-06**（生态观察 F-01 确认）：线上镜像停在 2026-09-08，
部署目录已到 2026-09-29，**差 37 个提交**。

【实测】那 37 个提交里 `src/` 改动为 0，所以当时功能等价——**但这不是安慰**。
定级看的是「必然触发 + 零发现」：下一次有人改 `src/` 并部署时，触发是必然的，
而 **4 层健康检查 + 12 个抓取目标 + 20+ 条告警规则 + 全绿巡检，没有一层验证「跑的是不是这一版代码」**。

**团队要建立的第一条机制**：部署脚本最后必须断言 `运行态 revision == 目标 revision`。
`CONTRIBUTING.md` 的「部署验证」一节已经把权威写法和这个断言的来龙去脉写清楚了【依据：文件】。

### 1.3 产品最独特的部分**一次都没跑过**

```
claims                        1   → withdrawn（已撤回）
claim_evidence                1
evidence_source_checks        0   ← 来源检查从未触发
claim_reviews                 0   ← 人工结论从未产生
independent_claim_reviews     0   ← 独立复核从未发生
knowledge_releases            0   ← 从未发布
```

这是【实测】的生产库状态。**主张—证据—独立复核—可靠发布**是 KnowTrace-Workflow 区别于普通笔记工具的全部，
它既没被证明有用，也没被证明无用——**它只是没被跑过**。

而且它有一个硬前提：ADR-0015 要求独立复核者必须是**不同的登录账号**，而认证库里**只有 1 个账号**。
**这条链路在当前账号结构下无法行使。**

## 2. 接手第一周：不要加功能

`docs/21` 已经把顺序定好了，团队照做即可（【依据：文件】）：

| 阶段 | 做什么 | 退出标准 |
| --- | --- | --- |
| **0（1–2 周）** | 只清「一用就撞」的东西，**不建任何新功能** | 连续 7 天每天记录一条，**全程不撞错误页** |
| **1（2–4 周）** | 建第二个账号，用真实内容走完整条链 | `knowledge_releases ≥ 1` 且 `independent_claim_reviews ≥ 1` |
| **2** | 按阶段 1 的结论决定：链路有用→补移动端；太重→做减法 | — |

> [!IMPORTANT]
> **不要跳过阶段 0。** 在「保存会随机报错」的系统上做任何验证，失败的归因都会是错的。

阶段 0 的具体条目（D-03 的 8 项、两条回归测试、连续 10 次真实 AI 调用成功率 ≥ 80%、
图片上传真实验证）见 `docs/21` 第 2 节。**截至 2026-10-01，D-03 的核心两项已修**【依据：文件】，
其余仍待做。

## 3. 团队要补的三个机制（现状是缺的）

KnowTrace-Workflow 是**单人工程**，它的文档体系完整，但**协作机制**是按一个人设计的。

### 3.1 有 ADR，没有 RFC

`docs/adr/` 有 16 条决策记录，质量很高（含 superseded 关系）。但 **16 条全部出自一个作者、一个时间窗**。
没有 RFC 流程意味着：**没有「谁来评审」的位置**。

团队接手后要补：**谁有权批准 ADR、变更走什么评审**。

### 3.2 `docs/changes/` 是好机制，但它按「单人先写后做」设计

`docs/changes/README.md` 规定了「**变动前**先写：改什么、为什么、验收、回滚」【依据：文件】。
这是这个项目**最好的协作基础设施**，它的存在是为了补上 D-03 暴露的信息传导断裂。

但它假设「一个人既写记录又执行」。团队化后要补：
**是谁审的、几人共识、谁执行、谁验收**——现在四者是同一个人。

### 3.3 AI 助手指令只有 AI 栈，缺项目纪律

`KnowTrace-Workflow/CLAUDE.md` 只有一行 `@AGENTS.md`，内容全在 `AGENTS.md`。后者除
`next dev` 自动生成的 Next.js 提示块外，现已补入一节**本项目的 AI 工具与模型**
（客户端：ChatGPT Codex、经 CC-Switch 代理的 Claude Code；模型：ChatGPT、DeepSeek；
并写明 `claude-*` 是 CC-Switch 的入站协议别名，不代表使用 Claude 模型）【依据：文件】。

但团队若用 AI 辅助开发，**这份指令仍缺项目特定内容**：本项目的证据纪律、`AppError` 约定、
Server Action 与 Application Service 的边界（`docs/06` 第 5 节的依赖方向禁令）都该进这里。
工作区根目录另有一份 `AGENTS.md` 是**未填写的模板**（占位符「Brief 1-2 sentence description…」
「Node 20+, Python 3.11」「`services/`」与实际不符），需要一并处理。

## 4. 团队最容易踩的坑

### 4.1 部署链路的「看起来成功了」

这是本仓库最反复出现的一类故障。已知至少六个坑，**全部表现为「部署看起来成功了」**：

| 坑 | 表现 |
| --- | --- |
| 分支核对缺失 | 部署的不是你以为的分支 |
| 未跟踪文件挡住 `git pull` | pull 失败但脚本继续 |
| `cp -r` 不改权限 | 属主错配，图片上传静默失败（D-01，曾静默 42 次） |
| 部署命令漏文件 | 只 restart 旧镜像，却报成功 |
| 绑定挂载盖掉镜像属主 | 容器内写不进挂载目录 |
| 不带 `--build-app` | 走 `--no-build`，重启旧镜像 |

**权威写法只有一处**：`scripts/linux/deploy-observability.sh`（`CONTRIBUTING.md` 已注明是唯一权威）。
**团队纪律：任何人不得手写 `docker compose up -d --build`。**

### 4.2 文档与实现不一致时，先问哪个是错的

`docs/06-architecture.md` 第 4 节的目录树是**规划态**（已在文中标注），与实际结构差异很大
（实际 `src/features/` 有 13 个域，无 route group）。
这类不一致在本仓库不止一处——**团队应把「文档与实现冲突」当作一个必须先判定的信号，而不是默认相信文档**。

### 4.3 验证缺口会被当成已完成的

`docs/13` 的 90 分就是这种误读的产物。**团队评审时，把「已验证」作为独立维度单独问**：
「这个能力，**跑通过几次**？有数据吗？」——而不是「代码在吗？」

## 5. 分工建议

按 `docs/13` 的能力域权重（【依据：文件】）：

| 能力域 | 权重 | 适合谁 | 当前状态 |
| --- | ---: | --- | --- |
| 主张、证据与可靠发布 | 22 | 最需要人手；也是**验证缺口最大**的一块 | 建成 20 / 验证 ~4 |
| 记录与生命周期 | 18 | 相对稳定 | 建成 18 / 验证 ~12 |
| 结构化与检索 | 16 | | 建成 14 / 验证 ~8 |
| AI 整理与可追溯性 | 16 | 需处理**延迟与可观测性**残余问题 | 建成 15 / 验证 ~5 |
| 运行、质量与恢复 | 11 | **恢复演练从未做过**、渗透测试从未做过 | 建成 9 / 验证 ~6 |
| 身份与小群体使用 | 10 | 需建第二个账号（阶段 1 硬前提） | 建成 9 / 验证 ~4 |
| App 与外部客户端准备 | 7 | 见 `docs/18` 的 M0–M4 | 建成 5 / 验证 ~1 |

**团队化后第一个该补的位置不是写代码，是「运行与恢复」**：
备份在跑且可校验，但**从未从备份恢复过一次整机**。「能备份」≠「能恢复」。

## 7. 一句话结论

> **这个项目的规则层、系统层、代码层写得比大多数团队项目完整，且有自我克制；
> 它的坑几乎全部是「某一环写好了，下一环没接上」。**
>
> 团队接手的价值不在于重写，在于**把已经写好的机制接上**——
> 先把「跑的是不是这一版」断言上，再把核心链路跑通一次，然后才谈扩展。
