# 2026-09-07 本地备份与恢复演练

- 环境：Windows Docker Desktop 29.6.2，独立 Compose project `knowtrace-stage2-fixture`。
- 目的：在 SSH 故障期间提前验证 Linux 备份/恢复脚本的真实容器行为。
- 证据级别：本地隔离模拟，不是 VPS 生产备份，不计入异地备份或生产 RPO/RTO。

## 隔离设计

- PostgreSQL、MySQL、Redis 使用 tmpfs，不挂载 KnowTrace 本地或 VPS 的生产卷。
- app/auth 使用两个临时 Nginx 容器，仅监听 `127.0.0.1:13000` 和 `127.0.0.1:18082`。
- 源 fixture 数据：PostgreSQL 2 表/5 行、MySQL 2 表/4 行、Redis 2 个带 TTL key、1 个 45 字节附件。
- 恢复容器不发布端口、网络设置为 `none`，并带 `com.knowtrace.purpose=restore-check` 标签。

## 首轮发现与修复

1. Redis `BGSAVE` 状态竞态：脚本读到上一次 `ok` 后过早复制。改为等待旧任务结束，记录 `rdb_saves`，必须看到计数递增且新任务结束。
2. Docker archive API 无法从 fixture tmpfs 导出 RDB：容器内文件存在，但 `docker cp` 报不存在。改为 `docker compose exec -T ... cat` 二进制流式导出。
3. MySQL 就绪误判：`mysqladmin ping` 在认证尚未完成时也可表示服务有响应。改为使用目标 root 凭据执行 `SELECT 1`。
4. MySQL 表统计漏项：循环内 `docker compose exec -T` 消耗了表名列表的 stdin。计数查询显式从 `/dev/null` 读取。

每次备份失败后，app/auth 都由 EXIT trap 自动恢复 healthy，失败目录以 `.incomplete-*` 保留；不被当成有效备份。

## 清理验证

```text
fixture_containers_remaining=0
fixture_network_remaining=0
restore_check_containers_remaining=0
```

Compose fixture 只使用 tmpfs，因此清理时没有使用 `down --volumes`，也没有生产卷可删除。脱敏归档保留在工作区 fixture 目录作为本地演练证据。
