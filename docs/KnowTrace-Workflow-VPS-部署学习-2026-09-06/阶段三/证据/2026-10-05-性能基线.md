## 3. 结论（只有三条，都直接读得出来）

### 3.1 延迟的绝大部分在网络，不在应用

公网 p50 406 ms vs 本机 p50 18 ms —— **相差约 22 倍**，而两者打的是同一个端点、同一份代码。
公网那 390 ms 是 TLS 握手 + 跨境 RTT + 边缘代理，不是应用的 CPU 时间。

**含义**：在这条链路上优化应用代码，对公网用户的体感几乎不可见。
要改善体感，该动的是**就近接入**（CDN / 区域节点），不是应用。

### 3.2 拐点在 200 rps 一带，且伴随尾延迟恶化

并发从 5 提到 20（×4），RPS 只从 211 涨到 242（×1.15），而 **p50 从 18 ms 涨到 66 ms（×3.6）、
p99 从 163 ms 涨到 543 ms**。

**含义**：这台机器在约 200 rps 附近开始排队。**注意这是健康端点**（几乎不碰数据库）——
真实业务读写路径的拐点只会更低。所以任何「面向公众」的容量规划都应以**远低于** 200 rps
的余量为准，而不是拿这个数字当容量。

### 3.3 压测本身没有把机器压垮，但也几乎没留余量

压测中 `app` 容器峰值 154 MB（限额 1.8 GB）、CPU 1.23%，load average 1.16，
60 秒内应用日志无 error/fail/timeout。`postgres` 全程 0%（健康端点不碰库）。

**含义**：瓶颈不在内存、不在数据库，而在 CPU 调度与网络栈。这与 2 vCPU 的预期一致。

## 4. 边界与未做

- **只测健康端点**。业务读路径（`/api/v1/captures` 等）**未测** —— 那需要种子数据，
  而生产库当前是空的（见 `KT-GAP-16`）。
- **未做长跑（soak）**。四档合计 1600 请求、约 66 秒，不足以暴露内存泄漏或连接池耗尽。
- **未做写入测试**。工具设计上只能 GET；写入路径的并发与幂等行为**未被验证**——
  `docs/18` §5 风险清单里「离线队列复用 `Idempotency-Key`」正属于这一类。
- **一次采样，未重复**。没有做多时段对照，日间负载差异未纳入。

## 5. 一个必须记下的坑：Python 默认 CA

首次以 `python-default` CA 跑公网档，**200/200 全部 `CERTIFICATE_VERIFY_FAILED`**
（`certificate has expired`）。查证后确认**服务器证书是有效的**
（`notBefore=Oct 3 07:55:09 2026` / `notAfter=Jan 1 07:55:08 2027`，issuer `Let's Encrypt YE1`），
curl 走 Windows 证书库也正常返回 200。

**所以那不是生产故障，是本机 Python 的 CA 包过期。** 换 `--ca-file "$(python -m certifi)"` 后
200/200 成功。这与 `阶段二/Bug记录/BUG-S2-005-Python默认CA导致公网压测TLS失败.md` 是**同一个问题**，
只是重装系统后又遇到了一次。

> ⚠️ 排障提示：`load-baseline.py` 失败时**先看 `error_examples`**，
> 别把 `network_error: 200` 读成「服务挂了」。
