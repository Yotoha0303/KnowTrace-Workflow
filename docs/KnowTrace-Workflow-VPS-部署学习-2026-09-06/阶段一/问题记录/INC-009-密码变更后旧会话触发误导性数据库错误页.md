# INC-009：密码变更后旧会话触发误导性数据库错误页

## 基本信息

- 发生时间：2026-09-06 23:42（Asia/Shanghai）
- 影响环境：线上 `https://knowtrace.duckdns.org`
- 当前状态：业务访问已恢复；会话过期缺陷已定位到代码；永久修复尚未上线
- 数据安全：未发现数据丢失或数据库损坏
- 保密说明：本记录不保存密码、Cookie、令牌、密钥或客户端 IP

## 用户现象

登录后的页面短暂显示：

> 暂时无法读取知识库。请确认数据库已经启动，然后重试。

用户在该时段无法正常读取知识库，页面提供“重新加载”按钮。

2026-09-07 用户补充了稳定触发条件：在记录页面使用 AI 修改内容，停留一段时间后再点击“保存修改”，会出现同一个“找不到数据库”错误页。AI 调用本身不是数据库故障点；关键条件是页面长时间保持打开后才提交保存。

## 影响范围

- 影响已登录用户当前浏览器会话。
- 从截图时间和访问日志比对，异常窗口约为 20 秒；随后刷新和知识采集页面请求恢复为 HTTP 200。
- 未观察到数据库停止、容器重启、磁盘耗尽、内存耗尽或迁移失败。

## 排查证据

### 1. 服务和数据库保持健康

- `app`、`auth`、`auth-mysql`、`auth-redis`、`postgres` 容器均为 healthy。
- 应用 `/api/health/live`、`/api/health/ready` 均返回 HTTP 200。
- 认证服务 `/livez`、`/readyz` 均返回 HTTP 200。
- 公网健康检查和 `/login` 均返回 HTTP 200。
- PostgreSQL 已应用 22 个迁移，核心表存在；`workspaces`、`workspace_memberships`、`captures` 中存在业务数据。
- PostgreSQL 近期日志没有 `ERROR` 或 `FATAL`；Nginx 错误日志为空。
- VPS 磁盘和内存仍有余量，不符合资源耗尽特征。

结论：截图中的“请确认数据库已经启动”不是本次故障的真实原因。

### 2. 密码变更使旧会话失效

- 管理员账户在 2026-09-06 23:09:46（Asia/Shanghai）更新密码并成功登录。
- 认证库中该账户的 `auth_version` 已变为 2；代码在修改密码时递增该字段，使旧访问令牌失效。
- 应用修改密码成功后会清除当前会话 Cookie，并重定向到 `/login?passwordChanged=1`。
- 部署环境中的初始化密码只用于首次创建管理员。管理员已经存在时，初始化任务会跳过，不会用 `.env` 再次覆盖当前密码。
- 只读验证确认：部署 `.env` 中的初始化密码已经不能通过认证，也不匹配认证库当前密码哈希。

结论：密码变更后继续使用旧页面或旧会话，会进入需要重新认证的状态；部署 `.env` 中的初始化密码不再是当前管理员密码。

### 3. 故障窗口与自动恢复

- 截图文件时间：2026-09-06 23:42:15（Asia/Shanghai）。
- 同一时段访问日志出现连续登录、刷新和页面导航请求，符合浏览器在旧会话与新会话之间切换的特征。
- 2026-09-06 23:42:35，刷新请求返回 HTTP 200。
- 2026-09-06 23:42:35 至 23:42:36，知识采集页面的 RSC 请求返回 HTTP 200。

结论：用户浏览器重新取得有效会话后恢复，未执行数据库修复或容器重启。

### 4. 长时间编辑后的会话过期链路

- 认证服务的 Access Token 默认有效期为 15 分钟；Refresh Token 默认有效期为 168 小时。
- KnowTrace-Workflow 当前只在登录页组件加载时调用 `/api/v1/auth/refresh`，应用主界面没有定时续期，也没有在页面重新获得焦点时续期。
- 点击“保存修改”调用 Next.js Server Action。认证代理只验证 Access Token；过期后不会先尝试 Refresh Token。
- 对于认证失败的非 API 请求，代理统一返回登录页重定向，没有针对 Server Action 返回可识别的认证错误。
- 使用不带真实令牌的本地模拟请求验证：`POST /captures/demo` 携带 `next-action` 请求头时，代理返回 HTTP 307 和 `Location: /login`，而不是 Server Action 可消费的结构化认证结果。
- 保存 Action 自身虽然可以返回 `AUTH_REQUIRED`，但请求可能先在代理层被重定向，客户端无法得到预期的 Action 结果。
- 全局错误边界把所有未处理错误固定显示成“请确认数据库已经启动”，掩盖了真正的认证状态。

结论：用户补充的“AI 修改后等待一段时间再保存”与 15 分钟 Access Token 过期窗口吻合。缺少工作区会话续期、代理未区分 Server Action、全局错误文案误报，是同一故障链上的三个代码缺陷。

## 根因结论

### 已确认事实

1. 数据库和服务在故障窗口保持健康。
2. 管理员密码已被修改，旧令牌会因 `auth_version` 递增而失效。
3. 全局错误页会把任意未处理异常统一显示为“数据库未启动”，因此页面提示具有误导性。
4. 页面随后恢复，服务端没有进行重启或数据修复。
5. Access Token 默认 15 分钟过期，应用工作区没有主动会话续期机制。
6. 认证代理不会使用 Refresh Token 恢复过期会话，也没有单独处理 Server Action 的认证失败。

### 高概率推断

密码变更或长时间编辑后，浏览器中的旧页面发起保存请求时携带失效 Access Token；请求在代理重定向和 Server Action 响应解析之间失败，继而进入全局错误边界，最终显示错误的数据库故障文案。

### 尚未确认

当前应用日志没有记录该次异常的 error digest、请求 ID 或完整调用栈，也尚未在线上对“等待超过 15 分钟后保存”进行受控复现。因此，代理重定向之后由 Next.js 客户端抛出错误的具体位置仍属于高概率推断；不能把某个具体数据库查询认定为直接故障点。

## 恢复操作

1. 未重启数据库或应用容器，避免扩大影响和破坏现场证据。
2. 验证健康检查、数据库迁移、核心表、业务记录和资源余量。
3. 根据访问日志确认浏览器刷新并重新取得有效会话后，知识采集页面恢复 HTTP 200。
4. 当前公网 live、ready 和登录页均可访问。

## 遗留问题与改进项

- [ ] 将全局错误页改为中性说明，例如“页面暂时无法加载”，不要在没有证据时断言数据库未启动。
- [ ] 对认证失效进行专门处理：清理失效 Cookie，并引导用户返回登录页。
- [ ] 在应用工作区增加安全的会话续期机制：在 Access Token 到期前刷新，并处理页面重新获得焦点的场景；多标签页刷新必须串行，避免 Refresh Token 重放。
- [ ] 让认证代理识别 Server Action，认证失效时返回客户端可处理的结果，不要把 POST 保存请求重定向成普通登录页 HTML。
- [ ] 为全局错误边界和服务端数据读取记录 error digest、请求 ID、错误分类，不记录密码和令牌。
- [ ] 在部署文档中明确：`.env` 中的管理员密码是首次初始化凭据，修改密码后不会自动同步，也不能当作当前密码恢复来源。
- [ ] 增加“修改密码后旧页面继续导航”的回归测试。
- [ ] 增加“页面保持打开超过 Access Token 有效期后保存”的端到端回归测试。
