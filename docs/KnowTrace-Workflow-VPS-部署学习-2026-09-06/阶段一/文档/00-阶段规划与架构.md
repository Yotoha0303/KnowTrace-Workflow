# 阶段规划与架构

> 历史说明：本文保留阶段一执行时的原始规划，因此后文阶段编号与最终计划不完全一致。最终阶段划分以本学习包根目录的 `总览/00-真实项目计划-阶段一至三.md` 为准。

## 业务资产

KnowTrace-Workflow 当前需要保护的状态包括：

- PostgreSQL：记录、Claim、Evidence 和 Workspace 数据。
- MySQL：用户、角色和认证数据。
- Redis：认证会话状态（可重建会导致会话失效）。
- `/opt/knowtrace/data/uploads`：上传的证据文件。
- `.env`：数据库、JWT、初始管理员等秘密，只保存在 VPS，权限 `600`。

## 阶段一流量路径

```text
浏览器
  │ HTTPS :443
  ▼
Caddy（公网 TLS、证书续期、边缘访问日志）
  │ HTTP 127.0.0.1:8080
  ▼
Nginx（反向代理、真实 IP、应用访问/错误日志）
  │ HTTP 127.0.0.1:3000
  ▼
KnowTrace-Workflow Compose app
  ├─ PostgreSQL（仅容器网络；宿主机 127.0.0.1:15432）
  ├─ Go auth（宿主机 127.0.0.1:8082）
  ├─ MySQL（仅容器网络）
  └─ Redis（仅容器网络）
```

## 为什么同时保留 Caddy 和 Nginx

用户明确要求 Caddy + Nginx，因此阶段一采用分层代理：Caddy 专门负责公网 HTTPS，Nginx 保留为应用入口与日志层。单应用场景中 Caddy 本可直接代理到应用；双层代理增加一个故障点，但能满足本次学习目标。故障排查顺序必须是 Caddy → Nginx → 应用容器 → 数据依赖。
