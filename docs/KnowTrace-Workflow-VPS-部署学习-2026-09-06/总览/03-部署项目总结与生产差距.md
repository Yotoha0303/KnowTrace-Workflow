# KnowTrace-Workflow VPS 部署总结与生产差距

## 一句话结论

KnowTrace-Workflow 已完成“单 VPS 公网部署 + HTTPS + 容器化 + 可恢复备份 + 基础可观测性”的真实远程实践，但仍是资源受限的单节点个人项目，不能称为高可用、具备 SLA 或经过真实规模验证的企业生产系统。

## 已经做到的部分

| 领域 | 已有实现与证据 | 可以诚实表达为 |
| --- | --- | --- |
| 上线 | 公网域名、HTTPS、登录页、健康端点 | 在真实云 VPS 上完成公网部署与 HTTPS 验证 |
| 容器化 | Compose 管理 app、auth、PostgreSQL、MySQL、Redis | 完成多服务 Docker Compose 部署 |
| 网络边界 | Caddy → Nginx → app，数据库和监控端口不公网暴露 | 配置分层反向代理与最小端口暴露 |
| 日志 | Caddy/Nginx/Docker 日志及轮转；ELK 可查询验证事件 | 建立基础日志采集和集中检索链路 |
| 备份 | 全量归档、SHA-256、隔离恢复、定时器、保留策略 | 完成备份与隔离恢复验证 |
| 压测 | 内部/公网健康端点 200 请求、并发 5、零失败 | 建立低风险性能基线 |
| 故障 | SSH 入口误判与 Blackbox 中断演练 | 形成证据、止损、定位、恢复和复盘闭环 |
| 指标 | Prometheus 12/12 targets、Grafana dashboard | 建立应用与主机指标可视化 |
| 告警 | Prometheus → Alertmanager 已验证 | 验证本地告警链路，不含外部送达 |

## 尚不能声称的内容

- 不能声称高可用、零停机、SLA/SLO 持续达标；
- 不能声称支持某个真实并发用户数或生产峰值；
- 不能声称完整灾难恢复已经通过，因为业务登录、历史记录和真实附件读取仍缺证据；
- 不能声称企业级 ELK，当前 ELK 与业务共用一台约 2 GiB VPS，并明显使用 swap；
- 不能声称邮箱告警完成，因为没有实际收件证据；
- 不能声称 Kubernetes、ACK、自动扩容或多节点能力，本目录明确排除第四阶段。

## P0：进入更真实用户阶段前必须补齐

### 1. 凭据与访问安全

- 作废曾在聊天中暴露的邮箱授权码，重新生成并只通过隐藏输入配置；
- 从公网 root SSH 逐步迁移到个人非 root 管理账号 + sudo；
- 建立 VPN/ZTNA 或云堡垒机入口，再考虑限制 SSH 来源地址；
- 为 Grafana/Kibana 建立个人身份、最小权限和审计，避免共享管理员账号；
- 建立秘密管理和轮换制度，不依赖长期散落的 `.env`。

### 2. 完成业务级恢复验收

当前 `RESTORE_VERIFY=PASS` 证明数据库、Redis 和文件统计可恢复，但还需要：

1. 准备一条非敏感、可识别的测试记录和真实附件；
2. 在独立恢复环境登录当前账号；
3. 读取历史记录、Claim/Evidence 关系和附件；
4. 验证保存或更新流程；
5. 记录实际 RPO、RTO 和验收时间。

### 3. 建立外部告警通道

监控与业务同机时，整机宕机可能同时失去 Prometheus 和 Alertmanager。至少增加：

- 服务器外部的 HTTPS/TCP 探测；
- 实际可送达的邮箱、电话或 IM 告警；
- 去重、抑制、升级和静默审计；
- 每月测试告警送达，不能只看配置存在。

### 4. 统一发布身份

当前 VPS 仓库 HEAD 与运行中 app 报告的 revision 不同，可能是后续只更新运维脚本而未重建应用。生产发布应生成 release manifest，至少绑定：

- Git commit；
- 镜像 digest；
- Compose/IaC 版本；
- 数据库 migration；
- 发布时间、操作者、备份 ID 和回滚点。

## P1：从单机实验走向生产化

| 差距 | 当前情况 | 建议目标 |
| --- | --- | --- |
| 单点故障 | 应用、数据库、监控、日志均在一台 VPS | 应用多副本；数据库托管/主从；监控与业务分离 |
| 存储 | 单磁盘、上传文件在本机 | 对象存储、数据库独立备份、跨账号/跨区域副本 |
| 备份 | 有本地 timer 和一次异地验证 | 持续异地复制、不可变保留、定期全流程恢复演练 |
| 发布 | Compose 分支部署 | CI/CD、审批、制品签名、镜像扫描、分批发布和自动回滚门禁 |
| 网络 | 公网 80/443/22345 | VPC 分层、WAF/CDN、VPN/堡垒机、云安全组与主机防火墙双层控制 |
| 可观测 | 同机 Prometheus/ELK，7 天本地留存 | 独立或托管监控/日志、长期存储、权限与审计 |
| 运维权限 | root 密钥直连 | 独立账号、MFA、临时提权、操作审计和密钥轮换 |
| 容量 | 健康端点短时基线 | 真实业务读写、长稳、峰值、依赖故障和容量模型 |

## P2：持续运营能力

- 定义 SLI/SLO，例如可用率、错误率和 P95/P99，而不是只看容器 alive；
- 建立 error budget、值班制度、升级路径、故障复盘和改进项追踪；
- 用 Ansible/Terraform 等 IaC 重建服务器，定期做空环境演练；
- 增加数据库慢查询、连接池、队列、外部 API、AI 调用成本与超时指标；
- 执行依赖安全扫描、SBOM、镜像签名和补丁窗口；
- 用真实但脱敏的业务旅程做合成监控和恢复验收；
- 收集真实用户反馈后再做容量和架构决策。

## 适合写入项目经历的事实表述

> 在单台 Ubuntu 云服务器上，使用 Docker Compose、Caddy、Nginx 部署 KnowTrace-Workflow 多服务应用，配置公网域名与 HTTPS；编写 Bash/Python 脚本实现 PostgreSQL、MySQL、Redis 和附件的备份、SHA-256 校验及隔离恢复；使用 Prometheus、Grafana、Alertmanager 和按需 ELK 建立基础可观测性，并通过受控故障演练验证告警发现与恢复流程。

应同时标注它是个人运维/SRE实践项目，并保留“单 VPS、短时基线、业务级恢复和外部邮件仍有缺口”的边界。
