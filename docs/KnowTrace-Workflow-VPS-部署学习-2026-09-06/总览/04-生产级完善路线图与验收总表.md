# KnowTrace-Workflow 生产级完善路线图与验收总表

> 文档性质：设计与验收计划。
>
> 本文没有执行生产部署、故障注入、压测、数据库恢复或线上配置修改。文中的命令、流程和验收项属于后续操作思路，不能作为“已经达到生产级”的证据。

## 1. 目标和边界

“生产级”不是安装了 Kubernetes、Prometheus 或 ELK，而是系统在真实用户、真实数据和真实故障下满足约定的安全性、可恢复性、可观测性和变更能力。

KnowTrace-Workflow 应分两个目标建设：

### 目标 A：小规模真实生产基线

- 单区域部署。
- 邀请制的小团队用户，而不是匿名公网注册。
- 允许单机应用，但必须能恢复、能回滚、能告警。
- 数据不可因普通升级或容器重建丢失。
- 先采用初始目标 RPO 24 小时、RTO 4 小时，待恢复演练后调整。
- 不宣称高可用。

### 目标 B：企业高可用生产

- 应用多副本和独立故障域。
- 数据库、Redis、对象存储具备高可用或托管能力。
- 发布、扩缩容、监控和告警平台化。
- 具有明确 SLO、值班、容量和灾难恢复制度。

当前阶段只应先完成目标 A。目标 A 没有通过前，不进入 Kubernetes 多副本建设。

## 2. 证据状态定义

后续所有清单统一使用以下状态，禁止混用：

| 状态 | 含义 |
|---|---|
| `未实施` | 只有想法或文档，没有配置和代码 |
| `已实现未验证` | 已有代码或配置，但未在对应环境执行 |
| `本地验证` | Windows/Docker Desktop 或本地 Ubuntu 实验通过 |
| `远程实验验证` | 在远程 VPS/测试环境通过，但不是正式生产流量 |
| `生产验证` | 在真实目标环境按变更流程执行并留下业务证据 |
| `持续达标` | 连续观察期内达到 SLO、告警、备份和容量目标 |

单元测试通过不能替代线上恢复；配置文件存在不能替代服务生效；容器 `running` 不能替代用户可以登录和保存。

## 4. 从已有故障案例得到的生产门禁

| 案例 | 暴露的问题 | 对应生产门禁 |
|---|---|---|
| INC-001 UFW规则存在但未启用 | 配置存在不代表实际生效 | 安全验收必须检查运行状态和真实端口 |
| INC-002 SSH密钥首次验证失败 | 密钥文件存在不代表签名登录成功 | 禁用密码前必须用独立终端完成密钥登录 |
| INC-003 DNS仍指向旧IP | 服务器配置正确也可能因DNS失败 | TLS前从本机、公共DNS和服务器多视角验证 |
| INC-004 Caddy日志权限 | root校验成功不代表服务用户能读取 | 配置必须以真实运行用户验证权限 |
| INC-005 浏览器控制中断 | 验证工具故障不等于业务故障 | 工具链与业务链路分开记录，保留替代验证方式 |
| INC-006 本机目录权限 | 文档交付也受文件权限和边界影响 | 自动化脚本必须检查目标路径和写权限 |
| INC-007 Windows直连失败 | 单一客户端失败不能证明服务器失败 | 外部、服务器本机、容器内部三层验证 |
| INC-008 注册入口关闭 | 功能存在、配置策略和UI入口是三件事 | 认证策略、路由、界面和实际接口必须一致 |
| INC-009旧会话误报数据库错误 | 基础健康正常不代表用户操作成功 | 必须监控登录、刷新、保存等业务链路；错误分类要准确 |
| Grafana停止演练 | `up=1` 只说明抓到了 Blackbox Exporter | HTTP可用性使用 `probe_success`，并验证告警通知 |
| 现有备份脚本 | 能生成文件不代表能恢复 | 必须恢复到空环境并验证登录、记录和附件 |

这些案例应转化为自动验收、Runbook和故障演练，不能只保留为复盘文档。

## 5. 目标生产架构演进

### 5.1 目标 A：单区域生产基线

```text
公网用户
   │
DNS / HTTPS / Caddy
   │
Nginx
   │
KnowTrace-Workflow App ───── Auth Service
   │                    ├── MySQL
   ├── PostgreSQL       └── Redis
   └── 对象存储

独立监控入口
   ├── Prometheus / Alertmanager / Grafana
   ├── Node Exporter / cAdvisor / DB Exporters
   └── 外部 Blackbox 探测

异机备份
   ├── PostgreSQL
   ├── MySQL
   ├── Redis恢复策略
   ├── 对象存储/附件
   └── 加密配置与版本清单
```

初期监控可以与应用同机用于学习，但必须增加外部探测，否则 VPS 整机宕机时本机 Prometheus 也无法告警。

### 5.2 目标 B：高可用演进

```text
CDN/WAF/Load Balancer
          │
   多副本无状态应用
      ├── KnowTrace-Workflow Pods
      └── AI Worker Pods
          │
   托管/高可用数据层
      ├── PostgreSQL
      ├── MySQL或统一身份服务
      ├── Redis
      └── 对象存储
```

进入多副本前必须解决：本地附件、应用启动自动 Migration、AI 同步长请求、Server Actions 一致密钥、部署版本标识和跨实例缓存协调。

参考：

- [Next.js Self-Hosting](https://nextjs.org/docs/app/guides/self-hosting)
- [Kubernetes Production Environment](https://kubernetes.io/docs/setup/production-environment/)

## 6. 标准变更流程

每一项生产完善工作都走同一条流程：

```text
定义用户影响和验收目标
  → 记录现状证据
  → 设计方案和回滚
  → 在隔离环境实现
  → 自动测试和安全检查
  → 预发布环境验证
  → 变更审批/维护窗口
  → 小范围发布
  → 业务冒烟
  → 指标观察
  → 完整发布或回滚
  → 保存证据和复盘
```

每个变更工单至少包含：

- 变更目标和业务价值。
- 影响服务、端口、数据表、volume和用户。
- 依赖和前置检查。
- 实施命令或流水线入口。
- 数据库兼容性说明。
- 预期指标变化。
- 明确回滚条件。
- 回滚步骤。
- 验收人和观察时间。
- 去敏后的日志、截图、CI链接和commit。

## 7. 分阶段建设路线

### 阶段 P0：先消除上线阻断项

#### P0-1 修复会话过期保存故障

当前依据：INC-009 已定位为 Access Token 过期、Server Action未正确恢复会话、错误页面误报数据库故障。

操作思路：

1. 统一页面请求、Route Handler和Server Action的会话刷新策略。
2. 刷新失败时返回明确的认证过期错误，不伪装成数据库故障。
3. 保存前保留用户尚未提交的内容。
4. 加入超过15分钟再保存、密码变更后旧页面保存和并发刷新测试。

验收标准：

- [ ] 页面停留超过 Access Token 生命周期后仍能保存，或明确提示重新登录且内容不丢失。
- [ ] 密码变更后旧会话失败被分类为认证问题。
- [ ] 数据库健康时页面不会显示“数据库未启动”。
- [ ] 自动测试能在旧实现上失败、在修复后通过。
- [ ] 日志通过 Request ID 关联认证失败和保存请求，不记录Token或正文。

#### P0-2 建立完整恢复能力

操作思路：

1. 同一备份批次保存 PostgreSQL、MySQL、Redis策略、附件/对象存储和配置清单。
2. 每份备份保存时间、commit、大小和SHA-256。
3. 复制到与VPS不同故障域的加密存储。
4. 在空环境恢复，不直接覆盖生产作为首次测试。
5. 使用测试账号验证登录、记录、Evidence、附件、保存和搜索。

验收标准：

- [ ] 自动备份连续成功，并能检测备份过期。
- [ ] 本机和异机副本SHA-256一致。
- [ ] PostgreSQL、MySQL、Redis策略和附件全部有恢复步骤。
- [ ] 空环境恢复后完成业务冒烟。
- [ ] 实测RPO不超过约定目标。
- [ ] 实测RTO不超过约定目标。
- [ ] 每月恢复演练有记录。

详细SOP：[07-备份巡检与故障处理SOP.md](../阶段二/文档/07-备份巡检与故障处理SOP.md)。

#### P0-3 拆分 Migration 与应用启动

当前问题：根级 `Dockerfile` 在启动命令中依次运行Migration、Maintenance和Server。

操作思路：

1. CI先在空数据库和升级数据库验证Migration。
2. 发布时由唯一Migration Job执行。
3. 应用镜像只启动应用，不自动改Schema。
4. 使用expand/contract方式保持新旧版本短期兼容。
5. 破坏性Migration必须单独审批和备份。

验收标准：

- [ ] 同时启动两个应用副本不会并发执行Migration。
- [ ] Migration失败时新应用不会接收流量。
- [ ] 上一个应用版本仍能在兼容窗口工作。
- [ ] Migration版本、日志和执行人可追踪。
- [ ] 回滚应用不依赖盲目回滚数据库。

#### P0-4 建立安全发布和仓库保护

操作思路：

1. 保护 `main`，禁止直接推送，要求PR和必需CI。
2. 开启Secret Scanning、Push Protection和私密漏洞报告。
3. CI增加Go测试、MySQL/Redis集成、Playwright关键链路。
4. 构建固定commit的镜像，推送到Registry并记录digest。
5. 生成SBOM，执行SAST、依赖和镜像扫描。
6. 测试、预发布、生产使用同一个镜像digest晋级。
7. 保留上一稳定镜像和一键回滚入口。

验收标准：

- [ ] `main`不能绕过PR和必需检查直接修改。
- [ ] 提交测试密钥会被Push Protection阻止。
- [ ] 前端、Go、数据库集成和关键E2E全部进入CI。
- [ ] 高危可达漏洞阻断发布。
- [ ] 发布记录包含commit、镜像digest、SBOM和扫描报告。
- [ ] 在预发布环境成功部署上一版本和当前版本，并演练回滚。

#### P0-5 完成生产密钥和入口策略

操作思路：

1. 生产Compose不允许回退到固定数据库密码和默认管理员密码。
2. 密钥由受控Secret文件或Secret Manager注入。
3. 数据库应用账号最小权限，备份账号单独授权。
4. 记录密钥轮换周期、负责人和回滚方式。
5. 注册默认关闭；开放注册前增加滥用控制和业务审批。
6. 验证Secure、HttpOnly、SameSite Cookie和真实代理地址。
7. 增加CSP、`frame-ancestors`和必要的安全响应头。

验收标准：

- [ ] 缺失生产密钥时服务拒绝启动，不使用默认值。
- [ ] 仓库、CI日志、镜像层和监控标签不含密钥。
- [ ] JWT、数据库和管理员密码能够独立轮换。
- [ ] 密钥轮换后新登录成功、旧会话按策略失效。
- [ ] `/metrics`、数据库、Redis和认证内部端口不暴露公网。
- [ ] 安全头和Cookie属性有实际HTTPS响应证据。

### 阶段 P1：形成可运维生产系统

#### P1-1 可观测性和告警

操作思路：

1. Next.js主应用增加低基数RED指标。
2. Prometheus采集auth、Node Exporter、cAdvisor和数据库exporters。
3. Blackbox从外部探测登录页、live和ready。
4. Alertmanager发送到真实通知渠道。
5. Grafana按用户体验、应用、依赖、主机、备份五层展示。
6. 每条可执行告警关联Runbook。

验收标准：

- [ ] 登录、保存、AI任务的请求量、错误率和延迟可查询。
- [ ] PostgreSQL、MySQL、Redis、容器和主机指标可查询。
- [ ] VPS整机不可达时外部监控能够通知。
- [ ] 备份超过26小时未成功会通知。
- [ ] 故障演练中告警从pending进入firing，恢复后清除。
- [ ] 通知实际到达接收人，而不只是Prometheus页面显示。

详细设计：[08-Prometheus容器监控与企业实践.md](../阶段三/文档/08-Prometheus容器监控与企业实践.md)。

#### P1-2 结构化日志和链路关联

操作思路：

1. 应用、auth、Nginx和Caddy统一时间、环境、服务和严重级别字段。
2. 从入口生成或接受Request ID，并贯穿应用、auth、AI Run和错误响应。
3. 对外部AI调用增加Trace/Span或至少结构化阶段日志。
4. 去除密码、Token、Cookie、API Key、完整正文和Prompt。
5. 使用Loki/ELK集中查询；小VPS可按需启动，避免抢占业务资源。

验收标准：

- [ ] 输入用户看到的Request ID可检索完整调用链。
- [ ] 日志中没有敏感凭据和完整私人知识内容。
- [ ] 日志轮转和保留不会填满根分区。
- [ ] 容器重建后历史日志仍可按策略查询。

#### P1-3 容器运行时加固

操作思路：

1. 保留应用非root运行。
2. 增加CPU、内存、PID限制和容量预留。
3. 移除不需要的Linux capabilities，禁止提权。
4. 尽可能启用只读根文件系统，仅挂载明确可写目录。
5. 设置优雅终止时间，验证SIGTERM期间不接受新流量且完成在途请求。
6. 固定基础镜像版本或digest并定期更新。

验收标准：

- [ ] 应用以非root运行且不能提权。
- [ ] 超过资源限制时故障可被监控识别，不拖垮整台主机。
- [ ] 滚动停止期间没有已确认的数据损坏。
- [ ] 日志、上传和临时目录的写权限符合最小范围。

#### P1-4 性能和容量

先定义场景，不先写“高并发”：

- 登录与Token刷新。
- 创建和编辑Capture。
- 搜索和分类档案。
- 附件上传与读取。
- AI整理长请求。
- 数据导入/导出。

验收标准：

- [ ] 写明目标并发、请求比例、数据规模和测试时长。
- [ ] 记录p50/p95/p99、错误率、吞吐量和资源峰值。
- [ ] 压测数据与生产数据隔离。
- [ ] 找到第一个瓶颈并保留修改前后对比。
- [ ] 完成长稳测试，证明没有持续内存、连接或磁盘增长。
- [ ] 给出安全容量，不把一次短测峰值当生产承诺。

#### P1-5 AI任务可靠性和成本

当前AI调用在HTTP请求内同步等待，适合小规模功能验证，不适合大量长任务。

操作思路：

1. 将AI Run变成持久化任务，HTTP只提交任务并返回ID。
2. Worker领取任务，使用幂等、租约、超时、有限重试和死信状态。
3. 保存provider、model、prompt/schema版本、耗时、Token和费用。
4. 建立每用户/Workspace限流、并发和每日预算。
5. Provider故障时不影响记录、编辑、分类等非AI功能。

验收标准：

- [ ] 应用或Worker重启后任务不会永久卡在running。
- [ ] 同一任务重试不会重复写Suggestion。
- [ ] 超时、限流和供应商失败有稳定错误码。
- [ ] 费用达到阈值时阻止新任务并通知，不自动删除已有任务。

### 阶段 P2：数据与高可用演进

#### P2-1 对象存储

- [ ] 附件不依赖单个应用容器或单台VPS目录。
- [ ] 上传使用服务端授权、大小/MIME/文件头校验和SHA-256。
- [ ] 对象按Workspace和Evidence权限读取，不公开bucket。
- [ ] 开启版本或备份策略，并验证数据库记录与对象一致性。
- [ ] 孤儿对象和丢失对象有只读审计及人工确认修复流程。

#### P2-2 数据库可靠性

- [ ] 根据RPO决定PostgreSQL WAL/PITR和MySQL binlog策略。
- [ ] 数据库不与应用共享单一故障磁盘，或明确接受该风险。
- [ ] 连接池、慢查询、锁、容量和复制延迟可监控。
- [ ] Schema变更经过升级与回滚兼容验证。
- [ ] 主库故障后的恢复/切换完成业务验证。

#### P2-3 多副本和Kubernetes

- [ ] 应用已无本地业务状态。
- [ ] Migration已独立。
- [ ] AI Worker可独立伸缩。
- [ ] Next.js多实例使用一致的Server Actions密钥和deployment ID。
- [ ] 缓存失效在多实例间协调，或确认当前路由不依赖共享缓存。
- [ ] 使用readiness控制流量，使用liveness检测进程死锁。
- [ ] 设置requests/limits、PDB、滚动发布和反亲和。
- [ ] Prometheus Operator通过ServiceMonitor/PodMonitor采集，不公开`/metrics`。
- [ ] 至少多节点；单节点Kubernetes不得宣称高可用。

## 8. 生产验收门禁总表

只有所有P0门禁通过，才允许目标A正式上线。

| 门禁 | 必须证据 | 当前结论 |
|---|---|---|
| G0 需求边界 | 用户范围、数据敏感度、RPO/RTO、SLO、容量目标 | 部分定义 |
| G1 代码质量 | Typecheck、Lint、单元、Go、集成、E2E、构建 | 部分通过，CI未全覆盖 |
| G2 安全 | 威胁模型、密钥扫描、SAST、依赖/镜像扫描、权限测试 | 部分实现 |
| G3 数据恢复 | 异机备份、空环境恢复、业务验证、RPO/RTO | 未通过 |
| G4 发布回滚 | 不可变镜像、独立Migration、预发布、回滚演练 | 未通过 |
| G5 可观测性 | 主应用指标、日志、外部探测、真实通知、Runbook | 未通过 |
| G6 性能容量 | 目标场景、负载、长稳、资源余量 | 未通过 |
| G7 故障恢复 | auth/DB/Redis/磁盘/Token/入口故障演练 | 部分案例 |
| G8 合规运维 | 审计、保留、删除、巡检、值班、变更记录 | 未通过 |

最终判定规则：

- 任一P0门禁失败：`不允许承载不可替代真实数据`。
- P0全部通过、单机故障仍会中断：`小规模生产基线，不是高可用`。
- 多故障域、恢复、容量和SLO持续达标：才可以评估为`高可用生产`。

## 10. 故障演练清单

所有演练只在隔离环境或明确维护窗口进行，并先准备回滚。

| 编号 | 故障 | 预期行为 | 恢复验收 |
|---|---|---|---|
| DR-01 | 停止KnowTrace-Workflow App | 外部探测告警；数据库不受影响 | App恢复、业务冒烟通过 |
| DR-02 | 停止auth | 登录/受保护请求失败关闭，不匿名降级 | ready恢复、旧/新会话符合策略 |
| DR-03 | 停止PostgreSQL | live可存活、ready失败、写入被拒绝 | 数据库恢复后读写正确 |
| DR-04 | 停止MySQL | auth ready失败、登录不可用 | 用户/角色数据完整 |
| DR-05 | 停止Redis | 生产auth拒绝就绪，不绕过撤销状态 | 会话和限流恢复 |
| DR-06 | 模拟磁盘80%/90% | 分级告警，不自动删除volume | 找到增长来源并安全释放 |
| DR-07 | Access Token过期后保存 | 自动刷新或准确提示，内容不丢 | 保存链路恢复，无数据库误报 |
| DR-08 | AI Provider超时/429 | AI任务失败可解释，非AI功能正常 | 重试受限、无重复结果 |
| DR-09 | 发布坏镜像 | 冒烟/指标阻断继续发布 | 回滚上一digest并验证 |
| DR-10 | 从备份恢复空环境 | 恢复全部数据资产 | 登录、记录、附件、保存通过 |

每次演练记录：检测时间、告警时间、确认时间、恢复时间、根因、证据、用户影响、RTO和改进项。

## 12. 面试和项目说明边界

当前可以说：

> 基于KnowTrace-Workflow真实VPS部署和九次故障记录，设计了从单机Compose生产基线到高可用架构的分阶段方案，覆盖备份恢复、发布回滚、可观测性、安全、容量、故障演练和验收证据。

只有后续实际完成对应实验后，才能分别补充“本地验证”“远程实验验证”或“生产验证”。

当前不能说：

- 已达到企业生产级。
- 已实现高可用或多可用区。
- 已达到某个SLA/SLO。
- 已完成生产容灾。
- 已支撑未经测试的并发量。
- 已建设完整Kubernetes、ELK或GitOps平台。

## 13. 推荐执行顺序

```text
INC-009永久修复
→ 完整备份和空环境恢复
→ 分支/密钥/供应链保护
→ 独立Migration与不可变发布
→ Prometheus/Alertmanager和业务指标
→ 对象存储
→ AI Worker与费用控制
→ 负载/长稳/故障演练
→ SLO观察
→ 最后评估Kubernetes和多副本
```

这条顺序优先解决用户数据丢失、无法回滚、故障不可见和单点状态问题，而不是优先堆叠工具。
