# 真实项目计划：阶段一至三

## 阶段一：上线基础

- [x] 上云：Ubuntu VPS 基线检查、SSH 密钥登录、UFW 与最小公开端口；
- [x] 域名与 HTTPS：DuckDNS、Caddy、Let's Encrypt、HTTP 跳转 HTTPS；
- [x] Docker 部署：Compose 部署 KnowTrace-Workflow、PostgreSQL、MySQL、Redis 和认证服务；
- [x] 日志基础：Docker 日志轮转、Nginx/Caddy access/error 日志。

完成边界：证明当前单机可通过公网域名访问、HTTPS 有效、容器健康；不证明高可用。

## 阶段二：可靠性与迭代

- [x] 全量备份：PostgreSQL、MySQL、Redis、uploads 和恢复配置；
- [x] SHA-256：归档和组件清单校验；
- [x] 隔离恢复：临时容器恢复并输出 `RESTORE_VERIFY=PASS`；
- [x] 加密异地副本：密文离开 VPS 并完成解密流校验；
- [x] 定时备份：systemd timer、14 天且至少 7 份保留策略；
- [x] 低风险压测：内部与公网健康端点各 200 请求、并发 5、零失败；
- [x] Bug 记录：隔离 fixture 中发现并回归多个备份脚本 Bug；
- [x] 真实故障：SSH 端口误判事件完成证据化排查；
- [x] 版本迭代：独立分支、测试门禁、部署与回滚点；
- [ ] 业务级恢复：当前账号登录、已知历史记录和真实附件读取仍未完成。

完成边界：基础设施和数据统计恢复已验证，但不能把它等同于完整业务灾备验收或生产容量。

## 阶段三：可观测性

- [x] Prometheus：应用、认证、主机、Blackbox 和备份新鲜度指标；
- [x] Grafana：数据源与 `KnowTrace-Workflow VPS 可观测性` dashboard 自动配置；
- [x] Alertmanager：Prometheus 告警接收与故障演练链路；
- [x] ELK：Logstash → Elasticsearch → Kibana 验证事件查询、ILM 与 Data View；
- [x] 故障演练：Blackbox 停止后经历发现、firing、Alertmanager 接收、恢复和清除；
- [ ] 外部邮箱告警：仍为 `local-only`，没有实际收件证据。

完成边界：证明单机最小可观测闭环可运行；不证明监控高可用、长期留存、企业权限或真实值班。

## 明确排除

第四阶段 Kubernetes、ACK 集群和真实用户扩展不在本目录中，避免把尚未实施的计划与阶段一至三的实际证据混合。
