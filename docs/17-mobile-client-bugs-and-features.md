## BUG-001 保存后偶发找不到数据库

- 类型：Bug
- 状态：**已修复并上线（2026-10-01）** —— 原「根因已定位」的后续
- 修复内容（2026-10-01，提交 `83c7e76`）：①错误边界不再把任何异常断言成「数据库未启动」，
  改为按类型区分（会话/网络/未知）；②Proxy 在 Access Token 失效时**先尝试用 Refresh Token 续期**。
- **一个中途引入又修掉的回归**：首次加的续期守卫写成 `if (accessToken)`，而 access cookie
  的 maxAge 就是它的有效期——15 分钟一到浏览器直接删掉它，真实场景是「只有 refresh cookie」，
  守卫不成立 → **续期从不触发**，每 15 分钟被踢一次。已修（守卫改看 refresh cookie），
  并补了覆盖真实状态的回归测试（该测试在旧代码上会失败，已证伪）。
  详见 `changes/2026-10-01-会话续期回归与hover转圈.md`。
- 验收：状态「只有 refresh cookie」→ **200**（修前 307），三条状态生产实测全过。
- **根因**：服务器上已存在完整事故报告 `docs/KnowTrace-Workflow-VPS-部署学习-2026-09-06/阶段一/问题记录/INC-009-密码变更后旧会话触发误导性数据库错误页.md`，五个环节闭合：
  1. Access Token 有效期 15 分钟；
  2. **应用主界面没有会话续期**——只在登录页组件加载时调一次 `/api/v1/auth/refresh`（`src/components/login-form.tsx:33`）；
  3. 保存走 Server Action，Proxy 只验证 Access Token，**过期后不会先尝试 Refresh Token**；
  4. 认证失败时 Proxy 对非 API 请求**统一 307 重定向到登录页 HTML**，Server Action 收到 HTML 而非结构化结果，解析失败；
  5. 全局错误边界把所有未处理异常**固定显示成「请确认数据库已经启动」**——于是会话过期被显示成数据库故障。
- **与现象的吻合**：报告人说的「AI 修改后等一段时间再点保存」正是 15 分钟令牌过期窗口。
- **为什么一直没修**：INC-009 写在**运维学习目录**下，不是待办队列；其末尾 8 项改进 checklist 全部未执行。这是信息传导断裂，不是技术难题。
- 需要补充的证据：无（根因已闭合）；若要复现，页面保持打开超过 15 分钟后保存即可
- 验收标准：见 INC-009 末尾的「永久修复验收标准」，共 7 条
- **2026-10-04 对账**：INC-009 的 8 项改进 **5 完成 / 1 部分 / 2 未完成**，7 条验收标准
  **1 已验收 / 3 部分 / 3 未验收**。未完成项已转为 `KT-DEFER-006…009`（见 `docs/14`），
  未验收项多为「缺留痕」而非「缺代码」，需要真实环境跑一次并归档。
  逐条对账见 [`changes/2026-10-04-INC-009改进项与验收标准跟踪.md`](changes/2026-10-04-INC-009改进项与验收标准跟踪.md)。
- 是否进入 PR：否，等排期。详见 `docs/19-product-defect-inventory.md` 的 D-03

## BUG-002 账户无法登录

- 类型：Bug
- 状态：**两条可能成因已于 2026-10-01 消除，但未确证**（【推断】，非【实测】）
- 2026-10-01 新发现并修复了两件事，**都能产生「账户无法登录」的现象**：
  1. **登录限流按容器 IP 计数** → 任一来源失败 20 次会让**全站 15 分钟都登不进去**
     （提交 `53bd38f`）。当时实测复现了这个行为。
  2. **会话续期从不触发** → 每 15 分钟被踢到登录页（提交 `83c7e76`）。
- **为什么只算推断**：原始现象从未被复现，无法确证「就是这两条」。
- **复发时的判据**：先看错误码——`AUTH_LOGIN_RATE_LIMITED` 表示是被限流（等 15 分钟），
  不是密码问题；若是 `AUTH_INVALID_CREDENTIALS` 才回到原假设（并发登录/会话限制）。
  锁定时界面现在会显示「已锁定 + 剩余时间」并倒计时。
- 已完成的修复（2026-09-30）：上游数字业务码不再被丢弃，改为在 `src/features/auth/auth-errors.ts` 翻译成语义错误码。现在限流（上游 2008 → `AUTH_LOGIN_RATE_LIMITED`）、账号停用（2004 → `AUTH_ACCOUNT_DISABLED`）、账号不存在（2003 → `AUTH_ACCOUNT_NOT_FOUND`）和真正的密码错误（2005 → `AUTH_INVALID_CREDENTIALS`）在客户端可以分辨，不再统一显示「账号或密码错误」。下一次出现该问题时，先看错误码即可判断是等一会还是该找管理员。
- 仍待完成：用修复后的错误码复现并定位原始症状。若再次出现且错误码为 `AUTH_INVALID_CREDENTIALS`，则初步推断（并发登录导致会话限制）需要重新评估，因为该假设指向的是 refresh token 被吊销，而密码校验失败是另一条路径。
- 影响：用户登录时无法进行正常登录
- 已知现象：在账户和密码输入后，无法进入主界面，出现账号或密码错误的情况
- 初步推断：登录设备过多，导致后台数据库记录的会话限制了其他地方的登录
- 需要补充的证据：浏览器 Network 里的登录响应原始 JSON（现在含可区分的 `error.code`）、auth 容器日志、MySQL 中该账号的 refresh token 记录、同时登录的设备数与时间
- 验收标准：复现路径明确；多次登录同个账号后，不退出继续登录不出现账号或密码报错的情况；不同失败原因给出可区分的提示
- 是否进入 PR：**是，已进入**（错误码透传部分）。原始症状的修复 PR 待定位原因后另开

## BUG-003 手动添加个人主张和证据时，图片无法正常上传和通过 AI 审核

- 类型：Bug
- 状态：**已修复并实测（2026-10-01）** —— 原「根因已确认」的后续
- 实测证据（2026-10-01）：
  ```text
  上传目录属主:         1001:65533   ← 与容器内 nextjs 身份一致
  容器内写入探测:       WRITE_OK
  应用启动自检告警:     0 次
  evidence_attachments: 3 行         ← 先前为 0，用户实操时真的传上去了
  ```
- **判定：已修，且已被真实使用验证**（不只是「代码改了」）。
- 仍待确认：图片上传后能否通过 AI 审核——本轮未走该分支。
- **根因（实测）**：容器以 `uid=1001(nextjs)` 运行，而 `/app/data/uploads/evidence` 属主是 `root:root 755`，创建于 2026-09-06 13:34，**权限从未调整过**。容器内现场探测 `touch` 返回 `Permission denied` / `WRITE_FAIL`；应用日志中 `EACCES: permission denied` 共 42 次（09-13 38 次、09-19 4 次）。
- **更正**：本节此前把根因推断为「HEIC 不被支持」。**那是错的。** 上传从未成功过一次，与格式无关；格式兼容是修好权限之后才会遇到的第二个问题。详见 `docs/19-product-defect-inventory.md` 的 D-01。
- 影响：上传的图片无法保存到对应的数据记录中，导致信息可靠性待验证
- 已知现象：在某条记录下，手动添加个人主张和证据的表单中，使用图片上传功能会出现图片格式不合适、图片上传失败等问题
- 修复方向：调整宿主机挂载目录属主为 `1001:65533`（或在 compose 中声明卷属主）。注意部署手册用 `cp -r` 不改权限，这类问题会反复出现
- 验收标准：容器内 `touch` 探测返回 `WRITE_OK`；真实上传一张 PNG 后 `evidence_attachments` 出现新行且 `GET /api/evidence-images/:id` 返回 200；随后再处理 HEIC 等格式兼容
- 是否进入 PR：否，根因已确认，等排期

### 已排除的假设

| 曾经的假设 | 现状 |
|---|---|
| HEIC/HEIF 不被支持（`image-validation.ts:9-12` 只允许 jpeg/png/webp/gif） | 仍然成立，但**不是本次根因**——上传在格式校验之前就已失败 |
| 魔数与 `file.type` 严格比对导致误拒（`image-validation.ts:43`） | 同上，是权限修好后的下一个问题 |
| 证据状态门槛（必须 `investigating` + `unreviewed`）造成「上传失败」误读 | 仍可能，但优先级低于权限问题 |
| 「AI 审核」不可用 | 真正的 AI 是 mock（见 `docs/19` 的 D-02），需要单独处理 |

### 代码侧现状（BUG-003 展开）

| 现象 | 代码位置 | 判定 |
|---|---|---|
| 「图片格式不合适」 | 魔数与 `file.type` 必须完全一致 | 高概率命中：HEIC 直接拒绝；声明与实际不符一律拒绝，无兼容回退 |
| 「上传失败」但格式没问题 | `service.ts:331` 证据状态必须 `investigating` + `unreviewed` | 中概率：状态门槛被误读为上传失败，提示语未区分 |
| 公网部署后失败，本机正常 | `readEvidenceImage` 走本地文件系统 `EVIDENCE_UPLOAD_DIR`（`src/features/claims/image-storage.ts:9-14`），依赖挂载卷可写 | 待验证：容器卷权限、磁盘水位、是否多实例部署 |
| 上传成功但看不到图 | `src/app/api/evidence-images/[id]/route.ts` 先做 `requireAttachmentReadAccess`，越权访问按 404 处理 | 待验证：Workspace/成员可见性是否让本人也拿到 404 |

## FEAT-004 AI 整理的内容没有结构化

- 类型：FEAT
- 状态：**部分化解（2026-09-30）**——「AI 只会改错别字」的原判定不是模型能力问题，而是线上提供方为 mock 本地规则
- 影响：散乱的记录无法进行模板化和结构化记录，导致记录的内容混乱且只会修改错别字
- 已知现象：使用 AI 整理后，AI 只能修改句子，没办法显性的结构化记录和协助使用者整理记录
- **根因（实测）**：线上 `AI_DEFAULT_PROVIDER=mock`，且 `DEEPSEEK_API_KEY`/`OPENAI_API_KEY` 均为空，实际执行的是 `knowtrace-local-rules-v1`（确定性规则替换）。已配置真实 DeepSeek 并实测通过：真实模型能稳定输出 `title/summary/contentType/categories` 结构化 JSON，四次都把「同一公司两个来源说法矛盾」抓成标题。详见 `docs/19-product-defect-inventory.md` 的 D-02。
- **仍待解决**：模板化与结构化骨架的**体验层**依然缺失（现有输出是候选字段，不是可套用的模板）；且真实模型延迟 7–20 秒，需要先解决延迟再设计交互。
- 验收标准：AI 可提供模板或者内置模板，AI 协助结构化记录
- 是否进入 PR：否，等延迟问题明确后再设计交互

## FEAT-005 可以语言或文字输入给主界面的 AI 协助记录

- 类型：FEAT
- 状态：待新增
- 影响：避免长期半自动记录和信息审核，记录方式更加便携
- 已知现象：目前记录只能通过手动添加标签或者 AI 提供标签建议和整理来处理文本，通常需要修改多次才能确保信息可靠
- 关联现状：`/api/v1/captures` 已支持幂等创建与乐观锁（`docs/12-mobile-api.md`），文本入口可以复用；语音输入需要新增端上转写或音频上传通道，后者当前不存在。
- 验收标准：新增信息输入主界面，可以通过语音或者文字输入的方式记录内容，完成从散乱记录、AI 信息整理、信息模板化和结构化、内容自动验证、信息自动归档的流程
- 是否进入 PR：否
- 待澄清：首期是「端上语音转文字后走现有文本链路」，还是「上传音频由服务端转写」。两者成本差距很大，进入设计前先定。

## FEAT-006 公网开放注册功能，且使用邮箱验证注册

- 类型：FEAT
- 状态：待新增
- 影响：扩大真实用户量
- 已知现象：注册入口由于安全性问题，在 `.env` 中暂时关闭
- 代码侧现状：开关是 `AUTH_REGISTRATION_ENABLED=false`（`.env.example`），未开启时 `src/proxy.ts:36` 把 `/register` 重定向到 `/login?registration=disabled`。现有注册只接受用户名和密码（`registerWithGoUserSystem`，`src/features/auth/go-user-system.ts:170`），**没有邮箱字段，也没有任何邮件发送设施**——邮箱验证需要先改 go-user-system 的账号模型，不是纯前端改动。
- 验收标准：开发邮箱验证功能，且在用户输入邮箱验证后，能够通过注册界面登录系统
- 是否进入 PR：否
